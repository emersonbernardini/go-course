O problema que generics resolve

Antes de Go 1.18, escrever código que operava sobre múltiplos tipos exigia uma das três abordagens — todas com trade-offs: duplicar o código para cada tipo, usar any (perdendo type safety) ou usar interfaces (limitando quais operações são possíveis). Generics adicionam uma quarta opção: parametrizar o código pelo tipo, mantendo type safety em tempo de compilação.

go o antes: duplicação ou any 
// ✗ Opção 1: duplicar para cada tipo
func MinimoInt(a, b int) int {
    if a < b { return a }
    return b
}
func MinimoFloat64(a, b float64) float64 {
    if a < b { return a }
    return b
}

// ✗ Opção 2: any — perde type safety, requer type assertion
func Minimo(a, b any) any {
    // como comparar? não há operador < em any
    // seria necessário switch de tipo — verboso e quebrável
}

// ✓ Com generics: um único Minimo, type-safe, sem duplicação
func Minimo[T constraints.Ordered](a, b T) T {
    if a < b { return a }
    return b
}

n  := Minimo(3, 7)          // T inferido como int
f  := Minimo(1.5, 2.3)      // T inferido como float64
s  := Minimo("ab", "ac")    // T inferido como string

O compilador instancia uma versão concreta da função para cada tipo usado — sem overhead de runtime, sem reflection, sem boxing. O código genérico é verificado estaticamente: tentar Minimo([]int{}, []int{}) é erro de compilação porque slices não implementam constraints.Ordered.

Generics chegaram tarde — e por bom motivo
Go ficou sem generics por 13 anos (2009–2022) intencionalmente. A equipe queria um design que não comprometesse a legibilidade e a velocidade de compilação. A proposta aprovada em Go 1.18 usa um sistema de constraints baseado em interfaces — mais restrito que C++ templates mas muito mais previsível e com mensagens de erro compreensíveis.

Type parameters e sintaxe

Type parameters são declarados entre colchetes [T Constraint] após o nome da função ou tipo. A constraint define quais tipos são permitidos para T — e portanto quais operações são permitidas sobre valores de tipo T dentro do corpo.

go anatomia da sintaxe genérica 
// Função genérica: [T any] — T pode ser qualquer tipo
func Map[T, U any](slice []T, f func(T) U) []U {
    resultado := make([]U, len(slice))
    for i, v := range slice {
        resultado[i] = f(v)
    }
    return resultado
}

// Múltiplos type parameters com constraints diferentes
func Transformar[T constraints.Integer, U any](vals []T, f func(T) U) []U {
    // T só aceita tipos inteiros; U aceita qualquer coisa
    return Map(vals, f)
}

// Tipo genérico: Stack parametrizado por T
type Stack[T any] struct {
    items []T
}

func (s *Stack[T]) Push(v T) {
    s.items = append(s.items, v)
}

func (s *Stack[T]) Pop() (T, bool) {
    var zero T  // zero value de T — único jeito de obter sem conhecer o tipo
    if len(s.items) == 0 {
        return zero, false
    }
    top := s.items[len(s.items)-1]
    s.items = s.items[:len(s.items)-1]
    return top, true
}

// Instanciação
s := Stack[int]{}          // T=int explícito — tipos não podem ser inferidos em structs
s.Push(1); s.Push(2)
v, ok := s.Pop()           // v=2, ok=true — sem type assertion

Inferência de tipo

Em funções genéricas, o compilador geralmente infere o type parameter a partir dos argumentos — você não precisa escrevê-lo explicitamente. Em tipos genéricos (structs), a inferência não funciona e o tipo precisa ser especificado:

go 
// Funções: T é inferido
nums   := Map([]int{1, 2, 3}, func(n int) string { return strconv.Itoa(n) })
// equivalente explícito: Map[int, string](...)

// Tipos: T deve ser explícito
s1 := Stack[string]{}      // ✓
s2 := Stack{}              // ✗ erro de compilação: missing type argument
Métodos de tipos genéricos não podem ter type parameters próprios
Em Go, métodos de um tipo genérico usam os type parameters do tipo, mas não podem declarar os seus próprios. Isso significa que func (s *Stack[T]) Map[U any](f func(T) U) []U é inválido — você precisaria de uma função livre: func StackMap[T, U any](s *Stack[T], f func(T) U) []U. Essa limitação é intencional e pode ser relaxada em versões futuras.

Constraints

Uma constraint é uma interface que define quais tipos são aceitos como type parameter. Com generics, interfaces ganharam um superpoder: além de listar métodos, podem listar tipos concretos via union elements. Isso permite expressar coisas como "qualquer tipo numérico" ou "qualquer tipo que suporte o operador <".

go definindo constraints 
import "golang.org/x/exp/constraints"

// Constraint com union de tipos concretos
type Numero interface {
    int | int8 | int16 | int32 | int64 |
    uint | uint8 | uint16 | uint32 | uint64 |
    float32 | float64
}

// O til (~) inclui tipos derivados: type MeuInt int também satisfaz ~int
type Inteiro interface {
    ~int | ~int8 | ~int16 | ~int32 | ~int64
}

// Constraint com métodos — como interface tradicional
type Stringer interface {
    String() string
}

// Constraint mista: tipo específico E com método
type StringerOrdered interface {
    ~string
    String() string  // tipos ~string que também tenham String() — raro na prática
}

// Constraints do pacote golang.org/x/exp/constraints (as mais usadas)
// constraints.Ordered  = tipos que suportam <, <=, >, >= (int, float, string)
// constraints.Integer  = todos os tipos inteiros
// constraints.Float    = float32 | float64
// constraints.Signed   = inteiros com sinal
// constraints.Unsigned = inteiros sem sinal

Usando constraints do pacote slices (Go 1.21+)

Go 1.21 adicionou os pacotes slices, maps e cmp à stdlib — todos implementados com generics. Eles substituem boa parte das funções utilitárias que antes exigiam código repetitivo ou dependências externas:

go stdlib genérica (Go 1.21+) 
import (
    "cmp"
    "slices"
    "maps"
)

nums := []int{3, 1, 4, 1, 5, 9, 2, 6}

slices.Sort(nums)                          // ordena in-place
slices.Contains(nums, 5)                   // true
slices.Index(nums, 4)                      // índice de 4
min := slices.Min(nums)                    // 1
slices.Reverse(nums)                       // inverte in-place

// Ordenação com comparador customizado
type Pessoa struct{ Nome string; Idade int }
pessoas := []Pessoa{{"Ana", 30}, {"Bob", 25}, {"Carl", 35}}
slices.SortFunc(pessoas, func(a, b Pessoa) int {
    return cmp.Compare(a.Idade, b.Idade)  // cmp.Compare: -1, 0, ou 1
})

// maps
m := map[string]int{"a": 1, "b": 2}
chaves := maps.Keys(m)      // []string — ordem não garantida
vals   := maps.Values(m)    // []int
maps.Clone(m)               // cópia rasa do map

Padrões genéricos úteis

Alguns padrões emergem naturalmente com generics e eliminam código boilerplate que antes era inevitável. Os mais recorrentes em projetos reais:

Map, Filter, Reduce

go 
func Map[T, U any](s []T, f func(T) U) []U {
    res := make([]U, len(s))
    for i, v := range s { res[i] = f(v) }
    return res
}

func Filter[T any](s []T, pred func(T) bool) []T {
    var res []T
    for _, v := range s {
        if pred(v) { res = append(res, v) }
    }
    return res
}

func Reduce[T, U any](s []T, init U, f func(U, T) U) U {
    acc := init
    for _, v := range s { acc = f(acc, v) }
    return acc
}

// Uso encadeado
nomes := []string{"Ana", "Bob", "Carlos", "Dani"}
comprimentos := Map(
    Filter(nomes, func(s string) bool { return len(s) > 3 }),
    func(s string) int { return len(s) },
)
// ["Carlos"=6, "Dani"=4]

Ponteiro opcional type-safe

go 
// Ptr retorna um ponteiro para v — elimina o boilerplate de variável temporária
// Ex: quero *int com valor 42 → antes: n := 42; return &n
func Ptr[T any](v T) *T { return &v }

// Uso em structs com campos opcionais
config := &Config{
    Timeout: Ptr(30),          // *int sem variável intermediária
    Debug:   Ptr(true),        // *bool
    Prefixo: Ptr("api/v1"),    // *string
}

// ValueOr: desreferencia com fallback para nil
func ValueOr[T any](p *T, def T) T {
    if p == nil { return def }
    return *p
}

timeout := ValueOr(config.Timeout, 10)  // 30 se não for nil, 10 se nil

Result type (sem panics)

go 
type Result[T any] struct {
    val T
    err error
}

func Ok[T any](v T) Result[T]       { return Result[T]{val: v} }
func Err[T any](e error) Result[T]  { return Result[T]{err: e} }

func (r Result[T]) Unwrap() (T, error) { return r.val, r.err }

func (r Result[T]) MustUnwrap() T {
    if r.err != nil { panic(r.err) }
    return r.val
}

// Uso: encadear operações sem checar erro a cada passo
resultado := Ok(buscarUsuario(id)).MustUnwrap()  // panic se err != nil

Quando NÃO usar generics

Generics adicionam complexidade ao código — tipos parametrizados são mais difíceis de ler, as mensagens de erro de constraints podem ser crípticas, e nem todo problema se beneficia da abstração. A equipe do Go publicou um guia explícito sobre quando generics são a ferramenta errada:

Situação Prefira
Comportamento que varia por tipo (serialização, validação) Interface com método — cada tipo implementa do seu jeito
Código usado em apenas um tipo hoje Código concreto — genericize quando a segunda necessidade aparecer
Estruturas de dados onde o tipo interno não importa para a lógica any + type assertion no ponto de uso (ex: sync.Map)
Funções simples chamadas poucas vezes Código duplicado — duplicar 3 linhas é mais claro que uma abstração genérica
go genérico desnecessário vs interface correta 
// ✗ Genérico forçado: a constraint any não restringe nada útil
// O comportamento é idêntico para todos os tipos — interface seria igual
func Imprimir[T any](v T) {
    fmt.Println(v)
}

// ✓ Simplesmente use any — sem overhead de type parameter
func Imprimir(v any) {
    fmt.Println(v)
}

// ✗ Genérico onde interface seria mais extensível
// Obriga o chamador a ter um tipo concreto — não aceita implementações externas
func Serializar[T int | string | bool](v T) []byte { ... }

// ✓ Interface: qualquer tipo que saiba se serializar
type Serializavel interface {
    Bytes() []byte
}
func Serializar(v Serializavel) []byte { return v.Bytes() }

// REGRA PRÁTICA:
// Use generics quando a ESTRUTURA do algoritmo é a mesma para múltiplos tipos
// Use interfaces quando o COMPORTAMENTO varia por tipo
Generics aumentam o tempo de compilação
O compilador instancia versões concretas para cada combinação de tipos usada. Em projetos grandes com muitos type parameters, isso pode aumentar significativamente o tempo de compilação e o tamanho do binário. Go usa GC shapes para agrupar instâncias com o mesmo layout de memória, mitigando o problema — mas é um fator a considerar em projetos críticos de build time.
Quiz · Questão 1 de 3 Verificação de entendimento

Qual das chamadas abaixo causa erro de compilação?

go 
type Caixa[T any] struct{ val T }

func Dobrar[T constraints.Integer](v T) T { return v * 2 }

// Qual linha causa erro de compilação?
A: resultado := Dobrar(5)
B: resultado := Dobrar[int](5)
C: c := Caixa{val: 42}
D: c := Caixa[int]{val: 42}
✓ Correto! Em funções genéricas, o compilador infere o type parameter a partir dos argumentos — Dobrar(5) infere T=int corretamente (linha A é válida). Especificação explícita também funciona (linha B é válida). Em tipos genéricos (structs), a inferência não existe — Caixa{val: 42} (linha C) é erro de compilação com "missing type argument for Caixa". A linha D, com tipo explícito, é a forma correta.
Quiz · Questão 2 de 3 Verificação de entendimento

Dado o código abaixo, qual chamada compila corretamente?

go 
type Metros int
type Litros float64

type SemTil interface{ int | float64 }
type ComTil interface{ ~int | ~float64 }

func FuncSemTil[T SemTil](v T) T { return v }
func FuncComTil[T ComTil](v T) T { return v }
✓ Correto! int na constraint significa exatamente o tipo int — type Metros int é um tipo diferente de int, não satisfaz a constraint sem til. ~int significa "qualquer tipo cujo tipo subjacente seja int" — isso inclui Metros, type ID int, type Contador int etc. O til é o que torna constraints úteis para tipos de domínio.
Quiz · Questão 3 de 3 Verificação de entendimento

Você precisa de uma função Validar que aplica regras de validação diferentes para Usuario, Produto e Pedido. Qual abordagem é mais idiomática em Go?

✓ Correto! O comportamento de validação é completamente diferente para cada tipo — não há estrutura de algoritmo compartilhada. Interface é a ferramenta certa: define o contrato (Validar() error) e deixa cada tipo implementar do seu jeito. Generics com switch interno (opção A) é o pior dos dois mundos: você teria que atualizar a constraint e o switch a cada novo tipo. Reflection (opção C) perde type safety e é mais lento. Três funções separadas (opção D) funciona mas impede polimorfismo — você não poderia ter uma lista de Validavel para validar em loop.
Exercício 1 — Método genérico inválido Aplicação prática

O código abaixo não compila. Qual é o problema e como corrigir mantendo type safety?

go 
type Cache[K comparable, V any] struct {
    dados map[K]V
}

// Transforma os valores do cache em outro tipo
func (c *Cache[K, V]) MapValues[U any](f func(V) U) map[K]U {
    res := make(map[K]U)
    for k, v := range c.dados {
        res[k] = f(v)
    }
    return res
}
✓ Correto! Em Go, métodos de tipos genéricos usam os type parameters do tipo receptor (K e V de Cache[K, V]) mas não podem declarar seus próprios type parameters adicionais. MapValues[U any] é inválido — o compilador emite "methods cannot have type parameters". A solução padrão é uma função livre que recebe o Cache como argumento: func MapCacheValues[K comparable, V, U any](c *Cache[K, V], f func(V) U) map[K]U. Essa limitação existe por simplicidade do sistema de tipos e pode ser removida em versões futuras do Go.
Exercício 2 — Constraint ou interface? Aplicação prática

Você está construindo um pipeline de processamento de eventos. Cada evento tem um método Tipo() string e um método Processar() error — mas a implementação de cada um varia completamente por tipo de evento. Você precisa de uma função ProcessarLote que recebe uma lista de eventos e processa todos, coletando erros. Como declarar corretamente?

✓ Correto! Interface é a ferramenta certa aqui. O comportamento de Processar() é diferente para cada tipo de evento — é polimorfismo de comportamento, não reutilização de estrutura de algoritmo. Uma interface nomeada Evento é mais clara, mais extensível (novos tipos de evento não requerem alterar ProcessarLote) e mais idiomática. A opção D com constraint inline também compilaria e funcionaria, mas cria um anti-padrão: constraints inline com métodos são essencialmente interfaces não nomeadas — é quase sempre melhor declarar a interface explicitamente. A diferença real entre []T genérico e []Evento aqui é zero — ambos aceitam qualquer implementação de Evento.
