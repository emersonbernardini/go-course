Anatomia de um teste em Go

Go tem suporte a testes embutido no toolchain — sem dependências externas, sem configuração, sem framework. Um arquivo de teste é um arquivo .go comum com o sufixo _test.go; o compilador o ignora nos builds normais mas o inclui ao rodar go test.

go math/soma.go 
package math

func Soma(a, b int) int {
    return a + b
}
go math/soma_test.go 
package math  // mesmo package — acessa símbolos não exportados também

import "testing"

// Assinatura obrigatória: Test + nome descritivo, recebe *testing.T
func TestSoma(t *testing.T) {
    resultado := Soma(2, 3)
    esperado  := 5

    if resultado != esperado {
        // t.Errorf: marca falha e continua o teste
        t.Errorf("Soma(2,3) = %d; esperado %d", resultado, esperado)
    }
}
bash rodando testes 
go test ./...             # todos os pacotes do módulo
go test ./math/...        # pacote específico
go test -v ./math/        # verbose: mostra cada Test* executado
go test -run TestSoma     # filtra por nome (regex)
go test -count=1 ./...    # desabilita cache — sempre reexecuta

t.Error vs t.Fatal vs t.Log

Método Comportamento Use quando
t.Error / t.Errorf Marca falha, continua executando Checar múltiplas condições independentes
t.Fatal / t.Fatalf Marca falha, interrompe o teste imediatamente Pré-condição falhou — próximos asserts não fazem sentido
t.Skip / t.Skipf Pula o teste, marca como SKIP Dependência externa ausente, feature flag desligada
t.Log / t.Logf Só aparece com -v ou em testes que falharam Contexto de debug sem poluir saída normal
Pacote _test: teste de caixa preta
Arquivos _test.go podem declarar package math_test (com sufixo _test) em vez de package math. Isso força o teste a usar apenas a API pública do pacote — como um consumidor externo faria. É a forma idiomática de testar a interface pública e garantir que ela é suficiente sem expor internos.

Table-driven tests e subtests

Escrever um TestFunc por caso de entrada leva a código repetitivo e difícil de expandir. O padrão idiomático em Go é o table-driven test: uma slice de structs onde cada entrada define um cenário, e um único loop executa todos. Combinado com t.Run, cada caso vira um subtest — isolado, nomeado e executável individualmente.

go table-driven test completo 
func TestDividir(t *testing.T) {
    casos := []struct {
        nome     string
        a, b     float64
        esperado float64
        erro     bool
    }{
        {"positivos", 10, 2, 5, false},
        {"negativo dividendo", -10, 2, -5, false},
        {"divisão por zero", 10, 0, 0, true},
        {"resultado fracionário", 7, 2, 3.5, false},
    }

    for _, tc := range casos {
        tc := tc  // captura a variável — necessário antes de Go 1.22
        t.Run(tc.nome, func(t *testing.T) {
            t.Parallel()  // subtests podem rodar em paralelo entre si

            resultado, err := Dividir(tc.a, tc.b)

            if tc.erro {
                if err == nil {
                    t.Fatal("esperava erro, mas não houve nenhum")
                }
                return
            }
            if err != nil {
                t.Fatalf("erro inesperado: %v", err)
            }
            if resultado != tc.esperado {
                t.Errorf("Dividir(%g, %g) = %g; esperado %g",
                    tc.a, tc.b, resultado, tc.esperado)
            }
        })
    }
}
bash executar subtest específico 
# -run aceita /subtest para filtrar dentro de um test
go test -run TestDividir/divisão_por_zero -v

# Espaços no nome viram underscores no filtro
go test -run TestDividir/resultado_fracionário -v
tc := tc antes de Go 1.22 — captura de loop
Em Go anterior a 1.22, variáveis de loop são compartilhadas entre iterações. Sem tc := tc dentro do loop, todos os subtests paralelos capturariam a mesma variável e veriam o último valor da slice ao executar. Go 1.22 mudou a semântica de loop para criar uma nova variável por iteração — mas em código que precisa ser compatível com versões anteriores, o tc := tc ainda é necessário.

Benchmarks

O pacote testing inclui suporte nativo a benchmarks: funções prefixadas com Benchmark que o runtime executa repetidamente, calibrando o número de iterações até obter uma medição estável. Sem biblioteca externa, sem setup manual.

go benchmark de duas implementações 
// Assinatura: Benchmark + nome, recebe *testing.B
func BenchmarkConcatPlus(b *testing.B) {
    lista := gerarLista(1000)

    b.ResetTimer()  // descarta o tempo de setup (gerarLista)

    for i := 0; i < b.N; i++ {  // b.N é calibrado pelo runtime
        resultado := ""
        for _, s := range lista {
            resultado += s
        }
        _ = resultado  // evita que o compilador elimine o código (dead code)
    }
}

func BenchmarkConcatBuilder(b *testing.B) {
    lista := gerarLista(1000)
    b.ResetTimer()

    for i := 0; i < b.N; i++ {
        var sb strings.Builder
        for _, s := range lista {
            sb.WriteString(s)
        }
        _ = sb.String()
    }
}
bash rodando e comparando benchmarks 
# -bench=. executa todos os Benchmark*, -benchmem inclui alocações
go test -bench=. -benchmem ./...

# Output típico:
# BenchmarkConcatPlus-8     3000    412330 ns/op    523456 B/op    999 allocs/op
# BenchmarkConcatBuilder-8  50000    28541 ns/op      4096 B/op      1 allocs/op

# Comparar antes/depois de uma otimização com benchstat
go test -bench=. -count=10 > antes.txt
# (faz a mudança)
go test -bench=. -count=10 > depois.txt
benchstat antes.txt depois.txt

b.ReportAllocs e b.SetBytes

go 
func BenchmarkProcessar(b *testing.B) {
    dados := make([]byte, 1024*1024)  // 1MB
    b.SetBytes(int64(len(dados)))     // informa o tamanho processado por iteração
    b.ReportAllocs()                  // equivalente a -benchmem só para este bench
    b.ResetTimer()

    for i := 0; i < b.N; i++ {
        _ = processar(dados)
    }
    // Output inclui: MB/s — útil para benchmarks de I/O e serialização
}
Benchmarks não rodam com go test ./... por padrão
go test ./... executa apenas funções Test*. Para rodar benchmarks, você precisa de -bench=. (ou um regex específico). Isso evita que benchmarks lentos atrasem o CI toda vez. O sufixo -8 no output indica que o runtime usou GOMAXPROCS=8 (número de CPUs).

TestMain, helpers e fixtures

Quando um pacote de testes precisa de setup e teardown globais — subir um banco de dados de testes, criar um diretório temporário, iniciar um servidor mock — o ponto de entrada é TestMain. Ele substitui o main padrão dos testes e dá controle total sobre o ciclo de vida.

go TestMain com setup e teardown 
var testDB *sql.DB

func TestMain(m *testing.M) {
    // Setup: executado uma vez antes de todos os testes do pacote
    var err error
    testDB, err = sql.Open("postgres", os.Getenv("TEST_DSN"))
    if err != nil {
        log.Fatalf("setup: abrir banco: %v", err)
    }
    if err = migrar(testDB); err != nil {
        log.Fatalf("setup: migrar: %v", err)
    }

    // m.Run() executa todos os Test*, Benchmark* e Example* do pacote
    codigo := m.Run()

    // Teardown: executado depois de todos os testes
    testDB.Close()
    limparBanco()

    os.Exit(codigo)  // propaga o exit code — 0=passou, 1=falhou
}

Funções helper com t.Helper()

Ao extrair lógica de assert para uma função auxiliar, as mensagens de falha apontam para a linha da função helper — não para onde ela foi chamada. t.Helper() resolve isso: marca a função como auxiliar e faz o stack trace apontar para o chamador.

go helper com t.Helper() 
// ✓ t.Helper() faz a falha apontar para quem chamou assertEqual
func assertEqual(t *testing.T, got, want any) {
    t.Helper()
    if got != want {
        t.Errorf("got %v; want %v", got, want)
    }
}

// t.TempDir() cria um diretório temporário limpo automaticamente após o teste
func TestProcessarArquivo(t *testing.T) {
    dir := t.TempDir()  // removido pelo cleanup automático — sem os.RemoveAll manual

    caminho := filepath.Join(dir, "entrada.csv")
    os.WriteFile(caminho, []byte("a,b\n1,2\n"), 0644)

    resultado, err := ProcessarArquivo(caminho)
    if err != nil {
        t.Fatalf("erro inesperado: %v", err)
    }
    assertEqual(t, len(resultado), 1)
}
t.Cleanup: teardown por teste, não global
t.Cleanup(func()) registra uma função que roda quando o teste (ou subtest) termina — seja passando ou falhando. É o equivalente do defer para testes, com a vantagem de poder ser chamado de dentro de helpers sem que o helper precise saber sobre o ciclo de vida do teste. Substituiu o padrão defer teardown() manual em código moderno.

testify e mocks

A stdlib de testing é deliberadamente minimalista — sem assert.Equal, sem mocks embutidos. Para a maioria dos projetos em produção, a biblioteca testify (github.com/stretchr/testify) é o complemento padrão de facto: assertions legíveis, suites de testes e mocks.

testify/assert e testify/require

go assert vs require 
import (
    "testing"
    "github.com/stretchr/testify/assert"
    "github.com/stretchr/testify/require"
)

func TestCriarUsuario(t *testing.T) {
    u, err := CriarUsuario("ana@email.com", "senha123")

    // require: equivale a t.Fatal — interrompe se falhar
    // Use para pré-condições: se err != nil, os asserts abaixo não fazem sentido
    require.NoError(t, err)
    require.NotNil(t, u)

    // assert: equivale a t.Error — continua mesmo se falhar
    // Use para checar múltiplos campos independentes
    assert.Equal(t, "ana@email.com", u.Email)
    assert.NotEmpty(t, u.ID)
    assert.True(t, u.CriadoEm.Before(time.Now()))

    // Comparação de structs com diff legível no output de falha
    esperado := &Usuario{Email: "ana@email.com", Ativo: true}
    assert.Equal(t, esperado, u, "usuário criado difere do esperado")
}

Mocks com testify/mock

Mocks permitem testar uma unidade isolada substituindo suas dependências por implementações controladas. Em Go, isso é feito via interfaces: a dependência real implementa uma interface, e no teste você passa um mock que implementa a mesma interface.

go mock de repositório 
// Interface que o serviço depende
type UsuarioRepo interface {
    BuscarPorEmail(email string) (*Usuario, error)
}

// Mock gerado manualmente (ou via mockery/moq)
type MockUsuarioRepo struct {
    mock.Mock  // embutido de testify/mock
}

func (m *MockUsuarioRepo) BuscarPorEmail(email string) (*Usuario, error) {
    args := m.Called(email)
    // args.Get(0) retorna any — type assertion necessária
    if u, ok := args.Get(0).(*Usuario); ok {
        return u, args.Error(1)
    }
    return nil, args.Error(1)
}

// Uso no teste
func TestLogin(t *testing.T) {
    repo := new(MockUsuarioRepo)

    // Configura o mock: quando BuscarPorEmail("ana") for chamado,
    // retorna este usuário e nil como erro
    usuario := &Usuario{Email: "ana@email.com", SenhaHash: hashSenha("abc123")}
    repo.On("BuscarPorEmail", "ana@email.com").Return(usuario, nil)

    svc := NovoAuthService(repo)
    ok, err := svc.Login("ana@email.com", "abc123")

    require.NoError(t, err)
    assert.True(t, ok)
    repo.AssertExpectations(t)  // falha se alguma chamada esperada não ocorreu
}
Mocks testam o contrato, não a implementação
Mocks são poderosos mas têm um custo: eles acoplam o teste aos detalhes de chamada da dependência. Se a implementação mudar internamente sem mudar o comportamento observável, os mocks quebram. Prefira fakes (implementações em memória da interface) quando possível — são mais robustos e mais próximos do comportamento real. Use mocks para dependências com efeitos colaterais difíceis de replicar (envio de email, chamadas externas).
Quiz · Questão 1 de 3 Verificação de entendimento

Um teste chama t.Errorf("valor incorreto") e depois continua executando mais verificações. O teste aparece como FAIL no output. Qual afirmação descreve corretamente esse comportamento?

✓ Correto! t.Errorf marca o teste como falho internamente mas não interrompe a execução — é equivalente a setar uma flag de falha e continuar. Isso é intencional: você pode verificar 10 campos de uma struct e ver todos os que falharam de uma vez, em vez de consertar um por vez. Use t.Fatalf quando uma falha torna os próximos asserts sem sentido (ex: o objeto retornado é nil).
Quiz · Questão 2 de 3 Verificação de entendimento

O que está errado no benchmark abaixo?

go 
func BenchmarkParseJSON(b *testing.B) {
    dados, _ := os.ReadFile("testdata/grande.json")  // 50MB

    for i := 0; i < b.N; i++ {
        var resultado map[string]any
        json.Unmarshal(dados, &resultado)
    }
}
✓ Correto! O timer começa quando a função Benchmark* é chamada. O os.ReadFile ocorre uma única vez, mas acontece enquanto o timer está rodando — nas primeiras iterações de calibração, o custo de I/O é incluído na média. Com um arquivo de 50MB, isso pode distorcer significativamente a medição do json.Unmarshal. A correção é adicionar b.ResetTimer() após o os.ReadFile. O erro ignorado é um problema secundário real, mas não é o bug de medição da questão.
Quiz · Questão 3 de 3 Verificação de entendimento

Em Go anterior a 1.22, o que acontece se t.Parallel() for chamado dentro de t.Run sem tc := tc?

go 
for _, tc := range casos {
    t.Run(tc.nome, func(t *testing.T) {
        t.Parallel()
        // usa tc.entrada e tc.esperado
    })
}
✓ Correto! t.Parallel() suspende o subtest até que o test pai termine de chamar todos os t.Run. Nesse ponto, o loop já terminou e tc aponta para o último elemento. Todos os subtests leem o mesmo tc — o último da slice — produzindo resultados incorretos sem nenhum erro de compilação ou runtime óbvio. O fix é tc := tc dentro do loop para criar uma cópia local por iteração. Em Go 1.22+, cada iteração do loop já tem sua própria variável.
Exercício 1 — Falha silenciosa no TestMain Aplicação prática

O TestMain abaixo tem um bug sutil que faz os testes sempre reportarem sucesso, mesmo quando falham. Qual é o problema?

go 
func TestMain(m *testing.M) {
    setup()
    m.Run()  // retorno ignorado
    teardown()
    os.Exit(0)  // sempre sai com sucesso
}
✓ Correto! m.Run() executa todos os testes e retorna 0 se todos passaram, 1 se algum falhou. Ao ignorar esse retorno e usar os.Exit(0) fixo, o processo sempre reporta sucesso — o CI verde mesmo com 50 testes falhando. Esse é um dos bugs mais perigosos em suites de teste: silencioso, não detectável pelo próprio Go, e destrói a confiança no pipeline. O padrão correto é sempre os.Exit(m.Run()), que propaga o código de saída real.
Exercício 2 — Mock vs Fake Aplicação prática

Um serviço de pedidos depende de uma interface EstoqueRepo com os métodos Reservar(id, qty) e Liberar(id, qty). Você precisa testar a lógica de rollback: se Reservar falhar, o serviço deve chamar Liberar. Qual abordagem é mais adequada?

✓ Correto! Este é um caso onde mock é a ferramenta certa. O que você quer verificar não é o estado do estoque, mas o comportamento do serviço: ele chamou Liberar após a falha? Com um fake em memória, você precisaria inspecionar estado interno ou adicionar contadores — essencialmente reimplementando um mock manualmente. Com testify/mock, você configura repo.On("Reservar", ...).Return(ErrEstoqueInsuficiente) e depois repo.AssertCalled(t, "Liberar", id, qty) — testando exatamente o contrato comportamental do serviço.
