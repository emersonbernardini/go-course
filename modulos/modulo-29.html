Marshal e Unmarshal

encoding/json converte valores Go para JSON (marshaling) e JSON para valores Go (unmarshaling). É a ponte entre o sistema de tipos estático de Go e o formato de dados dinâmico do JSON — a maioria das APIs REST e sistemas de configuração modernos depende dela.

json.Marshal — Go → JSON

go serialização básica 
type Produto struct {
    ID    int     `json:"id"`
    Nome  string  `json:"nome"`
    Preco float64 `json:"preco"`
    Ativo bool    `json:"ativo"`
}

p := Produto{ID: 1, Nome: "Teclado", Preco: 299.90, Ativo: true}

data, err := json.Marshal(p)
if err != nil {
    return fmt.Errorf("marshal: %w", err)
}

fmt.Println(string(data))
// {"id":1,"nome":"Teclado","preco":299.9,"ativo":true}

// Versão indentada para debug ou arquivos de configuração:
data, _ = json.MarshalIndent(p, "", "  ")
fmt.Println(string(data))
// {
//   "id": 1,
//   "nome": "Teclado",
//   "preco": 299.9,
//   "ativo": true
// }

json.Unmarshal — JSON → Go

go desserialização básica 
dados := []byte(`{"id":42,"nome":"Mouse","preco":89.90,"ativo":false}`)

var p Produto
if err := json.Unmarshal(dados, &p); err != nil {
    return fmt.Errorf("unmarshal: %w", err)
}

fmt.Println(p.Nome)  // Mouse
fmt.Println(p.Preco) // 89.9

// Unmarshal em slice:
dadosLista := []byte(`[{"id":1,"nome":"A"},{"id":2,"nome":"B"}]`)
var lista []Produto
json.Unmarshal(dadosLista, &lista)
fmt.Println(len(lista))  // 2

Mapeamento de tipos Go ↔ JSON

Tipo Go JSON Observação
bool true / false Direto
int, float64 number JSON não distingue inteiro de float
string string Escapes Unicode automáticos
[]byte string (base64) Codificado automaticamente em base64
struct object Apenas campos exportados
map[string]T object Chave deve ser string ou tipo com método String()
slice, array array nil slice → null; slice vazio → []
nil pointer null Ponteiro não-nil serializa o valor apontado
Apenas campos exportados são serializados
json.Marshal ignora silenciosamente campos com letra minúscula. Um campo nome string (minúsculo) nunca aparece no JSON — sem erro, sem aviso. Se um campo não aparece na saída JSON e você não sabe por quê, verifique se está exportado.

Struct tags

Struct tags são metadados em formato de string literal anexados a campos de struct. O pacote encoding/json as lê em tempo de execução via reflection para controlar como cada campo é serializado. São a principal ferramenta para mapear entre convenções de nomenclatura Go (CamelCase) e JSON (snake_case).

go anatomia de uma struct tag 
type Usuario struct {
    //         ┌── chave   ┌── nome no JSON
    ID          int    `json:"id"`
    NomeCompleto string `json:"nome_completo"`
    Email       string `json:"email"`
    SenhaHash   string `json:"-"`           // "-" → sempre omitir do JSON
    CreatedAt   time.Time `json:"created_at"`
}

Opções da tag json

go todas as opções 
type Pedido struct {
    ID        int     `json:"id"`

    // omitempty: omite o campo se for zero value (0, "", false, nil, slice/map vazio)
    Desconto  float64 `json:"desconto,omitempty"`

    // string: serializa número como string JSON (útil para IDs grandes em JS)
    IDExterno int64   `json:"id_externo,string"`

    // "-": campo nunca aparece no JSON (nem para leitura nem escrita)
    Token     string  `json:"-"`

    // "-,": nome do campo no JSON é literalmente "-" (raro mas válido)
    Marcador  string  `json:"-,"`

    // Sem tag: usa o nome do campo Go como está (PascalCase → "PascalCase")
    Metadata  map[string]string
}

Embedding e promoção de campos

Campos de structs embedded são promovidos para o nível superior do JSON — padrão útil para compor tipos sem aninhamento desnecessário:

go embedding e promoção 
type Auditoria struct {
    CriadoEm   time.Time `json:"criado_em"`
    AtualizadoEm time.Time `json:"atualizado_em"`
    CriadoPor  string    `json:"criado_por"`
}

type Produto struct {
    ID    int    `json:"id"`
    Nome  string `json:"nome"`
    Auditoria     // embedded sem tag — campos promovidos ao nível raiz
}

p := Produto{
    ID: 1, Nome: "Teclado",
    Auditoria: Auditoria{CriadoPor: "admin"},
}

data, _ := json.Marshal(p)
// {"id":1,"nome":"Teclado","criado_em":"0001-...","atualizado_em":"0001-...","criado_por":"admin"}
// — não {"id":1,"nome":"Teclado","Auditoria":{...}}
Tags mal formadas falham silenciosamente
`json: "id"` (espaço após o dois-pontos) e `json:"id" json:"outro"` (tag duplicada) são mal formadas — o pacote as ignora sem erro e usa o nome Go do campo. Use go vet para detectar tags inválidas antes de ir para produção.

json.Encoder e json.Decoder

json.Marshal e json.Unmarshal trabalham com []byte em memória — o JSON inteiro precisa estar alocado antes de processar. json.Encoder e json.Decoder operam sobre io.Writer e io.Reader, respectivamente: processam o JSON em fluxo, sem carregar tudo na memória.

json.Encoder — escrevendo JSON em um stream

go Encoder escrevendo direto no ResponseWriter 
func handleListarProdutos(w http.ResponseWriter, r *http.Request) {
    produtos, err := repo.Todos(r.Context())
    if err != nil {
        http.Error(w, "erro interno", http.StatusInternalServerError)
        return
    }

    w.Header().Set("Content-Type", "application/json")

    enc := json.NewEncoder(w)
    enc.SetIndent("", "  ")       // opcional: saída indentada
    enc.SetEscapeHTML(false)      // não escapa <, >, & em strings (útil para URLs)

    if err := enc.Encode(produtos); err != nil {
        // Header já enviado — só logar
        slog.Error("encode JSON", "erro", err)
    }
    // Encode já adiciona '\n' ao final — não precisa de w.Write([]byte("\n"))
}

json.Decoder — lendo JSON de um stream

go Decoder lendo body de requisição 
func handleCriarProduto(w http.ResponseWriter, r *http.Request) {
    r.Body = http.MaxBytesReader(w, r.Body, 1<<20) // 1 MB

    dec := json.NewDecoder(r.Body)
    dec.DisallowUnknownFields() // rejeita campos não mapeados na struct

    var p Produto
    if err := dec.Decode(&p); err != nil {
        http.Error(w, "JSON inválido: "+err.Error(), http.StatusBadRequest)
        return
    }

    // Garantia: apenas um objeto JSON no body
    if dec.More() {
        http.Error(w, "body deve conter exatamente um objeto JSON", http.StatusBadRequest)
        return
    }

    // ... salvar p
}

Decoder para streams de múltiplos objetos

Uma vantagem do Decoder que o Unmarshal não oferece: ler múltiplos valores JSON sequenciais do mesmo stream (NDJSON — Newline Delimited JSON, comum em logs e eventos):

go lendo NDJSON linha a linha 
// Arquivo com um JSON por linha:
// {"id":1,"evento":"login","usuario":"ana"}
// {"id":2,"evento":"compra","usuario":"bob"}
// {"id":3,"evento":"logout","usuario":"ana"}

func processarEventos(r io.Reader) error {
    dec := json.NewDecoder(r)
    for dec.More() {  // More() retorna false quando o stream acabou
        var evento Evento
        if err := dec.Decode(&evento); err != nil {
            return fmt.Errorf("decodificar evento: %w", err)
        }
        processar(evento)
    }
    return nil
}
Função Entrada/Saída Quando usar
json.Marshal Go → []byte Precisa do []byte para processar depois (ex: cache, hash)
json.Unmarshal []byte → Go Já tem os bytes em memória (ex: leu arquivo inteiro)
json.NewEncoder Go → io.Writer Escrevendo em HTTP, arquivo ou conexão de rede
json.NewDecoder io.Reader → Go Lendo de HTTP body, arquivo, múltiplos objetos sequenciais

Tipos customizados: MarshalJSON / UnmarshalJSON

O pacote encoding/json verifica se o tipo implementa as interfaces json.Marshaler ou json.Unmarshaler antes de usar a lógica padrão baseada em reflection. Isso permite controle total sobre a representação JSON de qualquer tipo — útil para datas em formatos específicos, enums como strings, IDs com prefixo, ou qualquer transformação que as tags sozinhas não conseguem expressar.

go definição das interfaces 
// Implementar qualquer uma (ou ambas) para controle customizado:
type Marshaler interface {
    MarshalJSON() ([]byte, error)
}

type Unmarshaler interface {
    UnmarshalJSON([]byte) error
}

Exemplo real: data em formato brasileiro

go time.Time com formato customizado 
// DataBR serializa como "DD/MM/AAAA" em vez do RFC3339 padrão
type DataBR struct {
    time.Time
}

const formatoBR = "02/01/2006"

func (d DataBR) MarshalJSON() ([]byte, error) {
    return []byte(`"` + d.Time.Format(formatoBR) + `"`), nil
}

func (d *DataBR) UnmarshalJSON(b []byte) error {
    s := strings.Trim(string(b), `"`)
    t, err := time.Parse(formatoBR, s)
    if err != nil {
        return fmt.Errorf("data inválida %q: esperado DD/MM/AAAA", s)
    }
    d.Time = t
    return nil
}

// Uso:
type Fatura struct {
    ID        int    `json:"id"`
    Emissao   DataBR `json:"emissao"`
    Vencimento DataBR `json:"vencimento"`
}

f := Fatura{ID: 1, Emissao: DataBR{time.Now()}}
data, _ := json.Marshal(f)
// {"id":1,"emissao":"14/06/2026","vencimento":"01/01/0001"}

Exemplo real: enum como string

go tipo enum serializado como string legível 
type StatusPedido int

const (
    StatusPendente   StatusPedido = iota
    StatusAprovado
    StatusEnviado
    StatusEntregue
    StatusCancelado
)

var statusNomes = map[StatusPedido]string{
    StatusPendente:  "pendente",
    StatusAprovado:  "aprovado",
    StatusEnviado:   "enviado",
    StatusEntregue:  "entregue",
    StatusCancelado: "cancelado",
}

var statusCodigos = func() map[string]StatusPedido {
    m := make(map[string]StatusPedido, len(statusNomes))
    for k, v := range statusNomes {
        m[v] = k
    }
    return m
}()

func (s StatusPedido) MarshalJSON() ([]byte, error) {
    nome, ok := statusNomes[s]
    if !ok {
        return nil, fmt.Errorf("status desconhecido: %d", s)
    }
    return json.Marshal(nome)  // delega para string → sem risco de escape errado
}

func (s *StatusPedido) UnmarshalJSON(b []byte) error {
    var nome string
    if err := json.Unmarshal(b, &nome); err != nil {
        return err
    }
    codigo, ok := statusCodigos[nome]
    if !ok {
        return fmt.Errorf("status inválido: %q", nome)
    }
    *s = codigo
    return nil
}

// Resultado:
// {"id":1,"status":"aprovado"}  → em vez de  {"id":1,"status":1}
Receiver por ponteiro em UnmarshalJSON
MarshalJSON pode usar receiver por valor ou ponteiro. UnmarshalJSON deve usar receiver por ponteiro — ele precisa modificar o valor no local apontado. Se usar receiver por valor, a modificação é descartada e o campo permanece com zero value silenciosamente.

Campos opcionais e omitempty

Representar campos opcionais em JSON é um dos problemas mais comuns e mais mal resolvidos em Go. A distinção entre "campo ausente no JSON", "campo com valor nulo" e "campo com zero value legítimo" exige atenção ao design dos tipos.

omitempty — quando e como funciona

A opção omitempty omite o campo do JSON se seu valor for o zero value do tipo: 0 para números, "" para strings, false para bool, nil para ponteiros, interfaces, maps e slices.

go comportamento de omitempty 
type Perfil struct {
    Nome     string  `json:"nome"`
    Bio      string  `json:"bio,omitempty"`       // omite se ""
    Seguidores int   `json:"seguidores,omitempty"` // omite se 0
    Verificado bool  `json:"verificado,omitempty"` // omite se false
}

p1 := Perfil{Nome: "Ana", Seguidores: 500, Verificado: true}
// {"nome":"Ana","seguidores":500,"verificado":true}

p2 := Perfil{Nome: "Bob"}
// {"nome":"Bob"}  — bio, seguidores e verificado omitidos

O problema do zero value legítimo

omitempty não distingue "zero porque não foi fornecido" de "zero como valor intencional". Para campos onde 0 ou false são valores válidos que devem aparecer no JSON, use ponteiros:

go ponteiros para distinguir ausente de zero 
type ConfiguracaoNotificacao struct {
    // Com omitempty em bool: false seria omitido — problema!
    // EmailAtivo bool `json:"email_ativo,omitempty"` // ERRADO para este caso

    // Ponteiro: nil → omitido; &false → aparece como false no JSON
    EmailAtivo  *bool `json:"email_ativo,omitempty"`
    PushAtivo   *bool `json:"push_ativo,omitempty"`
    LimiteItens *int  `json:"limite_itens,omitempty"`
}

// Helper para criar ponteiros de literais:
func ptr[T any](v T) *T { return &v }

cfg := ConfiguracaoNotificacao{
    EmailAtivo:  ptr(false),  // aparece no JSON como false
    PushAtivo:   ptr(true),   // aparece como true
    LimiteItens: nil,         // omitido (não configurado)
}

data, _ := json.Marshal(cfg)
// {"email_ativo":false,"push_ativo":true}

PATCH parcial — atualizando apenas campos fornecidos

Ponteiros são essenciais em endpoints PATCH, onde nil significa "não alterar" e um valor não-nil significa "atualizar para este valor":

go request de PATCH com campos opcionais 
type AtualizarUsuarioReq struct {
    Nome  *string `json:"nome,omitempty"`
    Email *string `json:"email,omitempty"`
    Bio   *string `json:"bio,omitempty"`
}

func handleAtualizarUsuario(w http.ResponseWriter, r *http.Request) {
    var req AtualizarUsuarioReq
    json.NewDecoder(r.Body).Decode(&req)

    // JSON: {"nome": "Novo Nome"}
    // req.Nome  → &"Novo Nome"   (atualizar)
    // req.Email → nil            (não alterar)
    // req.Bio   → nil            (não alterar)

    if req.Nome != nil {
        usuario.Nome = *req.Nome
    }
    if req.Email != nil {
        usuario.Email = *req.Email
    }
    // ...
}
omitempty não funciona com structs
omitempty em um campo do tipo struct nunca omite — uma struct não tem zero value vazio no sentido de encoding/json, mesmo que todos os campos sejam zero. Para omitir uma struct, use ponteiro para struct: *MinhaStruct `json:"campo,omitempty"` — nil é omitido; valor não-nil é serializado normalmente.

JSON dinâmico: json.RawMessage e map[string]any

Nem sempre a estrutura do JSON é conhecida em tempo de compilação. APIs externas retornam estruturas variáveis, campos polimórficos mudam de tipo conforme o contexto, ou você precisa repassar JSON sem interpretá-lo. Para esses casos, json.RawMessage e map[string]any são as ferramentas certas.

json.RawMessage — adiando a interpretação

json.RawMessage é simplesmente []byte com os métodos MarshalJSON e UnmarshalJSON implementados para preservar o JSON literal sem interpretar. Útil quando a estrutura de um campo depende de outro campo:

go campo polimórfico com RawMessage 
// Eventos com payload que varia conforme o tipo:
// {"tipo":"login",  "payload":{"usuario":"ana","ip":"1.2.3.4"}}
// {"tipo":"compra", "payload":{"produto_id":42,"valor":99.90}}
// {"tipo":"erro",   "payload":{"codigo":500,"msg":"timeout"}}

type Evento struct {
    Tipo    string          `json:"tipo"`
    Payload json.RawMessage `json:"payload"` // preserva o JSON bruto
}

type PayloadLogin struct {
    Usuario string `json:"usuario"`
    IP      string `json:"ip"`
}

type PayloadCompra struct {
    ProdutoID int     `json:"produto_id"`
    Valor     float64 `json:"valor"`
}

func processarEvento(data []byte) error {
    var ev Evento
    if err := json.Unmarshal(data, &ev); err != nil {
        return err
    }

    // Agora interpretamos o payload conforme o tipo:
    switch ev.Tipo {
    case "login":
        var p PayloadLogin
        if err := json.Unmarshal(ev.Payload, &p); err != nil {
            return fmt.Errorf("payload login: %w", err)
        }
        fmt.Printf("login de %s via %s\n", p.Usuario, p.IP)

    case "compra":
        var p PayloadCompra
        if err := json.Unmarshal(ev.Payload, &p); err != nil {
            return fmt.Errorf("payload compra: %w", err)
        }
        fmt.Printf("compra produto %d: R$%.2f\n", p.ProdutoID, p.Valor)
    }
    return nil
}

map[string]any — estrutura completamente desconhecida

Quando o schema é totalmente desconhecido ou varia arbitrariamente, faça o unmarshal em map[string]any. O encoding/json usa um mapeamento fixo para os tipos Go nesse modo:

go unmarshal em map[string]any 
dados := []byte(`{
    "nome": "Produto X",
    "preco": 29.90,
    "ativo": true,
    "tags": ["novo", "destaque"],
    "meta": {"cor": "azul", "peso": 1.2}
}`)

var m map[string]any
json.Unmarshal(dados, &m)

// Tipos resultantes (mapeamento fixo do encoding/json):
// string  → string
// number  → float64  (sempre float64, mesmo inteiros!)
// boolean → bool
// array   → []any
// object  → map[string]any
// null    → nil

nome := m["nome"].(string)       // "Produto X"
preco := m["preco"].(float64)    // 29.9
tags := m["tags"].([]any)        // ["novo", "destaque"]
meta := m["meta"].(map[string]any)
cor := meta["cor"].(string)      // "azul"

// IDs numéricos ficam como float64 — problema clássico:
// {"id": 9007199254740993}  → float64 perde precisão além de 2^53
// Solução: usar json.Decoder com UseNumber()
dec := json.NewDecoder(bytes.NewReader(dados))
dec.UseNumber()  // numbers → json.Number (string) em vez de float64
var m2 map[string]any
dec.Decode(&m2)
// m2["preco"].(json.Number).Float64()  → (29.9, nil)
Números JSON sempre viram float64 em map[string]any
Ao fazer unmarshal em map[string]any, todos os números JSON — incluindo inteiros — são representados como float64. Isso causa perda de precisão para inteiros acima de 2⁵³ (comum com IDs de 64 bits de sistemas externos). Use dec.UseNumber() e converta com json.Number.Int64() quando precisão importa.

✓ Correto! encoding/json distingue nil slice de slice vazio: nil → null, vazio → []. Isso importa em APIs REST: clientes que recebem null podem tratar diferente de []. Se sempre quiser [] em vez de null, inicialize o slice com make([]string, 0) ou use Tags: []string{} como zero value no retorno.

O código abaixo tem um comportamento inesperado. O que ele imprime?

go 
type Endereco struct {
    Rua    string `json:"rua"`
    Cidade string `json:"cidade"`
}

type Cliente struct {
    Nome     string   `json:"nome"`
    Endereco Endereco `json:"endereco,omitempty"`

c := Cliente{Nome: "Ana"}
data, _ := json.Marshal(c)
fmt.Println(string(data))
✓ Correto! omitempty não omite structs mesmo que todos os campos sejam zero — structs não têm um conceito de "vazio" em encoding/json. O resultado inclui o objeto com rua e cidade como strings vazias. Quiz · Questão 3 de 3 Verificação de entendimento

O código abaixo causa um panic em runtime. Por quê?

go 
dados := []byte(`{"id": 123, "nome": "produto"}`)

var m map[string]any
json.Unmarshal(dados, &m)

id := m["id"].(int)  // type assertion para int
fmt.Println(id)
✓ Correto! Ao desserializar em map[string]any, encoding/json representa todos os números JSON como float64 — sem exceção. A type assertion .(int) falha com panic porque o valor real é float64(123). A correção é m["id"].(float64) e converter se necessário, ou usar dec.UseNumber() e então m["id"].(json.Number).Int64() para preservar precisão em IDs grandes.
Exercício 1 — Bug em produção Aplicação prática

Uma API de pagamentos retorna o seguinte JSON e o serviço Go consome e exibe os valores. Em produção, IDs grandes estão sendo corrompidos silenciosamente. Identifique o problema e a correção adequada.

go 
// JSON recebido:
// {"transaction_id": 9007199254740993, "valor": 150.00, "status": "aprovado"}

type Transacao struct {
    ID     float64 `json:"transaction_id"`  // ← problema aqui
    Valor  float64 `json:"valor"`
    Status string  `json:"status"`
}

var t Transacao
json.Unmarshal(resposta, &t)
fmt.Println(t.ID)  // imprime 9007199254740992 — errado!
✓ Correto! float64 tem 53 bits de mantissa — inteiros acima de 2⁵³ (9.007 trilhões) não podem ser representados exatamente. O ID 9007199254740993 vira 9007199254740992 após a conversão para float64. A solução é usar int64 como tipo de destino: o encoding/json faz a conversão exata do número JSON para inteiro de 64 bits. A opção A funciona mas é desnecessariamente verbosa. A opção C (json.Number) resolve mas requer conversão manual e polui a struct com tipos de infraestrutura. A opção D é errada: UseNumber() afeta apenas unmarshal em interface{} / any, não em campos tipados.
Exercício 2 — Decisão de design Aplicação prática

Você está integrando com um webhook externo que envia eventos com o seguinte formato: o campo dados é um objeto JSON cujo schema varia completamente conforme o campo tipo. Qual abordagem é mais idiomática e segura em Go para desserializar esses eventos?

go 
// Exemplos de payload:
// {"tipo":"pagamento", "dados":{"valor":99.90,"metodo":"pix"}}
// {"tipo":"cancelamento", "dados":{"motivo":"fraude","reembolso":true}}
// {"tipo":"envio", "dados":{"transportadora":"Correios","rastreio":"BR123"}}
✓ Correto! json.RawMessage é exatamente o padrão para campos polimórficos: preserva o JSON bruto do campo dados sem interpretá-lo, permite determinar o tipo do evento, e então desserializa o RawMessage na struct correta — com type safety completo e validação de campos. A opção A (map[string]any) perde type safety e exige type assertions em todo lugar — frágil e propenso a panic. A opção B (struct unificada) cria acoplamento entre todos os tipos de evento e dificulta adicionar novos. A opção D introduz uma dependência externa desnecessária quando a stdlib resolve o problema com elegância.
