Closures

Uma closure é uma função que captura variáveis do escopo em que foi definida — mesmo após esse escopo ter encerrado. A função "fecha sobre" as variáveis externas, mantendo uma referência viva a elas.

go closure básica 
func contador() func() int {
    n := 0  // variável capturada pela closure
    return func() int {
        n++
        return n
    }
}

c := contador()
fmt.Println(c())  // 1
fmt.Println(c())  // 2
fmt.Println(c())  // 3

// Cada chamada a contador() cria uma closure independente
c2 := contador()
fmt.Println(c2()) // 1 — estado próprio, independente de c

n é uma variável local de contador(). Normalmente seria descartada quando contador() retorna. Mas como a função retornada a referencia, Go move n para o heap — ela sobrevive enquanto a closure existir.

Closures compartilham a mesma variável

Múltiplas closures criadas no mesmo escopo compartilham a mesma variável — não cópias dela:

go 
func criarPar() (func(), func() int) {
    n := 0
    incrementar := func() { n++ }
    ler := func() int { return n }
    return incrementar, ler  // ambas capturam o mesmo n
}

inc, ler := criarPar()
inc()
inc()
fmt.Println(ler())  // 2 — ambas operam sobre o mesmo n

Gotcha clássico: closure em loop

Em Go antes de 1.22, todas as closures criadas em um loop capturavam a mesma variável de iteração — não uma cópia por iteração. O resultado clássico:

go 
// Go < 1.22: bug clássico
funcs := make([]func(), 3)
for i := 0; i < 3; i++ {
    funcs[i] = func() { fmt.Println(i) }
}
funcs[0]()  // 3 — não 0!
funcs[1]()  // 3
funcs[2]()  // 3  — todas capturam o i final do loop

// Correção (necessária em Go < 1.22): captura explícita
for i := 0; i < 3; i++ {
    i := i  // nova variável i local a esta iteração
    funcs[i] = func() { fmt.Println(i) }
}

// Go >= 1.22: cada iteração tem sua própria variável — bug resolvido por padrão

Casos de uso reais

go 
// Middleware HTTP — injeta dependência via closure
func comAutenticacao(db *DB, handler http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        if !db.ValidarToken(r.Header.Get("Authorization")) {
            http.Error(w, "não autorizado", 401)
            return
        }
        handler(w, r)
    }
}

// Memoização — cache de resultados via closure
func memoizar(f func(int) int) func(int) int {
    cache := make(map[int]int)
    return func(n int) int {
        if v, ok := cache[n]; ok {
            return v
        }
        v := f(n)
        cache[n] = v
        return v
    }
}

Funções variádicas

Uma função variádica aceita um número variável de argumentos do mesmo tipo. O último parâmetro recebe ... antes do tipo — dentro da função ele é tratado como um slice:

go 
func somar(nums ...int) int {
    total := 0
    for _, n := range nums {  // nums é []int dentro da função
        total += n
    }
    return total
}

fmt.Println(somar())           // 0   — zero argumentos é válido
fmt.Println(somar(1, 2, 3))    // 6
fmt.Println(somar(1, 2, 3, 4, 5)) // 15

Expandindo um slice com ...

Para passar um slice existente a uma função variádica, use ... ao passar o argumento:

go 
nums := []int{1, 2, 3, 4, 5}

somar(nums...)      // ✓ expande o slice como argumentos individuais
// somar(nums)      // ✗ ERRO: []int não é int

Parâmetros fixos e variádicos

O parâmetro variádico deve ser o último. Os demais são fixos e normais:

go 
func logar(nivel string, msgs ...string) {
    for _, msg := range msgs {
        fmt.Printf("[%s] %s\n", nivel, msg)
    }
}

logar("INFO", "servidor iniciado", "porta 8080")
logar("ERRO", "conexão recusada")
fmt.Println é variádica
fmt.Println(a, b, c) funciona porque Println é declarada como func Println(a ...any) (n int, err error). O any (alias de interface{}) aceita qualquer tipo.

defer

defer adia a execução de uma instrução para o momento em que a função que a contém retorna — seja por return normal, panic ou qualquer outro caminho de saída. Os argumentos são avaliados imediatamente, mas a execução é adiada.

go uso básico 
func lerArquivo(nome string) error {
    f, err := os.Open(nome)
    if err != nil {
        return err
    }
    defer f.Close()  // garante fechamento independente do caminho de retorno

    // ... lê o arquivo
    return nil
}
// f.Close() é chamado aqui — após o return

Múltiplos defers: ordem LIFO

Quando há múltiplos defers na mesma função, eles executam em ordem LIFO (last in, first out) — o último defer registrado executa primeiro:

go 
func exemplo() {
    defer fmt.Println("terceiro")  // registrado primeiro, executa por último
    defer fmt.Println("segundo")
    defer fmt.Println("primeiro")  // registrado por último, executa primeiro
    fmt.Println("corpo da função")
}

// Saída:
// corpo da função
// primeiro
// segundo
// terceiro

Argumentos avaliados imediatamente

go 
x := 10
defer fmt.Println("valor de x:", x)  // x=10 capturado agora
x = 20
// Saída: "valor de x: 10" — não 20

// Para capturar o valor final, use uma closure
defer func() { fmt.Println("valor de x:", x) }()
x = 20
// Saída: "valor de x: 20" — closure lê x no momento da execução

defer com retornos nomeados

defer com uma closure pode modificar retornos nomeados após o return — útil para wrapping de erros:

go 
func consultar(id int) (resultado string, err error) {
    defer func() {
        if err != nil {
            // envolve o erro com contexto após o return
            err = fmt.Errorf("consultar(%d): %w", id, err)
        }
    }()

    resultado, err = db.Buscar(id)
    return  // defer executa aqui, modificando err se necessário
}
defer em loop tem custo
Cada defer tem um custo de alocação pequeno. Em loops com milhões de iterações, registrar um defer por iteração pode ser significativo. Se precisar de cleanup dentro de um loop, extraia o corpo para uma função separada com o defer, ou gerencie o recurso manualmente.

panic e recover

panic interrompe a execução normal do programa. O stack é desempilhado, os defers são executados, e o programa termina com mensagem de erro e stack trace — a menos que um recover intercepte o panic.

panic

go 
func dividir(a, b int) int {
    if b == 0 {
        panic("divisão por zero")  // aceita qualquer valor
    }
    return a / b
}

// Panics gerados automaticamente pelo runtime:
var s []int
_ = s[0]           // index out of range
var m map[string]int
m["x"] = 1         // assignment to entry in nil map
var p *int
_ = *p             // nil pointer dereference

recover — interceptando panics

recover só funciona dentro de um defer. Ele captura o valor passado ao panic e interrompe o desempilhamento — a função que chamou recover retorna normalmente (com zero values), mas a função que causou o panic não continua:

go 
func seguro(f func()) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("panic recuperado: %v", r)
        }
    }()
    f()
    return nil
}

err := seguro(func() {
    panic("algo deu muito errado")
})

fmt.Println(err)  // panic recuperado: algo deu muito errado
// programa continua normalmente

Quando usar panic vs error

Situação Use
Erro esperado, recuperável (arquivo não encontrado, input inválido) error
Violação de invariante do programa (bug, estado impossível) panic
Inicialização falhou e o programa não pode continuar panic ou log.Fatal
Servidor web precisa isolar panics de goroutines individuais recover em middleware
Não use panic para controle de fluxo normal
Em Go, erros esperados são retornados como valores — não lançados como exceções. panic é para situações verdadeiramente excepcionais. Usar panic/recover como substituto de try/catch é considerado antipadrão.

init()

init() é uma função especial chamada automaticamente pelo runtime antes de main(). Não pode ser invocada diretamente, não aceita parâmetros e não retorna valores. Um arquivo pode ter múltiplas init()s; um pacote pode ter init()s em múltiplos arquivos.

Ordem de execução

go ordem garantida 
// Para cada pacote (na ordem de dependência):
// 1. Variáveis de pacote são inicializadas
// 2. init() é chamada (pode haver várias, na ordem de aparição)
// 3. Após todos os pacotes: main() é chamada

var conexao = conectarDB()  // 1. variáveis de pacote

func init() {               // 2. init
    validarConexao(conexao)
}

func main() {               // 3. main
    // conexao já está válida aqui
}

Casos de uso legítimos

go 
// 1. Registrar drivers de banco de dados (padrão da stdlib)
import _ "github.com/lib/pq"  // init() de pq registra o driver PostgreSQL

// 2. Validar configurações obrigatórias na inicialização
func init() {
    if os.Getenv("API_KEY") == "" {
        log.Fatal("API_KEY não configurada")
    }
}

// 3. Inicializar tabelas de lookup que exigem lógica
var tabela [256]byte

func init() {
    for i := range tabela {
        tabela[i] = byte(i * 2 % 256)
    }
}
init() dificulta testabilidade
Código em init() executa automaticamente ao importar o pacote — inclusive nos testes. Efeitos colaterais em init() (conexões de rede, leitura de arquivos, variáveis globais mutáveis) tornam os testes frágeis e difíceis de isolar. Prefira inicialização explícita via construtores ou injeção de dependência quando possível.

Quiz · Questão 2 de 3 Verificação de entendimento

O código abaixo consegue recuperar o panic?

go 
func main() {
    if r := recover(); r != nil {
        fmt.Println("recuperado:", r)
    }
    panic("erro grave")
}
✓ Correto! recover() fora de um defer sempre retorna nil — não tem efeito. O padrão correto é: defer func() { if r := recover(); r != nil { ... } }() declarado antes do código que pode causar panic.

Exercício 1 — defer e recursos Aplicação prática

Uma função abre um arquivo, adquire um mutex e faz uma consulta ao banco. Qual é a ordem correta de usar defer para garantir liberação de todos os recursos?

go 
func processar() error {
    f, err := os.Open("dados.txt")
    if err != nil { return err }

    mu.Lock()

    rows, err := db.Query("SELECT ...")
    if err != nil { return err }  // mu nunca é desbloqueado!

    // ... processamento
    return nil
}
✓ Correto! O padrão idiomático é declarar o defer imediatamente após adquirir o recurso — não ao final da função. Assim, se um erro ocorrer no meio (como o erro na query sem o defer do mutex), todos os recursos já registrados são liberados corretamente na ordem LIFO. No código do exercício, mu nunca é desbloqueado se a query falhar.
Exercício 2 — Função variádica Aplicação prática

Dado o slice vals := []int{1, 2, 3}, como passar seus elementos para a função variádica func max(nums ...int) int?

✓ Correto! max(vals...) expande o slice como argumentos individuais — equivalente a max(1, 2, 3). max(vals) causaria erro de compilação porque []int não é int. A forma manual max(vals[0], vals[1], vals[2]) funciona mas é desnecessariamente verbosa e não escala.
