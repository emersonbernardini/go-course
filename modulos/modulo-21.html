O que é uma goroutine

Uma goroutine é a unidade de concorrência de Go. É uma função que executa concorrentemente com outras funções no mesmo processo — mas não é uma thread do sistema operacional. Goroutines são muito mais leves: uma thread do SO custa tipicamente 1–8 MB de stack; uma goroutine começa com apenas 2–8 KB e cresce sob demanda.

Isso significa que um programa Go pode facilmente ter dezenas de milhares (ou centenas de milhares) de goroutines ativas sem esgotar a memória — algo impossível com threads do SO equivalentes.

Goroutine vs thread vs processo

Processo Thread (SO) Goroutine
Stack inicial Vários MB 1–8 MB 2–8 KB
Criação Lenta (fork) Moderada Muito rápida
Gerenciamento Kernel Kernel Runtime Go
Quantidade típica viável Dezenas Milhares Centenas de milhares

Goroutines compartilham o mesmo espaço de endereços do processo — elas podem ler e escrever nas mesmas variáveis. Isso é poderoso mas também é a fonte dos problemas de concorrência que estudaremos nos próximos tópicos.

Stack dinâmica — goroutines crescem sob demanda
O runtime Go monitora a goroutine e, se a stack estiver quase cheia, aloca uma stack maior e copia o conteúdo. Isso permite começar com 2 KB e crescer para megabytes quando necessário — sem desperdício para goroutines simples e sem estouro de stack para as complexas.

A keyword go

Iniciar uma goroutine é deliberadamente simples: basta prefixar uma chamada de função com go. A função é lançada em uma nova goroutine e a execução continua imediatamente na goroutine atual, sem bloquear.

go básico 
func imprimir(msg string) {
    fmt.Println(msg)
}

func main() {
    go imprimir("goroutine")  // lança concorrentemente
    imprimir("main")          // executa na goroutine principal
    // Problema: main pode terminar antes da goroutine executar
}

O exemplo acima tem um problema crítico: quando main() termina, todas as goroutines são encerradas imediatamente, independente de terem terminado ou não. A saída pode ser "main" sem imprimir "goroutine" — ou ambas, dependendo do scheduling. É comportamento não-determinístico.

Goroutines com funções anônimas

É comum usar funções anônimas (literais) com go para goroutines inline:

go 
func main() {
    // Goroutine com função anônima
    go func() {
        fmt.Println("executando em goroutine separada")
    }()  // ← parênteses para invocar imediatamente

    // Passando argumentos por valor (evita problema de closure em loop)
    for i := 0; i < 3; i++ {
        go func(n int) {  // n é uma cópia de i no momento do lançamento
            fmt.Println(n)
        }(i)
    }

    time.Sleep(100 * time.Millisecond)  // gambiarra — use WaitGroup (tópico 5)
}
Goroutines não têm ID — e isso é intencional
Ao contrário de threads em outras linguagens, goroutines não expõem um identificador acessível no código. Isso é uma decisão de design: Go desencoraja o padrão "thread-local storage" onde o comportamento depende de qual thread está executando. Comunicação explícita via channels é o caminho correto.

Goroutines em produção — padrão real

go servidor HTTP concurrent 
// O net/http lança uma goroutine por request automaticamente
// Mas o padrão manual é o mesmo:
func processar(jobs []Job) {
    for _, job := range jobs {
        job := job  // captura por valor (Go >= 1.22: desnecessário)
        go func() {
            resultado, err := job.Executar()
            if err != nil {
                log.Printf("job %s falhou: %v", job.ID, err)
                return
            }
            log.Printf("job %s concluído: %v", job.ID, resultado)
        }()
    }
}

Scheduler do Go (M:N)

O runtime Go implementa um scheduler M:N — ele multiplexa M goroutines sobre N threads do SO. O número de threads reais é controlado por GOMAXPROCS, que por padrão é igual ao número de CPUs lógicas da máquina.

O modelo GMP

O scheduler usa três componentes principais:

go modelo conceitual 
// G — Goroutine: a unidade de trabalho (o que você cria com "go func()")
// M — Machine: uma thread do SO (gerenciada pelo kernel)
// P — Processor: um processador lógico do Go (fila de goroutines prontas)
//
// Relação:
//   - GOMAXPROCS define quantos P existem (padrão = número de CPUs)
//   - Cada P tem uma fila local de G prontas para executar
//   - Um M precisa de um P para executar G
//   - M sem P fica bloqueado (sem trabalho)
//
// Work stealing:
//   - Se o P de uma M fica vazio, ele "rouba" goroutines do P de outra M
//   - Isso garante que CPUs ociosas encontram trabalho automaticamente

Preempção e bloqueio

O scheduler preempta goroutines em pontos seguros — chamadas de função, operações de I/O, operações de channel. Quando uma goroutine bloqueia em I/O do sistema operacional, o runtime a desacopla do M e coloca outra goroutine no lugar, garantindo que o M não fique ocioso:

go 
// Quando esta goroutine chama os.ReadFile (I/O bloqueante):
// 1. O runtime detecta o bloqueio iminente
// 2. A goroutine é desacoplada do M
// 3. O M (thread) continua com outra goroutine da fila
// 4. Quando o I/O conclui, a goroutine volta à fila de G prontas
go func() {
    data, err := os.ReadFile("enorme.csv")  // bloqueia no I/O, mas não bloqueia a thread
    processar(data, err)
}()

// GOMAXPROCS — raramente ajustado manualmente
fmt.Println(runtime.GOMAXPROCS(0))  // 0 = apenas consultar, não alterar

// Em containers, pode ser necessário ajustar explicitamente:
// runtime.GOMAXPROCS(runtime.NumCPU())
Por que goroutines são tão eficientes em I/O
Em servidores web com threads do SO, cada request em espera de I/O mantém uma thread bloqueada — consumindo memória. Com goroutines, milhares de requests podem estar em "espera de I/O" enquanto apenas algumas threads do SO estão ativas, executando as goroutines que têm trabalho a fazer. Isso é o que permite Go lidar com alta concorrência de I/O com poucos recursos.

Race conditions

Uma race condition ocorre quando duas ou mais goroutines acessam a mesma variável concorrentemente e pelo menos uma delas escreve. O resultado depende do timing de execução — é não-determinístico e pode produzir corrupção de dados silenciosa, crashes ou comportamento imprevisível.

go race condition clássica 
var contador int  // variável compartilhada

func main() {
    for i := 0; i < 1000; i++ {
        go func() {
            contador++  // RACE: leitura + incremento + escrita NÃO são atômicos
        }()
    }
    time.Sleep(time.Second)
    fmt.Println(contador)  // pode ser qualquer valor entre 1 e 1000
}

// contador++ é na verdade três operações:
// 1. temp = contador  (leitura)
// 2. temp = temp + 1  (incremento)
// 3. contador = temp  (escrita)
//
// Se duas goroutines executam a leitura ao mesmo tempo com contador=5,
// ambas incrementam para 6 e escrevem 6 — um incremento é perdido.

O race detector — seu melhor amigo

Go tem um detector de race conditions integrado. Ative com a flag -race em qualquer comando Go:

bash 
# Compilar e rodar com race detector
go run -race main.go

# Rodar testes com race detector (sempre recomendado em CI)
go test -race ./...

# Saída quando detecta race:
# ==================
# WARNING: DATA RACE
# Write at 0x00c0000b4010 by goroutine 7:
#   main.main.func1()
#       /tmp/main.go:7 +0x28
# Previous read at 0x00c0000b4010 by goroutine 6:
#   main.main.func1()
#       /tmp/main.go:7 +0x20
# ==================

Regra de ouro da concorrência em Go

"Do not communicate by sharing memory; share memory by communicating."
O mantra da concorrência em Go: em vez de múltiplas goroutines acessando a mesma variável (compartilhar memória para comunicar), use channels para passar dados entre goroutines (comunicar para compartilhar memória). Quando necessário usar estado compartilhado, proteja com sync.Mutex (módulo 24).
go solução via channel 
// Ao invés de compartilhar um contador, enviar resultados por channel
func main() {
    ch := make(chan int, 1000)

    for i := 0; i < 1000; i++ {
        go func() {
            ch <- 1  // envia 1, sem acesso a variável compartilhada
        }()
    }

    total := 0
    for i := 0; i < 1000; i++ {
        total += <-ch  // apenas a goroutine principal escreve em total
    }
    fmt.Println(total)  // sempre 1000 — sem race condition
}

WaitGroup

O problema mais imediato ao lançar goroutines é: como esperar que todas terminem? time.Sleep é uma gambiarra — não é confiável em produção. O sync.WaitGroup é a solução idiomática para aguardar um conjunto de goroutines concluir.

go padrão básico 
import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup  // zero value é válido, não precisa de inicialização

    for i := 0; i < 5; i++ {
        wg.Add(1)         // incrementa o contador ANTES de lançar a goroutine
        go func(n int) {
            defer wg.Done()  // decrementa quando a goroutine termina
            fmt.Printf("goroutine %d concluída\n", n)
        }(i)
    }

    wg.Wait()  // bloqueia até o contador chegar a zero
    fmt.Println("todas as goroutines terminaram")
}

O WaitGroup tem três métodos: Add(n) incrementa o contador interno, Done() decrementa em 1 (equivalente a Add(-1)), e Wait() bloqueia até o contador chegar a zero.

Padrão real: processamento paralelo com coleta de erros

go processamento paralelo 
func baixarArquivos(urls []string) ([][]byte, error) {
    resultados := make([][]byte, len(urls))
    erros := make([]error, len(urls))

    var wg sync.WaitGroup

    for i, url := range urls {
        wg.Add(1)
        go func(idx int, u string) {
            defer wg.Done()
            data, err := http.Get(u)  // cada download em paralelo
            if err != nil {
                erros[idx] = err  // escrita segura: cada goroutine escreve em índice diferente
                return
            }
            defer data.Body.Close()
            resultados[idx], erros[idx] = io.ReadAll(data.Body)
        }(i, url)
    }

    wg.Wait()

    // Verificar se algum erro ocorreu
    for _, err := range erros {
        if err != nil {
            return nil, fmt.Errorf("falha em download: %w", err)
        }
    }
    return resultados, nil
}
Add() deve ser chamado antes de go, não dentro
Um erro comum é chamar wg.Add(1) dentro da goroutine. Se o scheduler executa wg.Wait() antes de qualquer goroutine chamar Add, o wait retorna imediatamente com contador zero — as goroutines não foram esperadas. Sempre chame wg.Add(1) na goroutine que lança a goroutine, antes do go.

WaitGroup não pode ser copiado

go 
// ✗ ERRADO: copia o WaitGroup ao passar por valor
func processar(wg sync.WaitGroup) {  // cópia — Done() não afeta o original
    defer wg.Done()
    // ...
}

// ✓ CORRETO: sempre passe por ponteiro
func processar(wg *sync.WaitGroup) {
    defer wg.Done()
    // ...
}

// ✓ Ou use closures que capturam o ponteiro
var wg sync.WaitGroup
wg.Add(1)
go func() {
    defer wg.Done()  // captura &wg implicitamente — correto
}()
wg.Wait()

Qual é o output do código abaixo?

go 
func main() {
    go fmt.Println("goroutine")
    fmt.Println("main")
}
✓ Correto! Quando main() retorna, o programa termina — todas as goroutines em execução são encerradas imediatamente, sem chance de completar. Quiz · Questão 2 de 3 Verificação de entendimento

O código abaixo tem race condition?

go 
resultados := make([]int, 10)
var wg sync.WaitGroup

for i := 0; i < 10; i++ {
    wg.Add(1)
    go func(idx int) {
        defer wg.Done()
        resultados[idx] = idx * idx  // escrita em índices diferentes
    }(i)
}
wg.Wait()
fmt.Println(resultados)
✓ Correto! Race condition exige acesso concorrente ao mesmo endereço de memória com pelo menos uma escrita. Aqui, cada goroutine escreve em resultados[idx] onde idx é único por goroutine — índices 0 a 9 distintos. Não há sobreposição de memória. sync.WaitGroup é thread-safe por design. O go run -race confirmaria: sem data race.
Quiz · Questão 3 de 3 Verificação de entendimento

Qual é o problema no código abaixo?

go 
var wg sync.WaitGroup

for i := 0; i < 5; i++ {
    go func(n int) {
        wg.Add(1)         // Add dentro da goroutine
        defer wg.Done()
        fmt.Println(n)
    }(i)
}

wg.Wait()
fmt.Println("fim")
✓ Correto! O problema é sutil mas crítico: se o scheduler executar wg.Wait() antes de qualquer goroutine chamar wg.Add(1), o contador está em zero e Wait() retorna imediatamente — sem esperar nenhuma goroutine. O padrão correto é sempre chamar wg.Add(1) na goroutine que lança a goroutine, antes do go: wg.Add(1); go func() { defer wg.Done(); ... }().
Exercício 1 — Identificar race condition Aplicação prática

O código abaixo é um cache simples. O que acontece quando múltiplas goroutines chamam Set e Get concorrentemente, e qual é a correção mais adequada para o cenário descrito?

go 
type Cache struct {
    data map[string]string
}

func (c *Cache) Set(key, value string) {
    c.data[key] = value  // escrita no map
}

func (c *Cache) Get(key string) (string, bool) {
    v, ok := c.data[key]  // leitura no map
    return v, ok
}

// Usado concorrentemente por muitas goroutines
✓ Correto! Maps em Go não são thread-safe — acesso concorrente com ao menos uma escrita causa panic em runtime (concurrent map read and map write). A solução correta é um sync.RWMutex: Get usa RLock (múltiplas leituras simultâneas são permitidas) e Set usa Lock exclusivo. Para casos de alta contenção, considere sync.Map (módulo 24), que tem otimizações específicas para leituras frequentes.
Exercício 2 — WaitGroup com limite de concorrência Aplicação prática

Você precisa processar 10.000 URLs em paralelo, mas lançar 10.000 goroutines simultâneas esgota conexões de rede. Qual padrão resolve isso limitando a concorrência a no máximo 20 goroutines ao mesmo tempo?

✓ Correto! O padrão semáforo com channel buffered é o idioma Go para limitar concorrência. sem := make(chan struct{}, 20) e então no loop: sem <- struct{}{} (bloqueia se já há 20 no canal), lança a goroutine com defer func() { <-sem }(). Assim, no máximo 20 goroutines executam simultaneamente. GOMAXPROCS controla threads do SO, não quantas goroutines ficam ativas. Batches sequenciais funcionam mas subutilizam: se uma URL de um batch demora, as outras 19 ficam ociosas.
