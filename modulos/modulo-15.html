O que é um ponteiro

Um ponteiro é uma variável que armazena o endereço de memória de outra variável — não o valor em si. Em vez de conter 42, contém "o valor está no endereço 0xc0000b4010".

O tipo de um ponteiro para int é *int. Para string é *string. Para uma struct Pessoa é *Pessoa. O asterisco faz parte do tipo.

go ponteiro na memória 
x := 42          // variável int — contém o valor 42
p := &x          // ponteiro *int — contém o endereço de x

fmt.Println(x)   // 42        — valor de x
fmt.Println(p)   // 0xc000b4010 — endereço de x (varia a cada execução)
fmt.Println(*p)  // 42        — valor no endereço apontado por p (derreferência)
Go não tem aritmética de ponteiros
Em C é possível fazer p++ para avançar um ponteiro para o próximo elemento de um array. Em Go isso não existe — ponteiros só podem ser dereferenciados ou comparados com nil. Isso elimina uma categoria inteira de bugs de corrupção de memória.

& e * — os dois operadores de ponteiro

Há dois operadores para trabalhar com ponteiros:

  • &x — endereço de: retorna um ponteiro para x
  • *p — derreferência: retorna o valor no endereço apontado por p
go 
x := 10
p := &x      // p aponta para x

// Leitura via ponteiro
fmt.Println(*p)  // 10

// Escrita via ponteiro — modifica x diretamente
*p = 99
fmt.Println(x)   // 99 — x foi modificado via ponteiro
fmt.Println(*p)  // 99

// & e * são inversos
fmt.Println(*&x == x)  // true — &x → ponteiro, * → volta ao valor

new() — outra forma de criar ponteiros

A função built-in new(T) aloca memória para um valor do tipo T, inicializa com zero value e retorna um ponteiro *T:

go 
p := new(int)       // *int, *p == 0
fmt.Println(*p)     // 0

*p = 42
fmt.Println(*p)     // 42

// new(T) é equivalente a:
// var v T
// p := &v
// Na prática, &T{} ou &v são mais usados que new()

Ponteiro para struct literal

A forma mais comum de criar um ponteiro para struct é com &NomeTipo{...} — mais conciso que declarar e depois tirar o endereço:

go 
type Pessoa struct{ Nome string; Idade int }

// Verboso
p1 := Pessoa{Nome: "Alice", Idade: 30}
ptr1 := &p1

// Idiomático — direto no literal
ptr2 := &Pessoa{Nome: "Bob", Idade: 25}

// Acesso via ponteiro — Go derreferencia automaticamente
fmt.Println(ptr2.Nome)   // Bob (equivale a (*ptr2).Nome)

nil pointer

O zero value de qualquer tipo ponteiro é nil — um ponteiro que não aponta para nenhum endereço válido. Derreferenciar um nil pointer causa um panic em tempo de execução: runtime error: invalid memory address or nil pointer dereference.

go 
var p *int  // nil — zero value de *int

fmt.Println(p)   // nil
fmt.Println(*p)  // PANIC: nil pointer dereference

// Verificar antes de derreferenciar
if p != nil {
    fmt.Println(*p)
}

nil pointer como valor opcional

Antes dos tipos genéricos e do tipo Option popularizado em outras linguagens, ponteiros nilizáveis eram (e ainda são) a forma de expressar "valor opcional" em Go — um campo de struct que pode ou não estar presente:

go 
type Pedido struct {
    ID          int
    Desconto    *float64  // nil = sem desconto; não-nil = tem desconto
    Observacao  *string   // nil = sem observação
}

p := Pedido{ID: 1}

// Sem desconto
fmt.Println(p.Desconto)  // nil

// Com desconto
desc := 0.1
p.Desconto = &desc
fmt.Printf("%.0f%% de desconto\n", *p.Desconto*100)  // 10% de desconto

// Verificação segura
if p.Desconto != nil {
    aplicarDesconto(*p.Desconto)
}
Nil pointer dereference é o erro mais comum em Go
Sempre que você trabalha com ponteiros — especialmente retornados por funções — verifique se são nil antes de derreferenciar. Em funções que retornam (*T, error), quando error != nil o ponteiro geralmente é nil — use o erro antes de tentar acessar o valor.

Passagem por valor vs por referência

Go passa todos os argumentos por valor — sempre. O que muda é o que está sendo copiado. Passar um ponteiro copia o endereço (8 bytes em sistemas 64-bit), não os dados apontados. A distinção prática:

go valor vs ponteiro 
type Config struct {
    Debug bool
    Porta int
}

// Por valor — recebe cópia, original não muda
func configurarV(c Config) {
    c.Debug = true  // modifica a cópia local
}

// Por ponteiro — modifica o original via endereço
func configurarP(c *Config) {
    c.Debug = true  // Go derreferencia automaticamente
}

cfg := Config{Porta: 8080}

configurarV(cfg)
fmt.Println(cfg.Debug)  // false — original inalterado

configurarP(&cfg)
fmt.Println(cfg.Debug)  // true — original modificado

Custo de cópia

Passar structs pequenas por valor é geralmente tão eficiente quanto por ponteiro — ou mais, pois evita indireção de memória e pressão no GC. A heurística prática:

Tamanho aproximado Preferir
≤ 3-4 words (~32 bytes) valor
> 32 bytes ou precisa modificar o original ponteiro

Quando usar ponteiros

As quatro razões legítimas para usar ponteiros em Go:

1. Modificar o original

go 
func resetar(n *int) {
    *n = 0
}

x := 42
resetar(&x)
fmt.Println(x)  // 0

2. Evitar cópia de structs grandes

go 
type Imagem struct {
    Pixels [4096][4096][3]byte  // ~50MB
}

// Copiar 50MB a cada chamada seria inaceitável
func processar(img *Imagem) { /* ... */ }

3. Expressar opcionalidade

go 
type Filtro struct {
    Limite   *int    // nil = sem limite
    DataInicio *time.Time  // nil = sem restrição de data
}

4. Receivers de método que modificam o receptor

Este é o caso mais frequente — estudaremos em detalhes no próximo módulo. Em resumo: se um método precisa modificar a struct, o receiver deve ser um ponteiro:

go 
type Contador struct{ n int }

// Receiver por ponteiro — modifica o Contador original
func (c *Contador) Incrementar() { c.n++ }

// Receiver por valor — opera em cópia, não modifica o original
func (c Contador) Valor() int { return c.n }

Quando NÃO usar ponteiros

  • Tipos básicos pequenos (int, bool, string) — cópia é barata e semântica de valor é mais clara
  • Structs pequenas sem necessidade de modificação — valor é mais simples e mais cache-friendly
  • Slices e maps — já são tipos de referência internamente; ponteiro para slice (*[]int) é raramente necessário e geralmente sinal de design ruim
Consistência do receiver importa
Se qualquer método de um tipo usa receiver por ponteiro, todos os métodos deveriam usar — mesmo os que não modificam o receptor. Misturar receivers por valor e por ponteiro no mesmo tipo causa confusão sobre quando o Go copia e quando não copia. Estudaremos isso no Módulo 16.
Quiz · Questão 1 de 3 Verificação de entendimento

O que é impresso pelo código abaixo?

go 
x := 5
p := &x
*p = 10
fmt.Println(x, *p)
✓ Correto! p := &x faz p apontar para x. *p = 10 escreve o valor 10 no endereço apontado por p — que é o mesmo endereço de x. Resultado: x e *p são o mesmo dado, ambos valem 10.
Quiz · Questão 2 de 3 Verificação de entendimento

Uma função retorna (*Usuario, error). O chamador faz u, err := buscar(1) e imediatamente acessa u.Nome sem verificar err. O que pode acontecer?

✓ Correto! Quando uma função falha e retorna error != nil, o ponteiro retornado é convencionalmente nil. Acessar qualquer campo de um nil pointer causa panic. A correção é sempre verificar o erro primeiro: if err != nil { return err }.
Quiz · Questão 3 de 3 Verificação de entendimento

Por que *[]int (ponteiro para slice) é raramente necessário em Go?

✓ Correto! Passar []int já permite modificar os elementos (backing array compartilhado). *[]int é necessário apenas quando a função precisa fazer o header do slice do chamador apontar para um novo array — ex: reimplementar append. Na prática, retornar o slice modificado é a abordagem idiomática em vez de *[]int.
Exercício 1 — Valor vs ponteiro Aplicação prática

O código abaixo tenta trocar os valores de duas variáveis. Por que não funciona e qual é a correção?

go 
func trocar(a, b int) {
    a, b = b, a
}

x, y := 1, 2
trocar(x, y)
fmt.Println(x, y)  // 1 2 — não trocou
✓ Correto! Go passa int por valor — a função opera em cópias. Duas correções são válidas: passar ponteiros (*int) ou retornar os valores trocados (return b, a e x, y = trocar(x, y)). A versão com ponteiros é mais didática; a versão com retorno é mais idiomática em Go.
Exercício 2 — Opcionalidade Aplicação prática

Uma API retorna dados de um produto. O campo Desconto pode ou não existir — quando existe, é um valor entre 0.0 e 1.0. Qual tipo representa isso corretamente?

✓ Correto! *float64 representa opcionalidade sem ambiguidade: nil = sem desconto; &0.0 = desconto de 0% (que pode ser semanticamente diferente de ausente). Usar float64 com 0.0 para "ausente" é ambíguo — 0% de desconto e sem desconto teriam o mesmo valor. Um campo bool adicional funciona, mas *float64 é mais conciso e o padrão da stdlib (ex: encoding/json).
