pprof — CPU e memória profiling

A regra fundamental de otimização é: nunca otimize sem medir primeiro. O instinto sobre onde está o gargalo quase sempre está errado. O Go oferece runtime/pprof e net/http/pprof como ferramentas de profiling embutidas — sem dependências externas, prontas para uso em produção.

CPU profiling — onde o tempo é gasto

O CPU profiler interrompe o programa a cada 10ms e registra a stack de chamadas ativa. Após muitas amostras, emerge um mapa estatístico de onde o tempo de CPU é consumido:

go CPU profiling em programa standalone 
package main

import (
    "os"
    "runtime/pprof"
)

func main() {
    // Criar arquivo de perfil
    f, err := os.Create("cpu.pprof")
    if err != nil {
        panic(err)
    }
    defer f.Close()

    // Iniciar coleta de CPU
    if err := pprof.StartCPUProfile(f); err != nil {
        panic(err)
    }
    defer pprof.StopCPUProfile()  // SEMPRE parar antes de analisar

    // ... código a ser perfilado
    processarDados(carregarEntrada())
}

// Analisar depois:
// go tool pprof cpu.pprof
// (pprof) top10        → top 10 funções por CPU
// (pprof) web          → abre gráfico de chama no browser (requer graphviz)
// (pprof) list minhafunc → código anotado com amostras por linha

Memory profiling — onde as alocações acontecem

go heap profiling 
import (
    "os"
    "runtime"
    "runtime/pprof"
)

func capturarHeap(nome string) {
    f, _ := os.Create(nome)
    defer f.Close()

    runtime.GC()  // forçar GC antes de capturar para dados mais limpos
    pprof.WriteHeapProfile(f)
}

// Em pontos estratégicos do programa:
capturarHeap("antes.pprof")
processarDados(entrada)
capturarHeap("depois.pprof")

// Comparar dois perfis (mostra delta de alocações):
// go tool pprof -base antes.pprof depois.pprof
// (pprof) top         → funções com maior crescimento de alocações

pprof via HTTP — profiling de servidores em produção

Para servidores HTTP, o subpacote net/http/pprof registra endpoints de profiling no DefaultServeMux com apenas um import. Permite capturar perfis de um servidor em execução sem reiniciá-lo:

go servidor com pprof endpoints 
import (
    "net/http"
    _ "net/http/pprof"  // import por efeito colateral — registra os handlers
)

func main() {
    // Servidor de diagnóstico em porta separada — NUNCA expor na porta pública
    go func() {
        http.ListenAndServe("localhost:6060", nil)
    }()

    // Servidor de aplicação normal
    srv := configurarServidor()
    srv.ListenAndServe()
}

// Comandos para capturar perfis do servidor em execução:
// go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30
//   → 30s de CPU profiling
//
// go tool pprof http://localhost:6060/debug/pprof/heap
//   → snapshot atual do heap
//
// go tool pprof http://localhost:6060/debug/pprof/goroutine
//   → todas as goroutines (detecta leaks)
Nunca expor pprof em porta pública
Os endpoints /debug/pprof/ expõem informação interna do processo — stack traces, goroutines, variáveis de ambiente. Sempre sirva em localhost:porta-separada e use SSH tunneling ou acesso restrito por rede para acessar em produção. O import _ "net/http/pprof" no pacote main garante que ele só exista em binários que você construiu explicitamente para isso.

Benchmarks com testing.B

Benchmarks são a ferramenta para medir o desempenho de funções específicas de forma reproduzível. O pacote testing os suporta nativamente: basta nomear funções com prefixo Benchmark no mesmo arquivo _test.go dos testes unitários. O runner calibra automaticamente o número de iterações necessário para uma medição estatisticamente válida.

go benchmark_test.go 
package processador_test

import (
    "strings"
    "testing"
    "unicode"
)

// b.N é ajustado automaticamente pelo runner para atingir ~1s de execução
func BenchmarkNormalizarV1(b *testing.B) {
    entrada := "  Olá, Mundo!  com ESPAÇOS extras  "
    b.ResetTimer()  // desconta setup do tempo medido

    for i := 0; i < b.N; i++ {
        normalizarV1(entrada)  // implementação com strings.TrimSpace + loop
    }
}

func BenchmarkNormalizarV2(b *testing.B) {
    entrada := "  Olá, Mundo!  com ESPAÇOS extras  "
    b.ResetTimer()

    for i := 0; i < b.N; i++ {
        normalizarV2(entrada)  // implementação com strings.Map + Fields
    }
}

// Benchmark com sub-benchmarks para diferentes tamanhos de entrada:
func BenchmarkProcessar(b *testing.B) {
    casos := []struct {
        nome    string
        tamanho int
    }{
        {"pequeno", 100},
        {"medio", 10_000},
        {"grande", 1_000_000},
    }

    for _, tc := range casos {
        entrada := gerarEntrada(tc.tamanho)
        b.Run(tc.nome, func(b *testing.B) {
            b.SetBytes(int64(tc.tamanho))  // reporta throughput em B/s
            b.ResetTimer()
            for i := 0; i < b.N; i++ {
                processar(entrada)
            }
        })
    }
}

Medindo alocações com AllocsPerRun

go assertion de alocações em teste unitário 
func TestFormatarSemAlocacao(t *testing.T) {
    entrada := Usuario{Nome: "Ana", ID: 42}

    // Garante que formatar() não aloca no caminho crítico
    allocs := testing.AllocsPerRun(100, func() {
        _ = formatar(entrada)
    })

    if allocs > 0 {
        t.Errorf("formatar alocou %.0f vez(es), esperado 0", allocs)
    }
}
-count=10 para resultados confiáveis
Uma única execução de benchmark pode ser ruidosa por interferência do scheduler, GC ou cache da CPU. Use -count=10 para executar cada benchmark dez vezes e passe a saída para benchstat (go install golang.org/x/perf/cmd/benchstat@latest), que calcula média, desvio padrão e detecta se a diferença entre duas versões é estatisticamente significativa.

Escape analysis e alocações

Em Go, cada variável vive ou na stack (alocação zero-cost, desalocada ao retornar da função) ou no heap (alocação cara, pressiona o GC). O compilador decide onde cada variável vai através da escape analysis: se uma variável pode sobreviver ao escopo da função que a criou, ela "escapa" para o heap.

Visualizando decisões de escape

# ./main.go:18:14: &Config{} escapes to heap
# ./main.go:24:16: buf does not escape    → buf fica na stack (bom)

# -m -m para detalhes extras:
go build -gcflags="-m -m" ./...

Causas comuns de escape — e como evitar

go padrões que causam escape vs alternativas 
// 1. Retornar ponteiro para variável local → escapa para heap
func novoUsuario(nome string) *Usuario {
    u := Usuario{Nome: nome}  // u escapa: retornamos &u implicitamente
    return &u
}
// Alternativa: retornar por valor quando o tipo é pequeno
func novoUsuario(nome string) Usuario {
    return Usuario{Nome: nome}  // fica na stack do chamador
}

// 2. Armazenar em interface{} → escapa para heap (boxing)
func exemplo() {
    var x int = 42
    var i any = x  // x é copiado e boxed no heap para caber na interface
    fmt.Println(i)
}

// 3. Closure capturando variável local → variável escapa
func contadorFactory() func() int {
    n := 0   // n escapa para o heap: a closure pode sobreviver a esta função
    return func() int {
        n++
        return n
    }
}

// 4. Slices crescendo além da capacidade inicial → realocação no heap
func processarIDs(ids []int) []string {
    // Se não pre-alocar, cada append que ultrapassar a cap gera nova alocação:
    result := make([]string, 0, len(ids))  // pré-alocar: sem realocação
    for _, id := range ids {
        result = append(result, strconv.Itoa(id))
    }
    return result
}

Interface vs tipo concreto no caminho crítico

go custo de interfaces em hot paths 
// Interface implica: dispatch indireto (vtable) + possível boxing
type Processador interface {
    Processar([]byte) []byte
}

func executarLoop(p Processador, dados [][]byte) {
    for _, d := range dados {
        p.Processar(d)  // chamada indireta por vtable — sem inlining
    }
}

// Em hot path com tipo conhecido: use tipo concreto ou genérico
func executarLoopConcreto(p *ProcessadorRapido, dados [][]byte) {
    for _, d := range dados {
        p.Processar(d)  // o compilador pode inline esta chamada
    }
}

// Ou com generics (Go 1.18+): mantém polimorfismo sem dispatch indireto
func executarLoopGenerico[P interface{ Processar([]byte) []byte }](p P, dados [][]byte) {
    for _, d := range dados {
        p.Processar(d)  // monomorphized em compile-time → inlineable
    }
}
Não otimize escape prematuro
Forçar variáveis para a stack (evitando ponteiros, evitando interfaces) tem custo de legibilidade e manutenibilidade. Escapes para o heap são baratos em Go — o GC é eficiente. Só invista nessa otimização quando o benchmark confirmar que a alocação específica é o gargalo. O compilador já faz escape analysis corretamente — confie nele primeiro.

sync.Pool — reutilização de objetos

sync.Pool é um cache thread-safe de objetos temporários que pode ser reutilizados — evitando alocações repetidas de objetos que têm vida curta mas são criados em alta frequência. O GC pode limpar o pool a qualquer momento, então objetos no pool não têm garantia de persistência — isso é o comportamento correto: o pool é uma otimização de alocação, não um cache de dados.

Caso de uso real: pool de bytes.Buffer

Um dos usos mais comuns em servidores HTTP: reutilizar bytes.Buffer para serializar respostas, evitando uma alocação por requisição:

go pool de bytes.Buffer para serialização 
var bufPool = sync.Pool{
    New: func() any {
        // New é chamado apenas quando o pool está vazio
        return new(bytes.Buffer)
    },
}

func serializarResposta(dados any) ([]byte, error) {
    // Pegar um buffer do pool (ou criar novo se pool vazio)
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset()  // SEMPRE resetar antes de usar — buffer pode ter estado anterior
    defer bufPool.Put(buf)  // devolver ao pool ao terminar

    if err := json.NewEncoder(buf).Encode(dados); err != nil {
        return nil, fmt.Errorf("serializar: %w", err)
    }

    // Copiar o resultado ANTES de devolver o buffer ao pool
    resultado := make([]byte, buf.Len())
    copy(resultado, buf.Bytes())
    return resultado, nil
}

// Sem pool: cada chamada aloca um novo bytes.Buffer no heap
// Com pool: a maioria das chamadas reutiliza um buffer existente
// Em um servidor com 10k req/s, isso elimina ~10k alocações/s

Pool de structs pesadas — exemplo com parser

go pool de parsers com estado inicializável 
type Parser struct {
    buf     [64 * 1024]byte  // buffer interno de 64KB — caro de alocar
    estado  int
    erros   []string
}

func (p *Parser) Reset() {
    p.estado = 0
    p.erros = p.erros[:0]  // reutiliza o slice sem realocar
}

var parserPool = sync.Pool{
    New: func() any { return new(Parser) },
}

func parsearDocumento(dados []byte) (*Resultado, error) {
    p := parserPool.Get().(*Parser)
    p.Reset()
    defer parserPool.Put(p)

    return p.Parse(dados)
}

// O benchmark mostra a diferença:
// Sem pool: 1 alloc/op (64KB), ~2.1µs/op
// Com pool: 0 allocs/op (após warmup), ~0.3µs/op
Três regras obrigatórias do sync.Pool
(1) Sempre Reset o objeto após Get — ele pode ter estado da última utilização. (2) Nunca guardar referências ao objeto após Put — outro goroutine pode estar usando. (3) Nunca colocar objetos com finalizers no pool — o GC pode coletar objetos do pool e acionar o finalizer enquanto o pool ainda o referencia.

Strings, slices e alocações evitáveis

A maioria das alocações desnecessárias em código Go de produção vem de dois lugares: concatenação de strings em loop e conversões desnecessárias entre string e []byte. Reconhecer esses padrões é o passo mais prático de otimização — frequentemente mais impactante do que qualquer mudança algorítmica.

Concatenação de strings — o antipadrão clássico

go concatenação em loop — 3 abordagens 
nomes := []string{"Ana", "Bob", "Carlos", "Diana", "Eduardo"}

// ❌ Antipadrão: concatenação com + em loop
// Cada iteração aloca uma nova string — O(n²) alocações
func juntarV1(nomes []string) string {
    resultado := ""
    for _, n := range nomes {
        resultado += n + ", "  // nova alocação a cada iteração
    }
    return resultado
}

// ✓ Correto: strings.Builder — pré-aloca e cresce internamente
func juntarV2(nomes []string) string {
    var sb strings.Builder
    sb.Grow(estimarTamanho(nomes))  // pré-alocar para evitar realocações
    for i, n := range nomes {
        if i > 0 {
            sb.WriteString(", ")
        }
        sb.WriteString(n)
    }
    return sb.String()  // única alocação de string no final
}

// ✓ Mais idiomático para este caso específico:
func juntarV3(nomes []string) string {
    return strings.Join(nomes, ", ")  // implementado com Builder internamente
}

// Benchmark com 1000 nomes:
// juntarV1: 999 allocs/op,  ~500µs/op
// juntarV2:   2 allocs/op,  ~2µs/op
// juntarV3:   1 alloc/op,   ~1.8µs/op

Conversão string ↔ []byte — quando é zero-cost

go conversões e otimizações do compilador 
// Conversão normal: aloca uma cópia
s := "hello world"
b := []byte(s)  // aloca — string e slice têm backends separados
s2 := string(b) // aloca novamente

// O compilador otimiza conversões em contextos específicos (zero-cost):
// 1. string → []byte apenas para lookup em map:
m := map[string]int{"chave": 1}
b2 := []byte("chave")
_ = m[string(b2)]  // compilador elimina a alocação aqui

// 2. []byte → string em comparação:
if string(b) == "hello" { ... }  // compilador pode comparar sem alocar

// Para evitar conversões em hot paths, projete as APIs para usar o mesmo tipo
// ao longo de todo o pipeline — não misture string e []byte sem necessidade.

// strings.Builder.WriteByte/WriteRune vs Write([]byte):
var sb strings.Builder
sb.WriteByte('G')   // zero alocação
sb.WriteRune('o')   // zero alocação
sb.Write(b)         // zero alocação (copia sem criar nova string)

Pré-alocação de slices — o impacto do append

go impacto de pré-alocação em append 
// Sem pré-alocação: Go cresce o slice dobrando a capacidade
// Para n=1000: ~10 realocações (1→2→4→8→...→1024)
func processarSemPrealloc(entrada []int) []string {
    resultado := []string{}
    for _, v := range entrada {
        resultado = append(resultado, strconv.Itoa(v))
    }
    return resultado
}

// Com pré-alocação: zero realocações
func processarComPrealloc(entrada []int) []string {
    resultado := make([]string, 0, len(entrada))  // cap = len(entrada)
    for _, v := range entrada {
        resultado = append(resultado, strconv.Itoa(v))
    }
    return resultado
}

// Caso especial: quando o tamanho é conhecido E todos os valores são preenchidos
func mapearComPrealloc(entrada []int) []string {
    resultado := make([]string, len(entrada))  // len E cap = len(entrada)
    for i, v := range entrada {
        resultado[i] = strconv.Itoa(v)  // acesso direto por índice, sem append
    }
    return resultado
}

// Benchmark com n=10_000:
// SemPrealloc:  14 allocs/op,  ~210µs/op
// ComPrealloc:   1 alloc/op,   ~120µs/op
// MapearCom:     1 alloc/op,   ~105µs/op
fmt.Sprintf vs strings.Builder em hot paths
fmt.Sprintf é conveniente mas usa reflection internamente e aloca ao menos uma string por chamada. Para formatação em loops críticos, strings.Builder com WriteString e strconv (para números) é significativamente mais rápido. Regra prática: use fmt.Sprintf fora do caminho crítico; use strings.Builder + strconv dentro de loops com alta frequência de chamada.

O fluxo correto de otimização
(1) Medir com benchmark ou pprof para confirmar onde está o gargalo. (2) Formular hipótese sobre a causa (alocação, algoritmo, contenção de lock). (3) Aplicar uma mudança por vez. (4) Medir novamente para confirmar melhora. (5) Verificar corretude com testes e race detector. Pular etapas gera código mais complexo sem ganho mensurável — o pior dos dois mundos.
Quiz · Questão 1 de 3 Verificação de entendimento

Um benchmark produz a seguinte saída. O que podemos concluir comparando as duas implementações?

bash 
BenchmarkV1-8    412_089    2_891 ns/op    1_024 B/op    12 allocs/op
BenchmarkV2-8  4_201_345      285 ns/op       32 B/op     1 allocs/op
✓ Correto! O runner de benchmarks calibra b.N automaticamente para que cada benchmark rode por ~1 segundo — implementações rápidas executam mais iterações para atingir esse tempo. Portanto, mais iterações indica implementação mais rápida, não o contrário. As métricas relevantes são sempre "por operação": ns/op, B/op e allocs/op. V2 é objetivamente melhor nos três.
Quiz · Questão 2 de 3 Verificação de entendimento

O código abaixo usa sync.Pool mas tem um bug que causa corrupção de dados em produção sob concorrência. Qual é o problema?

go 
var pool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

func processar(dados []byte) []byte {
    buf := pool.Get().(*bytes.Buffer)
    defer pool.Put(buf)

    buf.Write(dados)
    resultado := buf.Bytes()  // retorna slice referenciando o buffer interno
    return resultado           // bug: buffer devolvido ao pool antes do uso do resultado
}
✓ Correto! Dois problemas distintos. O primeiro: falta buf.Reset() após Get — o buffer pode conter bytes de quem o usou anteriormente. O segundo (mais grave): buf.Bytes() retorna um slice que aponta para o array interno do buffer. O defer pool.Put(buf) devolve o buffer ao sair da função, mas o chamador ainda segura o slice — que agora pode ser sobrescrito por outra goroutine que chamar pool.Get(). Corrija copiando o resultado: resultado := make([]byte, buf.Len()); copy(resultado, buf.Bytes()) antes do defer.
Quiz · Questão 3 de 3 Verificação de entendimento

Um serviço de alta carga tem um endpoint que processa 10.000 req/s. O profiling mostra que 40% das alocações vêm do código abaixo. Qual mudança elimina essas alocações?

go 
func handleMetrica(w http.ResponseWriter, r *http.Request) {
    id := r.URL.Query().Get("id")
    valor := calcularValor(id)

    // Esta linha causa ~3 alocações por requisição:
    msg := fmt.Sprintf("id=%s valor=%.2f", id, valor)
    w.Header().Set("X-Debug", msg)
    w.WriteHeader(http.StatusOK)
}
✓ Correto! fmt.Sprintf aceita ...any: cada argumento (id e valor) é convertido para interface, causando boxing — o que escapa para o heap. Com strings.Builder: sb.WriteString("id="); sb.WriteString(id); sb.WriteString(" valor="); sb.Write(strconv.AppendFloat(nil, valor, 'f', 2, 64)) — sem boxing, sem alocações além do resultado final. A opção A troca uma alocação por outra (a string ainda é criada internamente pelo fmt). Exercício 1 — Diagnóstico de performance Aplicação prática

Um serviço Go em produção começa a apresentar latência crescente ao longo do dia — começando rápido e degradando progressivamente até ser reiniciado. O gráfico de memória mostra crescimento linear sem queda. Qual é a sequência de investigação correta?

✓ Correto! Crescimento linear de memória ao longo do tempo com recuperação ao reiniciar aponta para duas causas clássicas: (1) memory leak — objetos acumulados no heap que o GC não consegue coletar porque ainda têm referências; (2) goroutine leak — goroutines bloqueadas que acumulam, cada uma com sua stack (mínimo 2KB, pode crescer). O heap profile comparativo identifica (1); o goroutine profile identifica (2). O trace (go tool trace) é útil para problemas de latência e scheduling, não crescimento de memória. sync.Pool sem diagnóstico é otimização cega. O race detector é para corretude, não para memória.
Exercício 2 — Decisão de otimização Aplicação prática

Um benchmark mostra que a função crítica do sistema executa em 450ns/op com 8 allocs/op. Um colega propõe três otimizações diferentes. Qual é a abordagem correta para decidir qual implementar?

✓ Correto! O processo científico de otimização exige isolar variáveis: implementar uma mudança por vez e medir o impacto antes de prosseguir. -count=10 + benchstat elimina ruído estatístico — uma diferença de 10% em uma única execução pode ser ruído do sistema; benchstat calcula se a diferença é real. Executar go test -race após cada mudança garante que a otimização não introduziu race condition. A opção D levanta um ponto válido (otimização prematura é real) mas não responde à pergunta de como decidir quando a otimização é necessária. A opção B é errada: alocações são frequentemente o gargalo, mas não sempre — um algoritmo O(n²) mais eficiente em alocações pode ser muito mais lento que um O(n log n) com mais alocações.
