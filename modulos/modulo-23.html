select

select é o mecanismo de Go para aguardar múltiplas operações de channel simultaneamente. Sua sintaxe lembra um switch, mas cada caso é uma operação de envio ou recebimento em um channel — e o select bloqueia até que ao menos um caso esteja pronto.

go select básico 
ch1 := make(chan string)
ch2 := make(chan string)

go func() {
    time.Sleep(1 * time.Second)
    ch1 <- "um"
}()
go func() {
    time.Sleep(2 * time.Second)
    ch2 <- "dois"
}()

// Aguarda o que chegar primeiro
select {
case msg := <-ch1:
    fmt.Println("recebido de ch1:", msg)
case msg := <-ch2:
    fmt.Println("recebido de ch2:", msg)
}
// Imprime "recebido de ch1: um" após ~1s

Se múltiplos casos estiverem prontos ao mesmo tempo, Go escolhe um aleatoriamente — não o primeiro na ordem textual. Isso é intencional: evita starvation de channels com menor prioridade.

Caso default — select não-bloqueante

Um default faz o select não bloquear: se nenhum channel estiver pronto, o caso default executa imediatamente. Útil para polling ou tentativas sem espera:

go 
// Verificação não-bloqueante de um channel
func tentarReceber(ch <-chan int) (int, bool) {
    select {
    case v := <-ch:
        return v, true
    default:
        return 0, false  // channel não tem valor disponível agora
    }
}

// Envio não-bloqueante
func tentarEnviar(ch chan<- int, v int) bool {
    select {
    case ch <- v:
        return true
    default:
        return false  // channel cheio ou sem receiver
    }
}

select em loop — o padrão event loop

O uso mais comum de select é dentro de um for para processar eventos de múltiplas fontes continuamente. Isso forma o núcleo de muitos servidores e workers em Go:

go worker com múltiplas fontes 
func worker(tarefas <-chan Tarefa, erros <-chan error, done <-chan struct{}) {
    for {
        select {
        case t := <-tarefas:
            processar(t)
        case err := <-erros:
            log.Printf("erro recebido: %v", err)
        case <-done:
            fmt.Println("worker encerrando")
            return
        }
    }
}
select com channels nil
Um case com channel nil nunca está pronto — é ignorado pelo select. Isso é um padrão útil: ao nil-ar um channel dentro de um loop de select, você efetivamente "desativa" aquele caso sem remover o código. Padrão comum para draining seletivo de múltiplos channels.

Timeout pattern

Todo sistema que faz I/O precisa de timeouts. Em Go, o padrão idiomático combina select com time.After ou context.WithTimeout para limitar quanto tempo uma operação pode bloquear.

time.After — timeout simples

time.After(d) retorna um channel que recebe um valor após a duração d. Basta colocá-lo como caso do select:

go timeout com time.After 
func buscarComTimeout(id int) (*Resultado, error) {
    resultado := make(chan *Resultado, 1)

    go func() {
        r, _ := buscarNoBanco(id)  // operação potencialmente lenta
        resultado <- r
    }()

    select {
    case r := <-resultado:
        return r, nil
    case <-time.After(3 * time.Second):
        return nil, fmt.Errorf("buscarComTimeout: timeout após 3s")
    }
}
time.After vaza memória em loops
Cada chamada a time.After cria um timer que não é coletado pelo GC até disparar — mesmo que o select já tenha saído pelo outro caso. Em loops de alta frequência, isso acumula. Use time.NewTimer com t.Stop() e reset explícito, ou prefira context.WithTimeout que é a abordagem recomendada em código de produção.

context.WithTimeout — abordagem de produção

context.WithTimeout propaga o timeout por toda a cadeia de chamadas — qualquer função que receba o ctx pode respeitar o prazo automaticamente. É o padrão correto para código real:

go timeout com context 
func handler(w http.ResponseWriter, r *http.Request) {
    // Herda o contexto da requisição e adiciona timeout
    ctx, cancel := context.WithTimeout(r.Context(), 5*time.Second)
    defer cancel()  // SEMPRE deferir o cancel — evita vazamento de goroutine

    resultado, err := buscarDados(ctx, r.URL.Query().Get("id"))
    if err != nil {
        if errors.Is(err, context.DeadlineExceeded) {
            http.Error(w, "serviço indisponível", http.StatusGatewayTimeout)
            return
        }
        http.Error(w, "erro interno", http.StatusInternalServerError)
        return
    }
    json.NewEncoder(w).Encode(resultado)
}

// buscarDados respeita o contexto:
func buscarDados(ctx context.Context, id string) (*Dados, error) {
    req, _ := http.NewRequestWithContext(ctx, "GET",
        "https://api.exemplo.com/dados/"+id, nil)
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return nil, fmt.Errorf("buscarDados: %w", err)
    }
    defer resp.Body.Close()
    // ...
}
Abordagem Quando usar Cuidado
time.After Scripts, testes, operações únicas Vaza em loops de alta frequência
context.WithTimeout Servidores, APIs, código de produção Sempre deferir cancel()

Done channel / cancellation

Como sinalizar a uma goroutine que ela deve parar? A abordagem mais direta é um done channel: um chan struct{} que, quando fechado, desbloqueia todos os <-done simultaneamente. O fechamento propaga o sinal para quantas goroutines precisar — sem precisar enviar um valor por destinatário.

go done channel manual 
func iniciarWorkers(n int) (func(), <-chan Resultado) {
    done := make(chan struct{})
    resultados := make(chan Resultado)

    for i := 0; i < n; i++ {
        go func(id int) {
            for {
                select {
                case <-done:
                    // sinal de encerramento — sai sem bloquear
                    return
                default:
                    r := executarTarefa(id)
                    select {
                    case resultados <- r:
                    case <-done:
                        return
                    }
                }
            }
        }(i)
    }

    parar := func() { close(done) }  // fecha uma vez, notifica todos
    return parar, resultados
}

// Uso:
parar, resultados := iniciarWorkers(4)
defer parar()

for r := range resultados {
    fmt.Println(r)
}

context.WithCancel — done channel da stdlib

O pacote context formaliza o padrão done channel. ctx.Done() retorna um channel que fecha quando o contexto é cancelado — e o contexto se propaga pela árvore de chamadas automaticamente:

go cancellation com context 
func gerarNumeros(ctx context.Context) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        n := 0
        for {
            select {
            case <-ctx.Done():
                // ctx cancelado ou deadline excedido — encerra limpo
                fmt.Println("gerador cancelado:", ctx.Err())
                return
            case out <- n:
                n++
            }
        }
    }()
    return out
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())

    nums := gerarNumeros(ctx)
    for i := 0; i < 5; i++ {
        fmt.Println(<-nums)  // 0 1 2 3 4
    }
    cancel()  // sinaliza encerramento — gerarNumeros retorna

    // Pequena espera para o print do gerador aparecer:
    time.Sleep(10 * time.Millisecond)
}

Por que chan struct{} e não chan bool?

go 
// chan bool — funciona, mas o valor é irrelevante e ambíguo:
done := make(chan bool)
close(done)
v := <-done  // v == false (zero value de bool) — confuso

// chan struct{} — sem ambiguidade: o sinal é o fechamento, não o valor
done := make(chan struct{})
close(done)
<-done  // sem valor útil — explícito que é apenas sinalização

// struct{} ocupa 0 bytes: sem alocação, sem overhead
Goroutine leak: o bug silencioso mais comum
Uma goroutine bloqueada em um channel que nunca receberá dados permanece viva para sempre — é um goroutine leak. Sempre forneça um caminho de saída via done channel ou contexto. O pacote goleak (uber-go/goleak) detecta leaks em testes automaticamente.

Fan-in / Fan-out

Fan-in e Fan-out são padrões para distribuir e consolidar trabalho entre múltiplas goroutines. São complementares: fan-out distribui um único fluxo de entrada para N workers; fan-in multiplexar N channels em um único channel de saída.

Fan-out — distribuindo trabalho

Quando uma etapa do pipeline é CPU-bound ou I/O-bound e lenta, lançar múltiplas goroutines para processá-la em paralelo reduz a latência total:

go fan-out: N workers para a mesma entrada 
// Simula compressão lenta de arquivos
func comprimirArquivo(ctx context.Context, nome string) Resultado {
    time.Sleep(100 * time.Millisecond) // I/O simulado
    return Resultado{Nome: nome, Tamanho: len(nome) * 10}
}

// fanOut lança n goroutines para processar o mesmo channel de entrada
func fanOut(ctx context.Context, entrada <-chan string, n int) []<-chan Resultado {
    saidas := make([]<-chan Resultado, n)
    for i := 0; i < n; i++ {
        saida := make(chan Resultado)
        saidas[i] = saida
        go func() {
            defer close(saida)
            for nome := range entrada {
                select {
                case <-ctx.Done():
                    return
                case saida <- comprimirArquivo(ctx, nome):
                }
            }
        }()
    }
    return saidas
}

Fan-in — consolidando resultados

Após o fan-out, os N channels de saída precisam ser consolidados em um único channel para a etapa seguinte. Isso é o fan-in:

go fan-in: N channels → 1 
// fanIn multiplexa N channels de entrada em um único channel de saída
func fanIn(ctx context.Context, canais ...<-chan Resultado) <-chan Resultado {
    saida := make(chan Resultado)
    var wg sync.WaitGroup

    encaminhar := func(c <-chan Resultado) {
        defer wg.Done()
        for r := range c {
            select {
            case saida <- r:
            case <-ctx.Done():
                return
            }
        }
    }

    wg.Add(len(canais))
    for _, c := range canais {
        go encaminhar(c)
    }

    // Fecha saida quando todos os workers terminarem
    go func() {
        wg.Wait()
        close(saida)
    }()

    return saida
}

// Uso combinado: fan-out + fan-in
func processarArquivos(ctx context.Context, arquivos []string) {
    entrada := make(chan string, len(arquivos))
    for _, f := range arquivos {
        entrada <- f
    }
    close(entrada)

    // Fan-out: 4 workers processam em paralelo
    workers := fanOut(ctx, entrada, 4)

    // Fan-in: consolida os 4 channels em 1
    resultados := fanIn(ctx, workers...)

    for r := range resultados {
        fmt.Printf("comprimido: %s (%d bytes)\n", r.Nome, r.Tamanho)
    }
}
Quando fan-out vale a pena
Fan-out só traz ganho real quando a operação é genuinamente paralelizável (I/O ou CPU em núcleos distintos) e o overhead de coordenação (channels, goroutines, WaitGroup) é menor que o ganho. Para operações de microssegundos, o overhead pode superar o ganho. Meça com benchmarks antes de distribuir.

Pipeline pattern

Um pipeline é uma cadeia de estágios conectados por channels, onde cada estágio recebe valores de um channel de entrada, transforma-os e envia para um channel de saída. Cada estágio roda em sua própria goroutine — o processamento ocorre em paralelo entre os estágios (como um pipeline de CPU).

A convenção de assinatura de cada estágio é:

go assinatura padrão de estágio 
// Estágio recebe um ctx + channel de entrada, retorna channel de saída
func estagio(ctx context.Context, entrada <-chan TipoA) <-chan TipoB {
    saida := make(chan TipoB)
    go func() {
        defer close(saida)  // sinaliza fim para o próximo estágio
        for v := range entrada {
            select {
            case <-ctx.Done():
                return  // cancellation se propaga por toda a cadeia
            case saida <- transformar(v):
            }
        }
    }()
    return saida
}

Exemplo real: pipeline de processamento de logs

go pipeline completo: ler → parsear → filtrar → agregar 
type LogEntry struct {
    Nivel   string
    Msg     string
    Campos  map[string]string
}

// Estágio 1 — gerador: lê linhas de um io.Reader
func lerLinhas(ctx context.Context, r io.Reader) <-chan string {
    out := make(chan string)
    go func() {
        defer close(out)
        scanner := bufio.NewScanner(r)
        for scanner.Scan() {
            select {
            case <-ctx.Done():
                return
            case out <- scanner.Text():
            }
        }
    }()
    return out
}

// Estágio 2 — parsear: string → LogEntry
func parsearLogs(ctx context.Context, linhas <-chan string) <-chan LogEntry {
    out := make(chan LogEntry)
    go func() {
        defer close(out)
        for linha := range linhas {
            var entry LogEntry
            if err := json.Unmarshal([]byte(linha), &entry); err != nil {
                continue  // linha inválida: descarta sem parar o pipeline
            }
            select {
            case <-ctx.Done():
                return
            case out <- entry:
            }
        }
    }()
    return out
}

// Estágio 3 — filtrar: apenas erros
func filtrarErros(ctx context.Context, entries <-chan LogEntry) <-chan LogEntry {
    out := make(chan LogEntry)
    go func() {
        defer close(out)
        for e := range entries {
            if e.Nivel != "ERROR" {
                continue
            }
            select {
            case <-ctx.Done():
                return
            case out <- e:
            }
        }
    }()
    return out
}

// Estágio 4 — consumidor final: conta erros por serviço
func contarPorServico(ctx context.Context, erros <-chan LogEntry) map[string]int {
    contagem := make(map[string]int)
    for e := range erros {
        select {
        case <-ctx.Done():
            return contagem
        default:
            contagem[e.Campos["service"]]++
        }
    }
    return contagem
}

// Composição do pipeline
func analisarLogs(ctx context.Context, r io.Reader) map[string]int {
    linhas  := lerLinhas(ctx, r)
    entries := parsearLogs(ctx, linhas)
    erros   := filtrarErros(ctx, entries)
    return contarPorServico(ctx, erros)
}

Propriedades do padrão

Propriedade Como o padrão garante
Backpressure Channel unbuffered bloqueia produtor quando consumidor está lento
Encerramento limpo close(out) em cada estágio propaga EOF para o próximo via range
Cancellation ctx.Done() em cada estágio encerra toda a cadeia
Composabilidade Estágios são funções puras de channel → channel; fáceis de testar e reusar
Não esqueça o close em cada estágio
Se um estágio intermediário não fechar seu channel de saída quando encerrar, o estágio seguinte ficará bloqueado em range para sempre — goroutine leak garantido. O defer close(out) no início da goroutine de cada estágio é mandatório, não opcional.
Quiz · Questão 1 de 3 Verificação de entendimento

O código abaixo executa o select 1000 vezes com ambos os channels prontos simultaneamente. O que podemos afirmar sobre a saída?

go 
ch1 := make(chan int, 1)
ch2 := make(chan int, 1)
contCh1, contCh2 := 0, 0

for i := 0; i < 1000; i++ {
    ch1 <- 1
    ch2 <- 2
    select {
    case <-ch1:
        contCh1++
    case <-ch2:
        contCh2++
    }
}
✓ Correto! A especificação de Go garante que quando múltiplos cases de um select estão prontos, um é escolhido pseudo-aleatoriamente. Não há garantia de 50/50, mas ambos receberão seleções ao longo de 1000 iterações. Isso é intencional — previne starvation de qualquer case.
Quiz · Questão 2 de 3 Verificação de entendimento

Um servidor de alta carga executa o loop abaixo milhares de vezes por segundo. Qual é o problema?

go 
func processarMensagens(msgs <-chan Msg) {
    for {
        select {
        case msg := <-msgs:
            processar(msg)
        case <-time.After(100 * time.Millisecond):
            flush()
        }
    }
}
✓ Correto! A cada iteração onde uma mensagem está disponível, o case do timer "perde" — mas o timer criado por time.After ainda existe no heap e só é coletado após 100ms. Em alta frequência, centenas ou milhares de timers acumulam simultaneamente. A correção é usar time.NewTicker (para flush periódico) ou time.NewTimer com Reset explícito.
Quiz · Questão 3 de 3 Verificação de entendimento

O estágio abaixo tem um bug que causa goroutine leak no pipeline. Qual é o problema?

go 
func filtrar(ctx context.Context, entrada <-chan int) <-chan int {
    saida := make(chan int)
    go func() {
        for v := range entrada {
            if v%2 == 0 {
                select {
                case saida <- v:
                case <-ctx.Done():
                    return  // encerra sem fechar saida
                }
            }
        }
        // entrada foi fechada — goroutine encerra aqui
        // saida também NÃO é fechada aqui
    }()
    return saida
}
✓ Correto! Quando o contexto cancela e a goroutine retorna pelo case <-ctx.Done(), saida não é fechado. O estágio seguinte que faz for v := range saida bloqueia indefinidamente — goroutine leak. A correção é defer close(saida) no início da goroutine, garantindo fechamento em qualquer caminho de saída.
Exercício 1 — Bug em produção Aplicação prática

Um serviço faz três chamadas a APIs externas em paralelo e retorna o primeiro resultado. O código abaixo tem um bug sutil que causa goroutine leak em produção. Qual é o problema e a correção correta?

go 
func primeiroResultado(urls []string) string {
    ch := make(chan string)  // unbuffered

    for _, url := range urls {
        go func(u string) {
            resp, _ := http.Get(u)
            body, _ := io.ReadAll(resp.Body)
            ch <- string(body)  // bloqueia se ninguém está lendo
        }(url)
    }

    return <-ch  // recebe apenas o primeiro
    // As outras 2 goroutines ficam bloqueadas em ch <- para sempre
}
✓ Correto! Com channel unbuffered, após a função retornar o primeiro valor, as 2 goroutines restantes ficam bloqueadas em ch <- para sempre — ninguém mais lê o channel. Com make(chan string, len(urls)), todas as goroutines conseguem enviar sem bloquear, mesmo que apenas o primeiro seja lido. O GC coleta o channel e as goroutines encerram normalmente. A opção D (select/default) descartaria silenciosamente resultados que chegassem quase ao mesmo tempo, o que pode ser incorreto.
Exercício 2 — Decisão de design Aplicação prática

Você está implementando um sistema que processa imagens: (1) lê arquivos do disco, (2) redimensiona, (3) comprime, (4) faz upload para S3. As etapas 2 e 3 são CPU-bound e lentas. Qual combinação de padrões é mais adequada?

✓ Correto! A combinação pipeline + fan-out seletivo é o padrão ideal aqui. O pipeline conecta as etapas com backpressure natural. O fan-out é aplicado apenas nas etapas CPU-bound (redimensionar e comprimir), onde o paralelismo traz ganho real. Leitura e upload são I/O-bound e geralmente têm seus próprios limitadores (disco, banda de rede) — fan-out nessas etapas poderia saturar recursos sem ganho. A opção B (uma goroutine por arquivo) pode criar milhares de goroutines com uso de memória proporcional.
