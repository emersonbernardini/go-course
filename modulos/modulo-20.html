go mod init

Antes de Go Modules (introduzido no Go 1.11, estabilizado no 1.13), o ecossistema dependia do GOPATH — uma única árvore de diretórios compartilhada por todos os projetos da máquina. Era impossível ter versões diferentes da mesma dependência em projetos distintos, e o repositório do código precisava estar em um caminho específico dentro do GOPATH. Go Modules resolveu tudo isso.

Um módulo é uma coleção de pacotes Go com versionamento e gerenciamento de dependências. O ponto de entrada é o comando go mod init, que transforma um diretório qualquer em um módulo:

bash terminal 
# Cria um novo projeto em qualquer diretório (fora do GOPATH)
mkdir meu-projeto && cd meu-projeto
go mod init github.com/usuario/meu-projeto

# O argumento é o "module path" — o nome canônico do módulo
# Convenção: usar o caminho do repositório onde o código vai ser publicado

O module path (github.com/usuario/meu-projeto) não precisa existir como repositório para desenvolver localmente — mas precisa ser único e, por convenção, corresponder ao URL real de onde o código será hospedado. Isso permite que outros projetos importem seu módulo sem ambiguidade.

bash estrutura após init 
meu-projeto/
├── go.mod        ← criado pelo go mod init
└── main.go       ← você cria

Para projetos internos ou ferramentas pessoais que nunca serão publicadas, o module path pode ser qualquer string — por convenção usa-se algo como example.com/meu-projeto ou simplesmente meu-projeto. O que importa é que seja consistente.

Módulos substituem o GOPATH para projetos novos
Com módulos, seu projeto pode estar em qualquer diretório — não mais em $GOPATH/src/.... O go.mod é o que declara que aquele diretório é um módulo. O compilador detecta o módulo raiz lendo o go.mod mais próximo na hierarquia de diretórios.

go.mod e go.sum

O arquivo go.mod é o manifesto do módulo. Ele declara o module path, a versão mínima de Go necessária e as dependências diretas. O formato é simples e legível por humanos:

go go.mod 
module github.com/usuario/meu-projeto

go 1.22

require (
    github.com/gin-gonic/gin v1.9.1
    github.com/jackc/pgx/v5 v5.5.4
)

// replace permite substituir uma dependência por uma local (útil para desenvolvimento)
// replace github.com/usuario/lib => ../lib

Cada linha em require especifica uma dependência e sua versão mínima requerida. Go usa o algoritmo MVS (Minimum Version Selection) — em vez de pegar sempre a versão mais nova, pega a versão mínima que satisfaz todos os requisitos do grafo de dependências. Isso torna builds reproduzíveis por padrão.

go.sum — verificação criptográfica

O go.sum é gerado automaticamente e contém os hashes criptográficos de cada dependência e seu go.mod:

go go.sum (trecho) 
github.com/gin-gonic/gin v1.9.1 h1:4idEAncQnU5cB7BerypkHKpy/nc2zjouW5Wi/M2U5Z4=
github.com/gin-gonic/gin v1.9.1/go.mod h1:hPrL7YrpYKXt5YId3A/Tnip5kqbEAP+KLuI3SUcPTeU=

Cada entrada tem dois hashes: um para o conteúdo do módulo (h1:) e um para o go.mod da dependência. Se qualquer arquivo baixado não corresponder ao hash registrado, o build falha — prevenindo ataques de supply chain onde um pacote é modificado sem mudar a versão.

Arquivo Responsabilidade Commitar?
go.mod Declara dependências e versões mínimas Sim, sempre
go.sum Hashes criptográficos para verificação Sim, sempre
Nunca edite go.sum manualmente
O go.sum é gerenciado automaticamente pelas ferramentas do Go. Editar manualmente pode corromper a verificação de integridade. Se o arquivo ficar inconsistente, delete-o e execute go mod tidy para regenerar.

Dependências externas

Quando você importa um pacote externo no código, o Go não sabe automaticamente de onde baixá-lo. A dependência precisa ser declarada no go.mod antes de compilar. O fluxo normal é: escrever o import, depois rodar go get (ou go mod tidy) para resolver e registrar a dependência.

go main.go 
package main

import (
    "fmt"
    "github.com/fatih/color"  // pacote externo
)

func main() {
    color.Green("Operação concluída com sucesso")
    color.Red("Erro: %v", fmt.Errorf("conexão recusada"))
}

Ao importar github.com/fatih/color, o Go resolve o módulo a partir do host declarado no import path. O cache local fica em $GOPATH/pkg/mod — baixado uma vez, reutilizado em todos os projetos da máquina que usarem a mesma versão.

Dependências indiretas

Quando uma dependência sua depende de outra, essa segunda é uma dependência indireta. Elas aparecem no go.mod com o comentário // indirect:

go go.mod 
require (
    github.com/fatih/color v1.16.0           // direta: você importa
    github.com/mattn/go-colorable v0.1.13    // indirect: dependência do color
    github.com/mattn/go-isatty v0.0.20       // indirect: dependência do color
    golang.org/x/sys v0.18.0                 // indirect: transitiva
)

Cache local de módulos

bash 
# Ver onde ficam os módulos baixados
go env GOMODCACHE
# Normalmente: /home/usuario/go/pkg/mod

# Limpar o cache (raramente necessário)
go clean -modcache

# Verificar dependências sem conexão à internet
# (usando apenas o cache local)
GOFLAGS="-mod=mod" go build
GOPROXY — de onde vêm os módulos
Por padrão, GOPROXY=https://proxy.golang.org,direct. O Go tenta baixar pelo proxy oficial primeiro (que tem cache global de módulos públicos), e só vai diretamente ao repositório se o proxy não tiver o módulo. Para redes corporativas com acesso restrito, é comum configurar um proxy privado.

go get e go tidy

go get e go mod tidy são os dois comandos centrais para gerenciar dependências. Eles têm papéis diferentes e complementares.

go get — adicionar e atualizar dependências

bash 
# Adicionar uma dependência (versão mais recente compatível)
go get github.com/fatih/color

# Versão específica
go get github.com/fatih/color@v1.16.0

# Versão mínima (qualquer versão >= 1.15.0)
go get github.com/fatih/color@>=v1.15.0

# Última versão de um branch específico
go get github.com/fatih/color@main

# Remover uma dependência (rebaixa para não usada)
go get github.com/fatih/color@none

# Atualizar todas as dependências diretas para a versão mais recente compatível
go get -u ./...
go get mudou de papel no Go 1.17+
Antes do Go 1.17, go get também instalava binários (ferramentas de CLI). Isso foi separado: para instalar uma ferramenta, use go install. O go get agora é exclusivamente para gerenciar dependências de módulo. Exemplo: go install golang.org/x/tools/gopls@latest.

go mod tidy — sincronizar go.mod com o código

go mod tidy analisa todos os arquivos .go do módulo e ajusta o go.mod para refletir exatamente o que é necessário — adicionando o que falta e removendo o que não é mais usado:

bash 
# Sincroniza go.mod e go.sum com o código atual
go mod tidy

# O que tidy faz:
# 1. Varre todos os imports nos arquivos .go
# 2. Adiciona dependências ausentes no go.mod
# 3. Remove dependências que não são mais importadas
# 4. Atualiza go.sum com os hashes corretos

# Verificar se tidy seria necessário (sem modificar)
go mod tidy -diff  # disponível a partir do Go 1.23

Outros comandos úteis

bash 
# Listar todas as dependências (diretas e indiretas)
go list -m all

# Verificar por quê uma dependência está no go.mod
go mod why github.com/fatih/color

# Ver o grafo de dependências
go mod graph

# Baixar todas as dependências para o cache (sem compilar)
go mod download

# Verificar integridade das dependências já baixadas
go mod verify
Fluxo de trabalho recomendado em CI
Em pipelines de CI, rode go mod tidy e verifique se o go.mod e go.sum não foram alterados. Se forem, o desenvolvedor esqueceu de commitar as atualizações das dependências. Isso evita builds não-reproduzíveis em produção.

Versionamento semântico

Go Modules adota o SemVer (Semantic Versioning) como contrato formal entre quem mantém e quem usa um módulo. A versão tem o formato vMAJOR.MINOR.PATCH, onde cada número tem semântica precisa:

Componente Quando incrementar Exemplo
MAJOR Mudança incompatível com versões anteriores (breaking change) v1 → v2
MINOR Nova funcionalidade, retrocompatível v1.3 → v1.4
PATCH Correção de bug, retrocompatível v1.3.2 → v1.3.3

Major versions — o caso especial do v2+

Go tem uma regra importante: módulos com versão major ≥ 2 devem incluir o sufixo /v2 no module path. Isso é chamado de "major version suffix" e permite que um projeto importe v1 e v2 da mesma biblioteca simultaneamente:

go 
// go.mod da biblioteca na versão 2
module github.com/usuario/lib/v2  // ← sufixo /v2 obrigatório

go 1.22

// -----------------------------------------------

// go.mod de quem usa a biblioteca
require (
    github.com/usuario/lib v1.5.0      // v1 — sem sufixo
    github.com/usuario/lib/v2 v2.3.1   // v2 — com sufixo /v2
)

// -----------------------------------------------

// imports no código podem coexistir
import (
    libv1 "github.com/usuario/lib"
    libv2 "github.com/usuario/lib/v2"
)

Versões pre-release e pseudo-versões

bash 
# Pre-release: sufixo após o patch
v1.5.0-alpha.1
v1.5.0-beta.2
v1.5.0-rc.1

# Pseudo-versão: gerada pelo Go para commits sem tag
# formato: vX.Y.Z-YYYYMMDDHHMMSS-HASH
v0.0.0-20240315120000-abc123def456

# Quando usar pseudo-versão: dependência de commit específico (não recomendado em produção)
go get github.com/usuario/lib@abc123def456
v0 não tem garantias de compatibilidade
Versões v0.x.y são explicitamente instáveis — qualquer update pode quebrar a API, mesmo em MINOR ou PATCH. Isso é um sinal oficial de que a biblioteca ainda não está pronta para produção. Use v0 ciente de que qualquer go get -u pode introduzir breaking changes.
Quiz · Questão 1 de 3 Verificação de entendimento

O módulo A requer a lib X v1.3.0. O módulo B também requer a lib X, mas na versão v1.5.0. Seu projeto depende de A e B. Qual versão da lib X será usada?

✓ Correto! O MVS seleciona a versão mínima que satisfaz todos os requisitos do grafo. A v1.3.0 é insuficiente para B (que precisa de pelo menos v1.5.0), então v1.5.0 é a versão mínima que satisfaz ambos. Go não pega a versão mais nova disponível — só o mínimo necessário. Isso torna builds reproduzíveis.
Quiz · Questão 2 de 3 Verificação de entendimento

Uma biblioteca publicada em github.com/user/cache vai lançar uma versão v2 com breaking changes. Qual deve ser o module path correto no go.mod da biblioteca?

✓ Correto! Go exige que o module path inclua o sufixo /v2, /v3, etc. para versões major ≥ 2. Isso permite que consumidores importem v1 e v2 simultaneamente no mesmo binário sem conflito de nomes — tratando-as como módulos distintos. O import path nos arquivos .go também deve usar github.com/user/cache/v2.
Quiz · Questão 3 de 3 Verificação de entendimento

Você removeu todos os imports de github.com/fatih/color do código, mas o pacote ainda aparece em go.mod. Qual comando resolve isso corretamente?

✓ Correto! go mod tidy é o comando correto — ele analisa os imports em todo o código-fonte e sincroniza o go.mod, removendo dependências que não são mais referenciadas. go get @none também funciona, mas exige saber o nome exato do pacote. go mod tidy faz o trabalho completo automaticamente, incluindo atualizar o go.sum.
Exercício 1 — Diagnóstico de go.mod Aplicação prática

Seu CI falha com o erro abaixo. O go.mod tem a linha require github.com/pkg/errors v0.9.0, mas nenhum arquivo .go importa esse pacote. Qual é a causa e a solução correta?

bash 
$ go mod verify
github.com/pkg/errors v0.9.0: missing go.sum entry for module...
FAIL: go.sum is out of sync with go.mod
✓ Correto! O problema tem duas camadas: a dependência está no go.mod sem ser usada, e o go.sum ficou dessincronizado. go mod tidy resolve ambos: remove github.com/pkg/errors do go.mod (porque nenhum import o referencia) e atualiza o go.sum de acordo. Deletar o go.sum manualmente é arriscado e desnecessário.
Exercício 2 — replace e desenvolvimento local Aplicação prática

Você mantém dois módulos: github.com/empresa/api e github.com/empresa/core. Está desenvolvendo uma feature que modifica core e precisa testá-la em api antes de publicar. Como configurar o go.mod de api para usar a versão local de core?

✓ Correto! A diretiva replace no go.mod é exatamente para esse cenário — desenvolvimento local de múltiplos módulos relacionados. O Go vai usar o diretório local (../core) em vez de baixar do proxy. Lembre-se de remover o replace antes de commitar o go.mod final ou de publicar a versão, caso contrário outros desenvolvedores precisarão ter a mesma estrutura de diretórios.
