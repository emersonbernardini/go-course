Pacotes: a unidade fundamental de Go

Em Go, todo código pertence a um pacote. Um pacote é um agrupamento de arquivos .go que vivem no mesmo diretório e compartilham o mesmo namespace. É a menor unidade de organização e reutilização de código na linguagem.

A declaração de pacote é obrigatória e deve ser a primeira linha de código de qualquer arquivo Go — antes de qualquer importação ou declaração.

go qualquer-arquivo.go 
package nome_do_pacote  // sempre a primeira linha

O pacote main é especial

Vimos no módulo anterior que package main instrui o compilador a gerar um binário executável. Todos os outros nomes de pacote produzem bibliotecas — código reutilizável que pode ser importado por outros pacotes, mas não executado diretamente.

go math/operacoes.go 
package math  // biblioteca — não gera executável, pode ser importada
go main.go 
package main  // executável — exige func main()

Regra: todos os arquivos de um diretório pertencem ao mesmo pacote

Em Go, todos os arquivos .go dentro de um mesmo diretório devem declarar o mesmo nome de pacote. O compilador trata o diretório inteiro como uma unidade — é como se todos os arquivos fossem um único arquivo gigante do ponto de vista de visibilidade de símbolos.

bash estrutura de diretório 
meu-projeto/
├── main.go          → package main
├── handlers.go      → package main  ✓ mesmo pacote
└── utils.go         → package main  ✓ mesmo pacote

# ERRO: arquivos no mesmo diretório com pacotes diferentes
meu-projeto/
├── main.go          → package main
└── helpers.go       → package utils  ✗ erro de compilação

Convenção de nome de pacote

Por convenção, o nome do pacote deve ser igual ao nome do diretório que o contém. Letras minúsculas, sem underscores, sem hífens. Nomes curtos e descritivos. Essa é a convenção da comunidade Go — o compilador não a força, mas go vet avisa quando ela é violada.

bash convenção nome = diretório 
projeto/
├── main.go               → package main
├── http/
│   └── server.go         → package http    ✓
├── database/
│   └── connection.go     → package database ✓
└── utils/
    └── strings.go        → package utils   ✓
Exceção: pacotes _test
Existe uma exceção à regra de pacote único por diretório: arquivos de teste podem usar o sufixo _test no nome do pacote (ex: package math_test). Isso permite testes de caixa-preta no mesmo diretório. Veremos em detalhes no Módulo 30.

Importações

Para usar código de outro pacote, você precisa importá-lo com a palavra-chave import. As importações ficam logo após a declaração de pacote e antes de qualquer outro código.

Formas de declarar importações

Go aceita duas sintaxes para importações — individual e em bloco. A forma em bloco é fortemente preferida quando há mais de um pacote:

go formas de import 
// Forma individual — aceitável, mas verbosa
import "fmt"
import "os"
import "strconv"

// Forma em bloco — preferida pela comunidade Go
import (
    "fmt"
    "os"
    "strconv"
)

O caminho de importação

O que fica entre as aspas não é o nome do pacote — é o caminho de importação (import path). Para pacotes da stdlib, é um caminho simples como "fmt" ou "net/http". Para pacotes externos, inclui o domínio do repositório:

go caminhos de importação 
import (
    // Pacotes da stdlib — caminho simples
    "fmt"
    "os"
    "net/http"
    "encoding/json"

    // Pacote externo — caminho com domínio
    "github.com/user/meu-pacote"
)
Caminho vs nome do pacote
O caminho "net/http" importa o pacote cujo nome é http. Você o usa como http.ListenAndServe(), não como net/http.ListenAndServe(). O que está após a última barra é o nome do pacote — o que você usa no código.

Aliases de importação

Você pode dar um nome alternativo a um pacote importado. Isso é útil quando dois pacotes têm o mesmo nome, ou quando o nome padrão é muito longo:

go aliases de importação 
import (
    // Alias comum: pacote externo com nome conflitante
    meuhttp "github.com/user/http"
    "net/http"

    // Alias de conveniência
    stdjson "encoding/json"

    // Blank identifier: importa apenas pelos efeitos colaterais (init())
    // O pacote é executado mas seus símbolos não ficam acessíveis
    _ "github.com/lib/pq"  // registra driver PostgreSQL
)

func main() {
    http.ListenAndServe(":8080", nil)   // stdlib
    meuhttp.DoSomething()               // pacote externo
    stdjson.Marshal(nil)                // alias
}

A regra de ouro: importação não usada é erro

Já mencionamos no módulo anterior, mas vale reforçar com mais precisão: se você importar um pacote e não usar nenhum dos seus símbolos exportados no arquivo atual, o compilador recusa compilar. Isso não é um aviso — é um erro fatal.

go erros de importação 
package main

import (
    "fmt"
    "os"    // ERRO: importado e não usado
)

func main() {
    fmt.Println("ok")
    // os não é usado em lugar nenhum
}

// Erro: ./main.go:5:2: "os" imported and not used

Ordenação das importações

A convenção Go é organizar as importações em grupos separados por linha em branco, na seguinte ordem:

go ordenação convencional 
import (
    // 1. Pacotes da stdlib
    "fmt"
    "net/http"
    "os"

    // 2. Pacotes externos (third-party)
    "github.com/gorilla/mux"
    "go.uber.org/zap"

    // 3. Pacotes internos do próprio projeto
    "meu-projeto/internal/database"
    "meu-projeto/pkg/auth"
)

O gofmt ordena importações alfabeticamente dentro de cada grupo, mas não cria os grupos automaticamente. A ferramenta goimports faz ambas as coisas: organiza em grupos e adiciona/remove importações conforme necessário.

A função main e o ponto de entrada

Quando um programa Go é iniciado, o runtime busca exatamente uma função: func main() no package main. Ela é o ponto de entrada — a primeira função do seu código que executa.

Assinatura obrigatória

A função main tem uma assinatura fixa: não aceita parâmetros e não retorna valores. Isso é diferente de C, onde main pode receber argc e argv.

go assinatura correta e errada 
// ✓ Correto
func main() {
    // ...
}

// ✗ Errado — main não aceita parâmetros
func main(args []string) {
    // erro de compilação
}

// ✗ Errado — main não retorna valores
func main() int {
    return 0  // erro de compilação
}

Como acessar argumentos da linha de comando

Se main não recebe argumentos, como acessar o que o usuário passa na linha de comando? Via o pacote os:

go argumentos via os.Args 
package main

import (
    "fmt"
    "os"
)

func main() {
    // os.Args é um slice de strings
    // os.Args[0] = caminho do próprio executável
    // os.Args[1:] = argumentos passados pelo usuário
    args := os.Args

    fmt.Println("Programa:", args[0])

    if len(args) > 1 {
        fmt.Println("Primeiro argumento:", args[1])
    }
}

// Executando: ./programa olá mundo
// Saída:
// Programa: ./programa
// Primeiro argumento: olá

O que acontece antes da main

Existe algo que executa antes da main: as funções init(). Cada arquivo pode ter uma ou mais funções init(), que são chamadas automaticamente pelo runtime na ordem em que os pacotes são inicializados.

go ordem de execução 
package main

import "fmt"

func init() {
    fmt.Println("1. init() executou")
    // usado para: validar configurações, registrar drivers,
    // inicializar variáveis que exigem lógica complexa
}

func main() {
    fmt.Println("2. main() executou")
}

// Saída:
// 1. init() executou
// 2. main() executou

Código de saída do programa

Quando main retorna normalmente, o programa termina com código de saída 0 (sucesso). Para sair com outro código — indicando erro para o sistema operacional — use os.Exit():

go código de saída 
package main

import (
    "fmt"
    "os"
)

func main() {
    err := fazerAlgo()
    if err != nil {
        fmt.Fprintln(os.Stderr, "erro:", err)
        os.Exit(1)  // código não-zero = falha
    }
    // saída normal = código 0 (sucesso)
}
os.Exit() não executa defers
Uma pegadinha importante: chamar os.Exit() termina o programa imediatamente, sem executar as funções agendadas com defer. Estudaremos defer no Módulo 13. Por ora, saiba que os.Exit() deve ser usado com cuidado.

Arquivos .go: anatomia e organização

Um arquivo .go tem uma estrutura bem definida. Cada seção tem seu lugar e ordem obrigatória:

go anatomia completa de um arquivo .go 
// 1. Comentário de cabeçalho (opcional, mas recomendado)
// Package utils fornece funções auxiliares para o projeto.

// 2. Declaração de pacote (obrigatória, sempre primeira)
package utils

// 3. Importações (logo após a declaração de pacote)
import (
    "fmt"
    "strings"
)

// 4. Constantes no nível do pacote (opcional)
const MaxTamanho = 100

// 5. Variáveis no nível do pacote (opcional)
var prefixoPadrao = "INFO"

// 6. Tipos definidos (optional)
type Config struct {
    Nome  string
    Valor int
}

// 7. Funções (incluindo init, se houver)
func init() {
    // inicialização do pacote
}

func Formatar(s string) string {
    return strings.TrimSpace(s)
}

func Logar(msg string) {
    fmt.Printf("[%s] %s\n", prefixoPadrao, msg)
}

Um pacote, múltiplos arquivos

Um pacote pode e deve ser dividido em múltiplos arquivos quando crescer. O compilador une todos os arquivos do pacote antes de compilar — como se fossem um único arquivo. Por isso, funções declaradas em handlers.go podem chamar funções de utils.go sem nenhuma importação:

go pacote dividido em arquivos 
// arquivo: handlers.go
package main

func handleRequest() {
    resultado := processar()  // chama função de outro arquivo do mesmo pacote
    responder(resultado)
}

// arquivo: processamento.go
package main

func processar() string {
    return "dados processados"
}

// arquivo: resposta.go
package main

import "fmt"

func responder(s string) {
    fmt.Println(s)
}

// Todos no mesmo diretório, mesmo package main.
// O compilador junta tudo automaticamente.

Exportação: maiúscula vs minúscula

Go usa uma regra elegante e simples para controlar visibilidade: identificadores que começam com letra maiúscula são exportados (visíveis fora do pacote); identificadores com letra minúscula são privados ao pacote.

Não existe palavra-chave public ou private em Go. A própria capitalização do nome já diz tudo.

go exportado vs privado 
package matematica

// Exportados — visíveis fora do pacote
const Pi = 3.14159
func Somar(a, b int) int { return a + b }
type Calculadora struct { ... }

// Privados — visíveis apenas dentro do pacote
const precisao = 6
func validarEntrada(n int) bool { return n >= 0 }
type estadoInterno struct { ... }

// Uso em outro pacote:
// matematica.Somar(1, 2)     ✓
// matematica.validarEntrada(1) ✗ erro de compilação
Por que isso é elegante
A capitalização como mecanismo de visibilidade elimina a necessidade de palavras-chave extras, torna a intenção visível na leitura do código, e é verificada pelo compilador — não apenas por convenção. Ao ler código Go, você imediatamente sabe o que é público e o que é privado pela primeira letra.

Como o compilador lê o código

Entender o que o compilador Go faz — e na qual ordem — explica muitos comportamentos que de outra forma pareceriam arbitrários. E explica por que a compilação é tão rápida.

Ponto de partida: o grafo de dependências

O compilador Go começa lendo as declarações de import e constrói um grafo de dependências entre pacotes. Pacotes sem dependências são compilados primeiro; pacotes que dependem deles são compilados depois.

A regra crucial: Go não permite dependências circulares. Se o pacote A importa B, e B importa A, é um erro de compilação. Isso é proposital — dependências circulares são um sinal de arquitetura ruim e causam problemas reais em sistemas grandes.

bash dependência circular — erro 
# pacote A importa pacote B
# pacote B importa pacote A
# → erro: import cycle not allowed

Por que a compilação é tão rápida

O compilador de C/C++ precisa processar headers repetidamente para cada arquivo que os inclui. Go resolve isso de forma diferente: quando um pacote é compilado, ele exporta as informações necessárias para quem o importa em um formato binário otimizado.

Isso significa que ao compilar o pacote A que importa B, o compilador já tem tudo que precisa de B em formato pré-processado — sem reprocessar o código-fonte de B novamente. Cada pacote é compilado exatamente uma vez.

Ordem de declarações não importa

Diferente de C, onde você precisa declarar funções antes de usá-las, em Go a ordem de declarações dentro de um pacote não importa. O compilador faz duas passagens: primeiro coleta todas as declarações, depois verifica referências.

go ordem não importa 
package main

import "fmt"

func main() {
    // Usa saudacao() mesmo ela estando declarada abaixo — sem problema
    fmt.Println(saudacao("Go"))
}

// Declarada depois de main — totalmente válido
func saudacao(nome string) string {
    return "Olá, " + nome + "!"
}

Ponto e vírgula automático

Go não usa ponto e vírgula ao final das linhas no código-fonte — mas internamente, o compilador os insere automaticamente. A regra é simples: se a última token de uma linha for um identificador, literal, ou um dos tokens ), ], }, o compilador insere ; ao final.

Isso explica por que a chave de abertura de um bloco não pode ficar sozinha em uma linha — o compilador inseriria um ponto e vírgula antes dela:

go posição de chaves — obrigatória 
// ✓ Correto — chave na mesma linha
func main() {
    if true {
        fmt.Println("ok")
    }
}

// ✗ Errado — o compilador insere ; após main() e após true
func main()
{                        // erro: unexpected {
    if true
    {                    // erro: unexpected {
        fmt.Println("ok")
    }
}
Não existe debate de estilo em Go
Em linguagens como C e Java, há guerras intermináveis sobre onde colocar chaves. Em Go, o compilador força a chave na mesma linha — não há escolha. O gofmt também garante isso. Resultado: zero debate, 100% de uniformidade em todo código Go do mundo.

Comentários

Go suporta dois estilos de comentário, idênticos ao C e à maioria das linguagens modernas:

go comentários 
// Comentário de linha — do // até o fim da linha

/*
   Comentário de bloco — pode ocupar
   múltiplas linhas
*/

// Comentários de documentação ficam imediatamente
// antes da declaração que documentam, sem linha em branco:

// Somar retorna a soma de dois inteiros.
// Ambos os parâmetros podem ser negativos.
func Somar(a, b int) int {
    return a + b
}

Comentários de documentação que precedem declarações exportadas são exibidos pelo comando go doc e na documentação online do pacote. Essa é a forma oficial de documentar APIs em Go — sem ferramentas extras, sem anotações especiais.

Quiz · Questão 1 de 3 Verificação de entendimento

Um diretório contém três arquivos: main.go, handlers.go e utils.go. Qual afirmação sobre as declarações de pacote desses arquivos é correta?

✓ Correto! Todos os arquivos .go de um diretório devem declarar o mesmo pacote. O compilador une todos eles antes de compilar — funções de handlers.go enxergam funções de utils.go sem importação, pois pertencem ao mesmo pacote.
Quiz · Questão 2 de 3 Verificação de entendimento

Dado o seguinte código no pacote matematica, quais identificadores podem ser acessados de fora do pacote?

go 
package matematica

const pi = 3.14159
const Euler = 2.71828
func calcular(n int) int { return n * 2 }
func Dobrar(n int) int { return n * 2 }
type resultado struct { valor int }
type Resultado struct { Valor int }
✓ Correto! Em Go, letra maiúscula = exportado (público); letra minúscula = privado ao pacote. Euler, Dobrar e Resultado são acessíveis de fora. pi, calcular e resultado são privados. Não existe palavra-chave public ou private.
Quiz · Questão 3 de 3 Verificação de entendimento

Por que o compilador Go exige que a chave de abertura { fique na mesma linha da declaração — e não na linha seguinte como é comum em C e Java?

✓ Correto! O compilador Go insere ; automaticamente ao final de linhas que terminam com identificadores, literais ou os tokens ), ], }. Se você escrever func main() e deixar { na próxima linha, o compilador insere ; após o ), tornando a chave inesperada — erro de sintaxe.
Exercício 1 — Identificação de erro Aplicação prática

O código abaixo não compila. Qual é a causa do erro?

go main.go 
package main

import "fmt"

func main() {
    fmt.Println(mensagem())
}

// arquivo: mensagens.go — mesmo diretório
package util

func mensagem() string {
    return "olá"
}
✓ Exato! Dois arquivos no mesmo diretório com nomes de pacote diferentes é um erro de compilação. A solução é mudar package util para package main em mensagens.go. A função mensagem() ser minúscula não é problema aqui — ela está no mesmo pacote, então é acessível.
Exercício 2 — Dependência circular Aplicação prática

Uma equipe estruturou seus pacotes da seguinte forma: auth importa database, database importa config, e config importa auth. O que acontece ao tentar compilar?

✓ Correto! Go detecta e recusa dependências circulares em tempo de compilação. A solução arquitetural é extrair as dependências compartilhadas para um terceiro pacote sem dependências próprias — por exemplo, mover para config apenas o que não depende de auth, ou criar um pacote types com interfaces que todos importam sem criar ciclo.
