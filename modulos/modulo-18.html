error como tipo

Em Go, erros não são exceções lançadas e capturadas — são valores retornados como qualquer outro. O tipo error é uma interface da stdlib com um único método:

go a interface error 
// Definição na stdlib — é tudo que existe
type error interface {
    Error() string
}

Por ser uma interface, qualquer tipo que implemente Error() string é um error válido. A convenção em Go é retornar o erro como último valor da função e verificá-lo imediatamente após a chamada:

go padrão idiomático 
// Assinatura típica: retorno útil + error
func lerArquivo(nome string) ([]byte, error) {
    f, err := os.Open(nome)
    if err != nil {
        return nil, err  // propaga o erro; retorno útil é nil
    }
    defer f.Close()

    return io.ReadAll(f)
}

// Chamada: verificar antes de usar o resultado
dados, err := lerArquivo("config.json")
if err != nil {
    log.Fatal(err)
}
fmt.Println(len(dados))  // seguro: só chega aqui se err == nil

Quando não há erro, a função retorna nil como error — nil é o zero value de qualquer interface e significa "sem erro". A verificação if err != nil é o padrão universal em Go.

Por que não exceções?
Em linguagens com exceções, um erro pode "pular" vários níveis do stack antes de ser tratado — ou nunca ser tratado. Em Go, o erro é um valor explícito: o compilador garante que você viu o retorno. Você pode ignorá-lo com _, mas é uma escolha consciente — não acidental.

errors.New e fmt.Errorf

A stdlib oferece duas formas principais de criar erros novos. Escolher entre elas é uma decisão de design, não de preferência:

go errors.New — erro simples e estático 
import "errors"

var ErrNaoEncontrado = errors.New("recurso não encontrado")
var ErrPermissao     = errors.New("permissão negada")

func buscar(id int) (*Usuario, error) {
    u, ok := db[id]
    if !ok {
        return nil, ErrNaoEncontrado  // retorna a sentinel var
    }
    return u, nil
}

// Comparação com == (ou errors.Is — veremos no tópico 4)
u, err := buscar(42)
if err == ErrNaoEncontrado {
    // trata ausência de recurso
}

errors.New cria um erro opaco — uma mensagem fixa sem contexto dinâmico. Quando você precisa incluir valores (o ID que causou o erro, o nome do arquivo), use fmt.Errorf:

go fmt.Errorf — erro com contexto 
import "fmt"

func buscar(id int) (*Usuario, error) {
    u, ok := db[id]
    if !ok {
        return nil, fmt.Errorf("buscar: usuário %d não encontrado", id)
    }
    return u, nil
}

// Cada chamada gera uma string diferente:
// "buscar: usuário 42 não encontrado"
// "buscar: usuário 99 não encontrado"
Função Use quando
errors.New Erro sentinela — quem chama vai comparar com == ou errors.Is
fmt.Errorf Erro com dados dinâmicos — mensagem varia por chamada
Erros sentinela: declare como variáveis de pacote
Por convenção, erros sentinela começam com Err e ficam no nível de pacote (não dentro de funções). Isso permite que quem usa seu pacote importe e compare contra eles. Nunca use errors.New dentro de uma função se precisar comparar o erro depois — cada chamada cria um valor distinto na memória.

Erros personalizados

Quando uma string de erro não é suficiente — quando quem chama precisa extrair dados estruturados do erro (código HTTP, campo inválido, linha do arquivo) — você cria um tipo próprio que implementa a interface error:

go tipo de erro personalizado 
// Erro com campos estruturados
type ErroValidacao struct {
    Campo   string
    Valor   any
    Motivo  string
}

// Implementa a interface error
func (e *ErroValidacao) Error() string {
    return fmt.Sprintf("validação falhou: campo %q, valor %v — %s",
        e.Campo, e.Valor, e.Motivo)
}

func validarIdade(idade int) error {
    if idade < 0 {
        return &ErroValidacao{
            Campo:  "idade",
            Valor:  idade,
            Motivo: "não pode ser negativa",
        }
    }
    if idade > 150 {
        return &ErroValidacao{
            Campo:  "idade",
            Valor:  idade,
            Motivo: "valor implausível",
        }
    }
    return nil
}

Quem recebe o erro pode extrair os campos usando errors.As (que veremos no tópico 4) — sem precisar fazer parsing da string de mensagem:

go extraindo dados do erro 
err := validarIdade(-5)

var ev *ErroValidacao
if errors.As(err, &ev) {
    fmt.Printf("campo com problema: %s\n", ev.Campo)
    fmt.Printf("valor recebido: %v\n", ev.Valor)
    // resposta HTTP 422 com detalhe do campo, por exemplo
}

Receiver por ponteiro é obrigatório aqui

Note que o receiver de Error() é *ErroValidacao (ponteiro). Se você implementar com receiver por valor (ErroValidacao), o tipo *ErroValidacao também satisfaz a interface — mas o contrário não vale. Use ponteiro como receiver para erros personalizados para evitar cópias e problemas com errors.As.

Quando criar um tipo de erro
Crie um tipo de erro personalizado quando quem chama sua função precisar inspecionar campos do erro programaticamente — não apenas exibir a mensagem. Se a mensagem de texto é tudo que será usado, fmt.Errorf é suficiente.

Wrapping de erros com %w

Ao propagar um erro entre camadas do programa, é bom adicionar contexto sem perder o erro original. O verbo %w do fmt.Errorf (introduzido em Go 1.13) faz exatamente isso: cria um novo erro que encapsula o original, formando uma cadeia (error chain):

go wrapping com %w 
var ErrNaoAutorizado = errors.New("não autorizado")

func buscarPerfil(userID int) (*Perfil, error) {
    perfil, err := db.Buscar(userID)
    if err != nil {
        // %w encapsula err dentro do novo erro
        return nil, fmt.Errorf("buscarPerfil(%d): %w", userID, err)
    }
    return perfil, nil
}

func handleRequest(w http.ResponseWriter, r *http.Request) {
    perfil, err := buscarPerfil(42)
    if err != nil {
        // %w preserva a cadeia — o erro original continua acessível
        return nil, fmt.Errorf("handleRequest: %w", err)
    }
    // ...
}

A cadeia resultante seria algo como:
"handleRequest: buscarPerfil(42): não autorizado"

%w vs %v — a diferença crítica

go 
var original = errors.New("disco cheio")

// %v — apenas formata a mensagem, perde o erro original
comV := fmt.Errorf("salvar: %v", original)
fmt.Println(errors.Is(comV, original))  // false — cadeia quebrada

// %w — encapsula o erro, preserva a cadeia
comW := fmt.Errorf("salvar: %w", original)
fmt.Println(errors.Is(comW, original))  // true — cadeia intacta

O verbo %w faz com que o novo erro implemente o método Unwrap() error, que retorna o erro encapsulado. errors.Is e errors.As percorrem essa cadeia automaticamente.

Use %w com intenção — não sempre
Ao usar %w, você está expondo o erro interno como parte da API pública da sua função. Quem chama poderá inspecionar a cadeia com errors.Is. Se o erro interno é um detalhe de implementação que pode mudar, use %v para não vazar a dependência.

errors.Is e errors.As

Com erros encapsulados por %w, a comparação direta com == não funciona mais — o erro original está embrulhado dentro de outro. As funções errors.Is e errors.As percorrem a cadeia automaticamente:

errors.Is — verifica identidade

go errors.Is percorre a cadeia 
var ErrNaoEncontrado = errors.New("não encontrado")

// Função que encapsula o erro
func buscar(id int) error {
    return fmt.Errorf("buscar(%d): %w", id, ErrNaoEncontrado)
}

err := buscar(42)

// == não funciona com erros encapsulados
fmt.Println(err == ErrNaoEncontrado)          // false

// errors.Is percorre a cadeia
fmt.Println(errors.Is(err, ErrNaoEncontrado)) // true

// Uso em ramificação de lógica
if errors.Is(err, ErrNaoEncontrado) {
    // retornar 404, tentar criar o recurso, etc.
} else if errors.Is(err, ErrNaoAutorizado) {
    // retornar 401
}

errors.As — extrai o tipo

Enquanto errors.Is compara por identidade (o mesmo valor), errors.As procura um tipo específico na cadeia e atribui a variável alvo — equivalente a um type assertion que percorre o wrapping:

go errors.As extrai dados estruturados 
type ErroHTTP struct {
    Codigo int
    Metodo string
}

func (e *ErroHTTP) Error() string {
    return fmt.Sprintf("HTTP %d em %s", e.Codigo, e.Metodo)
}

func fazerRequisicao() error {
    err := &ErroHTTP{Codigo: 503, Metodo: "GET"}
    return fmt.Errorf("fazerRequisicao: %w", err)
}

err := fazerRequisicao()

var httpErr *ErroHTTP
if errors.As(err, &httpErr) {
    // httpErr agora está preenchido com os campos do ErroHTTP
    fmt.Printf("falha HTTP %d — retry em 5s\n", httpErr.Codigo)
}
errors.Is vs errors.As — resumo rápido
Use errors.Is para verificar se um erro é um valor específico (erros sentinela como io.EOF, sql.ErrNoRows). Use errors.As para verificar se um erro é de um tipo específico e extrair seus campos.

Filosofia: erros explícitos vs exceções

A abordagem de Go para erros é uma escolha deliberada de design — não uma limitação. Entender o raciocínio por trás dela ajuda a escrever código Go idiomático em vez de lutar contra a linguagem.

O problema com exceções

Em linguagens como Java ou Python, exceções criam caminhos de saída invisíveis. Uma função que "não lança nada" pode na prática falhar em qualquer linha que chame outra função. O código parece linear mas não é — o tratamento de erros fica disperso em blocos try/catch que muitas vezes ficam genéricos demais ou são simplesmente omitidos.

Erros como valores: o que muda

go legibilidade do fluxo de erros 
// Em Go, todo ponto de falha é explícito no código
func processarPedido(id int) error {
    pedido, err := buscarPedido(id)
    if err != nil {
        return fmt.Errorf("processarPedido: %w", err)
    }

    if err := validarEstoque(pedido); err != nil {
        return fmt.Errorf("processarPedido: %w", err)
    }

    if err := cobrarCartao(pedido); err != nil {
        return fmt.Errorf("processarPedido: %w", err)
    }

    return enviarConfirmacao(pedido)
    // Cada linha que pode falhar está visível.
    // Não há surpresas de stack unwinding silencioso.
}

Padrões comuns no código Go real

go padrões idiomáticos 
// 1. Early return — sem else após o if de erro
func abrirConexao(dsn string) (*sql.DB, error) {
    db, err := sql.Open("postgres", dsn)
    if err != nil {
        return nil, fmt.Errorf("abrirConexao: %w", err)
    }
    // sem else — o código "feliz" continua no nível raiz
    return db, nil
}

// 2. Adicionar contexto em cada camada
func (s *Service) CriarUsuario(nome string) error {
    if err := s.db.Inserir(nome); err != nil {
        return fmt.Errorf("Service.CriarUsuario %q: %w", nome, err)
    }
    return nil
}

// 3. Nunca silenciar erros sem razão explícita
f, _ := os.Open("config.json")  // ✗ erro silenciado — evitar
f, err := os.Open("config.json")
if err != nil {
    // ✓ tratar ou propagar — nunca ignorar acidentalmente
    return fmt.Errorf("config: %w", err)
}
Exceções (outras linguagens) Erros como valores (Go)
Caminhos de falha implícitos Caminhos de falha explícitos no código
Fácil de esquecer de tratar Difícil de ignorar acidentalmente
Stack unwinding automático Propagação manual, rastreável
Difícil de saber o que uma função pode lançar A assinatura da função documenta falhas possíveis
O "problema" do if err != nil
Quem vem de outras linguagens frequentemente reclama da verbosidade dos checks de erro em Go. Mas isso é o ponto: o código verbose é uma escolha explícita de visibilidade. Cada if err != nil é uma documentação inline de que aquela operação pode falhar — e de como a falha é tratada. Esse custo visual compra clareza de comportamento.

Quiz · Questão 2 de 3 Verificação de entendimento

O código abaixo tem um bug sutil. Qual é ele?

go 
func buscar(id int) (*Item, error) {
    if id <= 0 {
        return nil, errors.New("id inválido")
    }
    // ...
}

// Em outro lugar:
err := buscar(-1)
if err == errors.New("id inválido") {  // verificação
    fmt.Println("id era inválido")
}
✓ Correto! errors.New retorna um ponteiro para uma struct interna. Cada chamada aloca um ponteiro novo — mesmo que a string seja idêntica, os endereços são diferentes, portanto == sempre retorna false. A correção é declarar um erro sentinela no nível de pacote: var ErrIDInvalido = errors.New("id inválido") e comparar com errors.Is(err, ErrIDInvalido).

Exercício 1 — Wrapping e inspeção de cadeia Aplicação prática

Uma função de repositório retorna sql.ErrNoRows encapsulado em três camadas de contexto via %w. Na camada HTTP, você precisa retornar 404 quando o recurso não existe. Qual código faz isso corretamente?

// Repositório
func (r *Repo) BuscarUsuario(id int) (*Usuario, error) {

    if err != nil {
        return nil, fmt.Errorf("Repo.BuscarUsuario: %w", err)
    }
    return u, nil
}

// Serviço
func (s *Service) Usuario(id int) (*Usuario, error) {
    u, err := s.repo.BuscarUsuario(id)
    if err != nil {
        return nil, fmt.Errorf("Service.Usuario: %w", err)
    }
    return u, nil
}

// Handler HTTP — como detectar o 404?
func (h *Handler) GetUsuario(w http.ResponseWriter, r *http.Request) {

✓ Correto! errors.Is percorre a cadeia de Unwrap() automaticamente — não importa quantas camadas de fmt.Errorf("%w", ...) existam. Comparar com == falharia porque o valor retornado é um *fmt.wrapError, não o sql.ErrNoRows diretamente. Comparar strings de mensagem é um anti-padrão frágil — a mensagem pode mudar entre versões da stdlib.
Exercício 2 — Tipo de erro personalizado Aplicação prática

Você está construindo uma API de validação. A função validar deve retornar um erro que inclua qual campo falhou e por quê — para que o handler HTTP possa montar uma resposta JSON com detalhes. Qual design resolve isso corretamente?

✓ Correto! Tipo personalizado + errors.As é o padrão idiomático Go para erros estruturados. Fazer parse de strings é frágil e acopla código a detalhes de mensagem. Usar panic/recover para controle de fluxo normal é anti-padrão. Retornar múltiplos valores extras funciona, mas não compõe bem com camadas de wrapping — quem usa só vê o error após propagação. O tipo personalizado permanece inspecionável através de qualquer número de camadas de %w.
