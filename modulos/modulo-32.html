O que é reflection e por que existe

Go é uma linguagem estaticamente tipada: o compilador conhece o tipo de cada variável em tempo de compilação. Isso torna o código previsível e seguro — mas cria um problema: como escrever código que opere sobre qualquer tipo, sem conhecê-lo com antecedência?

É exatamente essa a função de reflection: inspecionar e manipular tipos e valores em tempo de execução. O pacote reflect da stdlib expõe uma API que permite descobrir o tipo de um valor, ler e escrever campos de structs, chamar métodos e funções — tudo dinamicamente, sem que o compilador precise saber o tipo em questão.

Isso é o que possibilita pacotes como encoding/json, database/sql, text/template e frameworks de teste como testify: eles recebem any e precisam entender a estrutura interna do valor para serializar, mapear ou comparar.

Reflection tem custo real
Operações via reflect são significativamente mais lentas que código estático — 5x a 100x dependendo da operação. O compilador não consegue otimizar código reflexivo da mesma forma. Use reflection apenas quando não há alternativa estática viável — jamais no caminho quente de sistemas de alta performance.

Os dois tipos centrais: reflect.Type e reflect.Value

Toda a API de reflection gira em torno de dois tipos:

Tipo Obtido via Representa
reflect.Type reflect.TypeOf(x) A descrição estática do tipo (nome, campos, métodos)
reflect.Value reflect.ValueOf(x) O container que envolve o valor em tempo de execução
go TypeOf vs ValueOf 
import "reflect"

x := 3.14

t := reflect.TypeOf(x)
fmt.Println(t)         // float64
fmt.Println(t.Kind())  // float64  (Kind é mais granular que o nome do tipo)

v := reflect.ValueOf(x)
fmt.Println(v)         // 3.14
fmt.Println(v.Type())  // float64
fmt.Println(v.Float()) // 3.14  (extrai o valor concreto como float64)

Type descreve o tipo em si — seus campos, métodos, nome, pacote. Value carrega o valor concreto e permite ler ou escrever dados. Na prática, você usará os dois em conjunto.

Kind vs Type
Kind é a categoria primitiva do tipo: Int, Struct, Slice, Ptr, Func etc. Type é o tipo nomeado: http.Request, time.Duration, MyStruct. Um time.Duration tem Kind Int64. Ao escrever código reflexivo genérico, trate o Kind — não o Type.

Inspecionando structs com reflect

O caso de uso mais frequente de reflection em código real é inspecionar structs: descobrir seus campos, tipos, valores e tags em tempo de execução. É assim que encoding/json sabe quais campos de uma struct serializar e com qual nome JSON.

go inspecionar campos de struct 
type Produto struct {
    Nome  string  `json:"nome" validate:"required"`
    Preco float64 `json:"preco" validate:"min=0"`
    Ativo bool    `json:"ativo"`
}

func inspecionarStruct(v any) {
    t := reflect.TypeOf(v)
    val := reflect.ValueOf(v)

    // Se for ponteiro, dereferenciar
    if t.Kind() == reflect.Ptr {
        t = t.Elem()
        val = val.Elem()
    }

    if t.Kind() != reflect.Struct {
        fmt.Println("não é uma struct")
        return
    }

    fmt.Printf("Struct: %s (%d campos)\n", t.Name(), t.NumField())

    for i := 0; i < t.NumField(); i++ {
        field := t.Field(i)        // reflect.StructField — metadados estáticos
        value := val.Field(i)     // reflect.Value — valor em runtime

        jsonTag := field.Tag.Get("json")
        validateTag := field.Tag.Get("validate")

        fmt.Printf("  [%d] %s %s = %v  json:%q validate:%q\n",
            i, field.Name, field.Type, value.Interface(),
            jsonTag, validateTag)
    }
}

p := Produto{Nome: "Teclado", Preco: 299.90, Ativo: true}
inspecionarStruct(p)

// Saída:
// Struct: Produto (3 campos)
//   [0] Nome string = Teclado  json:"nome" validate:"required"
//   [1] Preco float64 = 299.9  json:"preco" validate:"min=0"
//   [2] Ativo bool = true      json:"ativo" validate:""

Tags de struct como metadados extensíveis

reflect.StructTag é apenas uma string com um formato convencional: chave:"valor". O método Get("chave") extrai o valor para uma chave específica. Isso é a base de todo o ecossistema de tags em Go — não há mágica do compilador, apenas reflection em runtime.

go validador simples via tags 
// Mini-validador: usa a tag `required` para checar campos string vazios
func validar(v any) []string {
    var erros []string

    t := reflect.TypeOf(v)
    val := reflect.ValueOf(v)

    if t.Kind() == reflect.Ptr {
        t, val = t.Elem(), val.Elem()
    }

    for i := 0; i < t.NumField(); i++ {
        field := t.Field(i)
        value := val.Field(i)

        tag := field.Tag.Get("validate")
        if tag == "required" && field.Type.Kind() == reflect.String {
            if value.String() == "" {
                erros = append(erros, field.Name+" é obrigatório")
            }
        }
    }
    return erros
}

p := Produto{Preco: 10.0}
fmt.Println(validar(p))  // [Nome é obrigatório]
Campos não exportados são inacessíveis
val.Field(i).Interface() entra em panic se o campo for não exportado (letra minúscula). Antes de chamar Interface(), verifique field.IsExported() (Go 1.17+) ou field.PkgPath == "" em versões anteriores. Campos não exportados existem para encapsulamento — reflection não é uma porta dos fundos para ignorar isso.

Modificando valores com reflect

Ler valores via reflection é direto. Modificá-los exige um passo extra: o valor precisa ser endereçável (addressable). Um valor só é endereçável quando passado como ponteiro — do contrário, você estaria modificando uma cópia dentro do reflect.Value, o que não teria efeito no valor original.

go por que ponteiro é obrigatório 
x := 42

// Tentativa com valor — entra em panic
v := reflect.ValueOf(x)
// v.SetInt(100)  // panic: reflect: reflect.Value.SetInt using unaddressable value

// Correto: passar o ponteiro, depois Elem() para chegar ao valor subjacente
v = reflect.ValueOf(&x).Elem()
fmt.Println(v.CanSet())  // true
v.SetInt(100)
fmt.Println(x)           // 100 — o valor original foi modificado

Modificando campos de struct

go set de campos via reflect 
type Config struct {
    Host    string
    Port    int
    Debug   bool
}

// Preenche uma struct a partir de um map[string]any — padrão usado em ORMs e deserializadores
func preencherStruct(dst any, dados map[string]any) error {
    val := reflect.ValueOf(dst)
    if val.Kind() != reflect.Ptr || val.Elem().Kind() != reflect.Struct {
        return fmt.Errorf("dst deve ser um ponteiro para struct")
    }

    val = val.Elem()
    typ := val.Type()

    for i := 0; i < typ.NumField(); i++ {
        field := typ.Field(i)
        if !field.IsExported() {
            continue
        }

        dado, ok := dados[field.Name]
        if !ok {
            continue
        }

        fieldVal := val.Field(i)
        srcVal := reflect.ValueOf(dado)

        // Apenas atribui se os tipos forem compatíveis
        if srcVal.Type().AssignableTo(field.Type) {
            fieldVal.Set(srcVal)
        }
    }
    return nil
}

cfg := Config{}
preencherStruct(&cfg, map[string]any{
    "Host":  "localhost",
    "Port":  5432,
    "Debug": true,
})
fmt.Printf("%+v\n", cfg)
// {Host:localhost Port:5432 Debug:true}

CanSet vs CanAddr

CanAddr() indica se o valor tem endereço de memória (foi derivado de um ponteiro). CanSet() é mais restrito: exige endereçabilidade e que o campo seja exportado. Um campo não exportado de uma struct é endereçável mas não settável — a distinção existe para preservar encapsulamento mesmo sob reflection.

go 
type Exemplo struct {
    Exportado    string
    naoExportado string
}

e := Exemplo{Exportado: "a", naoExportado: "b"}
val := reflect.ValueOf(&e).Elem()

fmt.Println(val.Field(0).CanSet())  // true  — Exportado
fmt.Println(val.Field(1).CanSet())  // false — naoExportado
fmt.Println(val.Field(1).CanAddr()) // true  — endereçável, mas não settável

Chamando funções e métodos dinamicamente

Além de ler e escrever dados, reflection permite chamar funções e métodos pelo nome em tempo de execução. A API central é Value.Call([]reflect.Value) — que recebe e retorna slices de reflect.Value, um por argumento/retorno.

go chamar método por nome 
type Calculadora struct{}

func (c Calculadora) Somar(a, b int) int     { return a + b }
func (c Calculadora) Multiplicar(a, b int) int { return a * b }

func chamarMetodo(obj any, nome string, args ...any) ([]reflect.Value, error) {
    val := reflect.ValueOf(obj)
    metodo := val.MethodByName(nome)

    if !metodo.IsValid() {
        return nil, fmt.Errorf("método %q não encontrado", nome)
    }

    // Converte args para []reflect.Value
    in := make([]reflect.Value, len(args))
    for i, arg := range args {
        in[i] = reflect.ValueOf(arg)
    }

    return metodo.Call(in), nil
}

calc := Calculadora{}

resultados, _ := chamarMetodo(calc, "Somar", 10, 5)
fmt.Println(resultados[0].Int())  // 15

resultados, _ = chamarMetodo(calc, "Multiplicar", 4, 7)
fmt.Println(resultados[0].Int())  // 28

_, err := chamarMetodo(calc, "Dividir", 10, 2)
fmt.Println(err)  // método "Dividir" não encontrado

Inspecionando a assinatura antes de chamar

Chamar um método com número ou tipo de argumentos errados causa panic. Em código de produção que usa chamadas dinâmicas, sempre valide a assinatura antes de chamar:

go 
func chamarComValidacao(obj any, nome string, args []any) ([]reflect.Value, error) {
    val := reflect.ValueOf(obj)
    metodo := val.MethodByName(nome)

    if !metodo.IsValid() {
        return nil, fmt.Errorf("método %q não existe", nome)
    }

    mt := metodo.Type()

    // Verifica aridade (exceto variádicosms)
    if !mt.IsVariadic() && mt.NumIn() != len(args) {
        return nil, fmt.Errorf("método %q espera %d args, recebeu %d",
            nome, mt.NumIn(), len(args))
    }

    in := make([]reflect.Value, len(args))
    for i, arg := range args {
        v := reflect.ValueOf(arg)
        expected := mt.In(i)
        if !v.Type().AssignableTo(expected) {
            return nil, fmt.Errorf("arg %d: esperado %s, recebeu %s",
                i, expected, v.Type())
        }
        in[i] = v
    }

    return metodo.Call(in), nil
}
Onde isso aparece na stdlib
text/template e html/template chamam funções e métodos de structs passadas como dados do template exatamente assim — via Value.Call() em runtime. O pacote testing usa reflection para executar funções cujo nome começa com Test, Bench ou Fuzz.

Quando usar (e quando não usar) reflection

Rob Pike, um dos criadores de Go, escreveu três leis de reflection. A terceira é a mais importante na prática: "Reflection is fragile." Código reflexivo não é verificado pelo compilador — erros de tipo, campos faltando, métodos com nome errado: tudo explode em runtime. Isso inverte a garantia central que faz Go atraente.

Use reflection quando... Prefira alternativa quando...
Escrevendo serialização/deserialização genérica (JSON, YAML, BSON) Os tipos são conhecidos em tempo de compilação — use type switch ou interfaces
Implementando frameworks que precisam operar sobre tipos arbitrários de usuários Os tipos têm estrutura comum — defina uma interface explícita
Código de teste que compara structs arbitrárias (reflect.DeepEqual) Generics (Go 1.18+) resolvem o problema com verificação estática
Injeção de dependência automática via tags (como GORM, Beego) O código está no caminho crítico de performance — o custo é proibitivo

reflect.DeepEqual — o caso de uso mais comum

O uso mais frequente de reflection em código de aplicação (não de framework) é via reflect.DeepEqual — que compara dois valores recursivamente, independente de tipo. É o coração do assert.Equal do testify:

go 
// DeepEqual compara estruturas aninhadas recursivamente
a := []map[string]int{{"x": 1}, {"y": 2}}
b := []map[string]int{{"x": 1}, {"y": 2}}
c := []map[string]int{{"x": 1}, {"y": 99}}

fmt.Println(reflect.DeepEqual(a, b))  // true
fmt.Println(reflect.DeepEqual(a, c))  // false

// Cuidado: nil slice != empty slice para DeepEqual
var s1 []int
s2 := []int{}
fmt.Println(reflect.DeepEqual(s1, s2))  // false — nil != []

Generics como alternativa moderna

Com generics (Go 1.18+), parte dos casos que antes exigiam reflection podem ser resolvidos de forma estática — com verificação de tipo em compilação e sem custo de runtime:

go reflect vs generics 
// Antes: reflection para encontrar o máximo de qualquer slice numérico
func maxReflect(slice any) any {
    val := reflect.ValueOf(slice)
    if val.Kind() != reflect.Slice || val.Len() == 0 {
        return nil
    }
    max := val.Index(0)
    for i := 1; i < val.Len(); i++ {
        cur := val.Index(i)
        // Comparação reflexiva — frágil, sem checagem de tipo
        if cur.Float() > max.Float() {
            max = cur
        }
    }
    return max.Interface()
}

// Depois: genérico — verificado pelo compilador, sem custo de runtime
func maxGenerico[T int | int64 | float64](slice []T) T {
    m := slice[0]
    for _, v := range slice[1:] {
        if v > m {
            m = v
        }
    }
    return m
}

// Uso — tipagem verificada em compilação
fmt.Println(maxGenerico([]int{3, 1, 4, 1, 5, 9}))      // 9
fmt.Println(maxGenerico([]float64{1.1, 2.2, 0.5}))      // 2.2
As três leis de reflection (Rob Pike)
1. Reflection vai de interface value para reflect object.
2. Reflection vai de reflect object para interface value.
3. Para modificar um reflect object, o value deve ser settável.

A regra implícita não escrita é a quarta: se você não consegue fazer sem reflection, pergunte primeiro se a arquitetura não está errada. A maioria dos usos de reflection em código de aplicação pode ser eliminada com interfaces bem definidas ou generics.

Qual é o output do código abaixo?

go 
type Celsius float64

c := Celsius(36.6)
t := reflect.TypeOf(c)

fmt.Println(t.Name())
fmt.Println(t.Kind())
✓ Correto! Type.Name() retorna o nome do tipo como declarado — "Celsius". Type.Kind() retorna a categoria primitiva subjacente — float64, porque Celsius é definido como float64. Essa distinção é fundamental: ao escrever código reflexivo genérico, trate o Kind (para saber como operar) e consulte o Name apenas quando precisar identificar um tipo específico.
Quiz · Questão 2 de 3 Verificação de entendimento

O código abaixo compila mas entra em panic em runtime. Qual é a causa?

go 
type Ponto struct {
    X, Y int
}

func dobrar(v any) {
    val := reflect.ValueOf(v)
    val.FieldByName("X").SetInt(val.FieldByName("X").Int() * 2)
    val.FieldByName("Y").SetInt(val.FieldByName("Y").Int() * 2)
}

func main() {
    p := Ponto{X: 3, Y: 4}
    dobrar(p)
    fmt.Println(p)
}
✓ Correto! A causa é a falta de endereçabilidade. Quando dobrar(p) é chamada, p é copiado para o parâmetro v any. O reflect.ValueOf(v) encapsula essa cópia — que não tem endereço de memória estável, logo não é settável. A correção é dobrar(&p) e dentro da função: val := reflect.ValueOf(v).Elem(). Elem() derreferencia o ponteiro e retorna um Value com CanSet() == true.
Quiz · Questão 3 de 3 Verificação de entendimento

Qual é o output?

go 
type Resp struct {
    Items []string
    Total int
}

a := Resp{Items: nil,      Total: 0}
b := Resp{Items: []string{}, Total: 0}
c := Resp{Items: nil,      Total: 0}

fmt.Println(reflect.DeepEqual(a, b))
fmt.Println(reflect.DeepEqual(a, c))
✓ Correto! reflect.DeepEqual distingue nil de slice vazio ([]string{}). Internamente, um slice nil tem ponteiro nil enquanto um slice vazio tem um ponteiro válido para zero bytes. Por isso DeepEqual(a, b) é false — a.Items é nil, b.Items não é. DeepEqual(a, c) é true porque ambos têm Items == nil e Total == 0. Esse comportamento é uma fonte real de bugs em testes onde JSON unmarshaling produz []string{} e o esperado tem nil.
Exercício 1 — Bug em deserializador reflexivo Aplicação prática

Um deserializador genérico percorre os campos de uma struct via reflection e preenche seus valores a partir de um map[string]any. O código abaixo tem um bug sutil que causa panic em produção quando a struct tem campos não exportados. Qual é a correção correta?

go 
func deserializar(dst any, dados map[string]any) {
    val := reflect.ValueOf(dst).Elem()
    typ := val.Type()

    for i := 0; i < typ.NumField(); i++ {
        field := typ.Field(i)
        dado, ok := dados[field.Name]
        if !ok {
            continue
        }
        // BUG: panic se field for não exportado
        val.Field(i).Set(reflect.ValueOf(dado))
    }
}
✓ Correto! A guarda correta é field.IsExported() (disponível desde Go 1.17; equivale a checar field.PkgPath == "" em versões anteriores). Campos não exportados são endereçáveis (CanAddr() pode ser true), mas não são settáveis (CanSet() é sempre false) — por isso a opção D está errada. Usar recover() funcionaria, mas é uma má prática: oculta bugs reais e tem custo de performance. A solução correta é verificar explicitamente antes de tentar o Set.
Exercício 2 — Reflection vs interface Aplicação prática

Um colega implementou uma função de logging que usa reflection para imprimir o nome e o valor de cada campo de qualquer struct recebida como any. Você precisa adicionar suporte a um novo tipo Conexao que tem um campo senha string (não exportado por segurança) e um campo URL string. Qual abordagem é mais robusta?

✓ Correto! Esta é a solução mais robusta porque aplica o princípio Go corretamente: quando um tipo precisa de representação personalizada, ele implementa uma interface — não força o chamador a tratar seu caso especial. O logger faz if s, ok := v.(fmt.Stringer); ok { use s.String() } antes de cair no caminho reflexivo genérico. A opção B é segura quanto ao vazamento de senha, mas frágil: qualquer campo não exportado futuro também seria omitido silenciosamente, mesmo que fosse desejável logá-lo. A opção D funciona mas é verbosa e quebra a encapsulação — dois tipos para representar a mesma entidade. A opção A exporta dados sensíveis, o que é uma decisão de design ruim independente da tag.
