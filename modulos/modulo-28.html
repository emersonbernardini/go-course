Servidor HTTP

O pacote net/http da stdlib de Go é capaz de construir servidores HTTP prontos para produção — sem nenhuma dependência externa. Ao contrário de Python ou Node, o servidor de Go não é apenas para desenvolvimento: ele lida com multiplexação de conexões, keep-alive e goroutines por requisição nativamente.

O servidor mais simples possível

go servidor mínimo 
package main

import (
    "fmt"
    "net/http"
)

func main() {
    http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
        fmt.Fprintf(w, "olá, %s!", r.URL.Path[1:])
    })

    // ListenAndServe bloqueia e serve até erro fatal
    if err := http.ListenAndServe(":8080", nil); err != nil {
        log.Fatal(err)
    }
}

http.ListenAndServe(addr, handler) aceita dois argumentos: o endereço a escutar e um http.Handler. Quando o segundo argumento é nil, usa o DefaultServeMux — o roteador global padrão, no qual http.HandleFunc registra rotas.

ServeMux — roteador explícito

O DefaultServeMux é conveniente para exemplos, mas em código de produção você usa um ServeMux próprio. Isso evita que pacotes importados registrem rotas acidentalmente no mux global:

go mux explícito 
func main() {
    mux := http.NewServeMux()

    mux.HandleFunc("GET /healthz", handleHealth)
    mux.HandleFunc("GET /api/usuarios", handleListarUsuarios)
    mux.HandleFunc("POST /api/usuarios", handleCriarUsuario)
    mux.HandleFunc("GET /api/usuarios/{id}", handleBuscarUsuario)

    srv := &http.Server{
        Addr:    ":8080",
        Handler: mux,
    }

    log.Println("servidor iniciado em :8080")
    if err := srv.ListenAndServe(); err != nil {
        log.Fatal(err)
    }
}

func handleHealth(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
    w.Write([]byte("ok"))
}
Go 1.22: padrões de rota com método e parâmetros
A partir do Go 1.22, o ServeMux passou a suportar prefixo de método HTTP ("GET /path") e parâmetros de caminho ("{id}") diretamente, sem dependências externas. Acesse o parâmetro com r.PathValue("id"). Para projetos que precisam de roteamento mais avançado (wildcards, grupos, middleware por rota), frameworks como chi ou gorilla/mux ainda fazem sentido.

Goroutine por requisição

O servidor de Go lança uma goroutine para cada requisição recebida. Isso significa que seu handler pode bloquear (I/O, banco de dados) sem travar o servidor, e que handlers são chamados concorrentemente — qualquer estado compartilhado entre handlers precisa de sincronização.

go estado compartilhado — requer mutex 
type Servidor struct {
    mu       sync.Mutex
    visitas  int
}

func (s *Servidor) handleContador(w http.ResponseWriter, r *http.Request) {
    s.mu.Lock()
    s.visitas++
    v := s.visitas
    s.mu.Unlock()
    fmt.Fprintf(w, "visitas: %d", v)
}

func main() {
    s := &Servidor{}
    mux := http.NewServeMux()
    mux.HandleFunc("GET /contador", s.handleContador)
    log.Fatal(http.ListenAndServe(":8080", mux))
}

Handlers e http.HandlerFunc

O coração do servidor de Go é a interface http.Handler:

go definição da interface 
type Handler interface {
    ServeHTTP(ResponseWriter, *Request)
}

Qualquer tipo que implemente ServeHTTP pode ser registrado como handler. http.HandlerFunc é um type adapter que converte uma função com a assinatura correta em um http.Handler:

go HandlerFunc como type adapter 
// http.HandlerFunc é definido na stdlib como:
type HandlerFunc func(ResponseWriter, *Request)
func (f HandlerFunc) ServeHTTP(w ResponseWriter, r *Request) { f(w, r) }

// Logo, qualquer func(ResponseWriter, *Request) pode virar um Handler:
var h http.Handler = http.HandlerFunc(meuHandler)  // conversão explícita
mux.Handle("/rota", h)

// HandleFunc faz a conversão implicitamente:
mux.HandleFunc("/rota", meuHandler)  // equivalente

Handler como struct — injeção de dependências

Implementar a interface em uma struct é o padrão para injetar dependências (banco de dados, logger, configuração) nos handlers sem variáveis globais:

go handler com dependências injetadas 
type UsuarioHandler struct {
    repo   UsuarioRepo
    logger *slog.Logger
}

func (h *UsuarioHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    switch r.Method {
    case http.MethodGet:
        h.listar(w, r)
    case http.MethodPost:
        h.criar(w, r)
    default:
        http.Error(w, "método não permitido", http.StatusMethodNotAllowed)
    }
}

func (h *UsuarioHandler) listar(w http.ResponseWriter, r *http.Request) {
    usuarios, err := h.repo.Todos(r.Context())
    if err != nil {
        h.logger.Error("listar usuários", "erro", err)
        http.Error(w, "erro interno", http.StatusInternalServerError)
        return
    }
    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(usuarios)
}

// Wiring na main:
func main() {
    db := conectarDB()
    logger := slog.Default()

    mux := http.NewServeMux()
    mux.Handle("/api/usuarios", &UsuarioHandler{
        repo:   postgres.NewUsuarioRepo(db),
        logger: logger,
    })
    log.Fatal(http.ListenAndServe(":8080", mux))
}

ResponseWriter — escrevendo respostas

go 
func handler(w http.ResponseWriter, r *http.Request) {
    // 1. Defina headers ANTES de WriteHeader ou Write
    w.Header().Set("Content-Type", "application/json")
    w.Header().Set("X-Request-ID", r.Header.Get("X-Request-ID"))

    // 2. Status code (padrão 200 se omitido)
    w.WriteHeader(http.StatusCreated)  // 201

    // 3. Body
    w.Write([]byte(`{"status":"criado"}`))

    // Atenção: após Write ou WriteHeader, headers não podem mais ser alterados
}
Headers devem ser definidos antes do body
Em HTTP, o status code e os headers são enviados antes do body. Em Go, a primeira chamada a w.Write() ou w.WriteHeader() envia os headers. Qualquer w.Header().Set() após isso é silenciosamente ignorado. O padrão: headers → WriteHeader → Write, nessa ordem.

Middleware

Middleware em Go é uma função que recebe um http.Handler e retorna outro http.Handler — envolvendo o handler original com comportamento adicional. Isso é possível porque http.Handler é uma interface, e funções são valores de primeira classe em Go.

go assinatura padrão de middleware 
// Tipo canônico: recebe Handler, retorna Handler
type Middleware func(http.Handler) http.Handler

Implementando middlewares reais

go logging + autenticação + recover 
// Logging: registra método, path e duração de cada requisição
func comLogging(logger *slog.Logger) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            inicio := time.Now()
            next.ServeHTTP(w, r)
            logger.Info("requisição",
                "método", r.Method,
                "path", r.URL.Path,
                "duração", time.Since(inicio),
            )
        })
    }
}

// Autenticação: valida Bearer token no header Authorization
func comAutenticacao(validar func(string) bool) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            token := strings.TrimPrefix(r.Header.Get("Authorization"), "Bearer ")
            if !validar(token) {
                http.Error(w, "não autorizado", http.StatusUnauthorized)
                return  // interrompe a cadeia — next NÃO é chamado
            }
            next.ServeHTTP(w, r)
        })
    }
}

// Recovery: captura panics em handlers e retorna 500
func comRecovery(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if r := recover(); r != nil {
                log.Printf("panic recuperado: %v\n%s", r, debug.Stack())
                http.Error(w, "erro interno", http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}

Compondo middlewares em cadeia

Middlewares são compostos envolvendo uns aos outros. A ordem importa: o middleware mais externo é executado primeiro na entrada e por último na saída:

go composição de cadeia 
// Função utilitária para compor middlewares (aplicados de fora para dentro)
func encadear(h http.Handler, ms ...func(http.Handler) http.Handler) http.Handler {
    for i := len(ms) - 1; i >= 0; i-- {
        h = ms[i](h)
    }
    return h
}

func main() {
    logger := slog.Default()
    mux := http.NewServeMux()
    mux.HandleFunc("GET /api/perfil", handlePerfil)

    handler := encadear(mux,
        comRecovery,                           // 1º a executar (mais externo)
        comLogging(logger),                    // 2º
        comAutenticacao(validarJWT),           // 3º (mais interno antes do mux)
    )

    log.Fatal(http.ListenAndServe(":8080", handler))
}
// Ordem de execução por requisição:
// Recovery → Logging → Autenticação → Handler → Autenticação → Logging → Recovery
Passando dados entre middlewares: context
Para passar dados de um middleware para o handler (ex: o usuário autenticado extraído do token), use r.WithContext(context.WithValue(r.Context(), chave, valor)) e recupere com r.Context().Value(chave). Use tipos concretos como chave — nunca strings — para evitar colisões entre pacotes.

Cliente HTTP

O pacote net/http inclui também um cliente HTTP completo. A função http.Get é conveniente para casos simples, mas em código de produção você sempre cria um http.Client próprio com timeouts configurados.

Fazendo requisições — o básico

go GET simples 
resp, err := http.Get("https://api.github.com/users/golang")
if err != nil {
    return fmt.Errorf("GET: %w", err)
}
defer resp.Body.Close()  // SEMPRE fechar o body

if resp.StatusCode != http.StatusOK {
    return fmt.Errorf("status inesperado: %d", resp.StatusCode)
}

body, err := io.ReadAll(resp.Body)
if err != nil {
    return fmt.Errorf("lendo body: %w", err)
}
fmt.Println(string(body))
resp.Body.Close() é mandatório
O body de uma resposta HTTP é uma conexão de rede ativa. Se não for fechado, a conexão permanece aberta e não retorna para o pool — esgotando as conexões disponíveis com o tempo. Use sempre defer resp.Body.Close() imediatamente após verificar o erro do http.Get ou client.Do.

http.NewRequest — controle total

Para requisições com método específico, headers customizados ou body, use http.NewRequestWithContext:

go POST com body e headers 
func criarIssue(ctx context.Context, token, repo string, payload any) error {
    body, err := json.Marshal(payload)
    if err != nil {
        return fmt.Errorf("marshal: %w", err)
    }

    req, err := http.NewRequestWithContext(ctx,
        http.MethodPost,
        fmt.Sprintf("https://api.github.com/repos/%s/issues", repo),
        bytes.NewReader(body),
    )
    if err != nil {
        return fmt.Errorf("criar request: %w", err)
    }

    req.Header.Set("Content-Type", "application/json")
    req.Header.Set("Authorization", "Bearer "+token)
    req.Header.Set("Accept", "application/vnd.github+json")

    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return fmt.Errorf("executar request: %w", err)
    }
    defer resp.Body.Close()

    if resp.StatusCode != http.StatusCreated {
        b, _ := io.ReadAll(resp.Body)
        return fmt.Errorf("API retornou %d: %s", resp.StatusCode, b)
    }
    return nil
}

Timeouts e configuração do cliente

http.DefaultClient não tem timeout configurado. Em produção, uma requisição a uma API lenta pode bloquear a goroutine indefinidamente. Todo cliente HTTP em Go para produção deve ter timeouts explícitos.

go cliente configurado para produção 
// cliente criado uma vez e reutilizado — nunca criar por requisição
var clienteHTTP = &http.Client{
    Timeout: 10 * time.Second,  // timeout total da requisição (dial + TLS + headers + body)
    Transport: &http.Transport{
        DialContext: (&net.Dialer{
            Timeout:   3 * time.Second,  // tempo máximo para estabelecer conexão TCP
            KeepAlive: 30 * time.Second, // keep-alive de conexões no pool
        }).DialContext,
        TLSHandshakeTimeout:   5 * time.Second,  // tempo máximo para handshake TLS
        ResponseHeaderTimeout: 5 * time.Second,  // tempo máximo aguardando headers de resposta
        MaxIdleConns:          100,              // total de conexões idle no pool
        MaxIdleConnsPerHost:   10,               // idle por host
        IdleConnTimeout:       90 * time.Second, // tempo de vida de conexão idle
    },
}

Timeout por requisição com context

O campo Timeout do cliente define um limite global. Para timeouts por requisição (mais granular), use context.WithTimeout e http.NewRequestWithContext:

go timeout por requisição 
func buscarDados(ctx context.Context, url string) ([]byte, error) {
    // timeout específico para esta requisição
    ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
    defer cancel()

    req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
    if err != nil {
        return nil, err
    }

    resp, err := clienteHTTP.Do(req)
    if err != nil {
        // context.DeadlineExceeded se o timeout expirou
        if errors.Is(err, context.DeadlineExceeded) {
            return nil, fmt.Errorf("timeout ao buscar %s", url)
        }
        return nil, fmt.Errorf("buscarDados: %w", err)
    }
    defer resp.Body.Close()

    return io.ReadAll(resp.Body)
}
Parâmetro O que limita Valor típico
Client.Timeout Requisição inteira (dial + TLS + body) 10–30s
DialContext.Timeout Apenas estabelecimento TCP 3–5s
TLSHandshakeTimeout Negociação TLS/SSL 5s
ResponseHeaderTimeout Aguardando primeiro byte dos headers 5s
Nunca criar http.Client por requisição
http.Client mantém um pool interno de conexões TCP reutilizáveis (http.Transport). Criar um novo cliente por requisição descarta o pool a cada vez — forçando um novo handshake TCP e TLS para cada chamada. Crie o cliente uma vez como variável de pacote ou campo de struct e reutilize.

JSON sobre HTTP

A combinação de net/http e encoding/json é o padrão para APIs REST em Go. O módulo 29 detalha JSON em profundidade — aqui o foco é nos padrões de integração HTTP, que têm suas próprias armadilhas.

Decodificando o body de uma requisição

go lendo JSON do body de uma requisição POST 
type CriarUsuarioReq struct {
    Nome  string `json:"nome"`
    Email string `json:"email"`
}

func handleCriarUsuario(w http.ResponseWriter, r *http.Request) {
    // Limitar tamanho do body — previne ataques de payload gigante
    r.Body = http.MaxBytesReader(w, r.Body, 1<<20)  // 1 MB

    var req CriarUsuarioReq
    dec := json.NewDecoder(r.Body)
    dec.DisallowUnknownFields()  // rejeita campos desconhecidos

    if err := dec.Decode(&req); err != nil {
        var maxBytesErr *http.MaxBytesError
        switch {
        case errors.As(err, &maxBytesErr):
            http.Error(w, "payload muito grande", http.StatusRequestEntityTooLarge)
        case err == io.EOF:
            http.Error(w, "body vazio", http.StatusBadRequest)
        default:
            http.Error(w, "JSON inválido: "+err.Error(), http.StatusBadRequest)
        }
        return
    }

    // Validação de negócio
    if req.Nome == "" || req.Email == "" {
        http.Error(w, "nome e email são obrigatórios", http.StatusUnprocessableEntity)
        return
    }

    usuario, err := criarUsuario(r.Context(), req.Nome, req.Email)
    if err != nil {
        http.Error(w, "erro interno", http.StatusInternalServerError)
        return
    }

    responderJSON(w, http.StatusCreated, usuario)
}

Utilitário para responder JSON

Um helper centraliza o padrão de resposta JSON e garante que o header Content-Type seja sempre definido:

go 
// responderJSON serializa v como JSON e escreve na resposta
func responderJSON(w http.ResponseWriter, status int, v any) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(status)
    if err := json.NewEncoder(w).Encode(v); err != nil {
        // Neste ponto o status já foi enviado — apenas logamos
        slog.Error("encoding JSON", "erro", err)
    }
}

// Uso:
responderJSON(w, http.StatusOK, map[string]any{
    "usuarios": lista,
    "total":    len(lista),
})

// Para erros JSON estruturados (padrão de API REST):
type ErroResp struct {
    Erro   string `json:"erro"`
    Codigo string `json:"codigo,omitempty"`
}

func responderErro(w http.ResponseWriter, status int, mensagem, codigo string) {
    responderJSON(w, status, ErroResp{Erro: mensagem, Codigo: codigo})
}

Decodificando resposta JSON do cliente

go cliente decodificando resposta JSON 
type GitHubUser struct {
    Login     string `json:"login"`
    Nome      string `json:"name"`
    Seguidores int   `json:"followers"`
}

func buscarUsuarioGitHub(ctx context.Context, login string) (*GitHubUser, error) {
    req, _ := http.NewRequestWithContext(ctx, http.MethodGet,
        "https://api.github.com/users/"+login, nil)
    req.Header.Set("Accept", "application/vnd.github+json")

    resp, err := clienteHTTP.Do(req)
    if err != nil {
        return nil, fmt.Errorf("buscarUsuarioGitHub: %w", err)
    }
    defer resp.Body.Close()

    if resp.StatusCode != http.StatusOK {
        body, _ := io.ReadAll(resp.Body)
        return nil, fmt.Errorf("GitHub API %d: %s", resp.StatusCode, body)
    }

    // Decodificar diretamente do body — sem io.ReadAll intermediário
    var u GitHubUser
    if err := json.NewDecoder(resp.Body).Decode(&u); err != nil {
        return nil, fmt.Errorf("decodificar resposta: %w", err)
    }
    return &u, nil
}
json.NewDecoder vs json.Unmarshal
json.NewDecoder(r.Body).Decode(&v) lê o io.Reader diretamente — sem carregar o body inteiro na memória primeiro. json.Unmarshal exige um []byte completo em memória. Para payloads HTTP, prefira o Decoder — especialmente para respostas grandes. O Decoder também suporta múltiplos valores JSON sequenciais no mesmo stream.
Quiz · Questão 1 de 3 Verificação de entendimento

O handler abaixo tem um bug: o header Content-Type não aparece na resposta. Por quê?

go 
func handler(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
    w.Header().Set("Content-Type", "application/json")
    w.Write([]byte(`{"ok":true}`))
}
✓ Correto! w.WriteHeader(http.StatusOK) serializa e envia a linha de status HTTP e todos os headers acumulados até aquele momento. O Set("Content-Type", ...) vem depois — quando os headers já foram transmitidos. O Go não retorna erro: silenciosamente ignora a modificação. A correção: mover o Header().Set para antes do WriteHeader.
Quiz · Questão 2 de 3 Verificação de entendimento

Um microserviço faz centenas de chamadas por minuto a uma API externa. Após algumas horas em produção, começa a acumular erros "connection refused" e esgotamento de file descriptors. Qual é o bug mais provável no código abaixo?

go 
func chamarAPI(url string) ([]byte, error) {
    resp, err := clienteHTTP.Get(url)
    if err != nil {
        return nil, err
    }
    if resp.StatusCode != 200 {
        return nil, fmt.Errorf("status %d", resp.StatusCode)
    }
    return io.ReadAll(resp.Body)
}
✓ Correto! No caminho de erro (StatusCode != 200), a função retorna sem fechar o body — deixando a conexão TCP aberta indefinidamente. O defer resp.Body.Close() deve ser colocado imediatamente após verificar o erro do Get — antes de qualquer verificação de status — para garantir fechamento em todos os caminhos de retorno. Curiosamente, a opção D também está incorreta: io.ReadAll não fecha o body — isso é responsabilidade do chamador.
Quiz · Questão 3 de 3 Verificação de entendimento

Dado o código de encadeamento abaixo, qual é a ordem de execução quando uma requisição chega?

go 
handler := comRecovery(
    comLogging(
        comAutenticacao(mux),
    ),
)
✓ Correto! O middleware mais externo (comRecovery) é o primeiro a receber a requisição e o último a processar a resposta. É como camadas de uma cebola: a requisição entra de fora para dentro (Recovery → Logging → Autenticação → mux) e a resposta sai de dentro para fora. Isso explica por que Recovery deve ser o mais externo — ele precisa capturar panics de todos os outros middlewares e do handler.
Exercício 1 — Bug em produção Aplicação prática

Um serviço em Go faz chamadas a três APIs externas para montar uma resposta composta. O código abaixo funciona em testes mas é lento em produção sob carga alta. Identifique o problema principal e a correção correta.

go 
func handleDashboard(w http.ResponseWriter, r *http.Request) {
    cliente := &http.Client{Timeout: 5 * time.Second}  // novo cliente por requisição

    usuario, _ := buscarUsuario(cliente, r.Context())
    pedidos, _ := buscarPedidos(cliente, r.Context())
    notifs, _  := buscarNotificacoes(cliente, r.Context())

    responderJSON(w, http.StatusOK, map[string]any{
        "usuario": usuario,
        "pedidos": pedidos,
        "notifs":  notifs,
    })
}
✓ Correto! Dois problemas distintos. O primeiro: cada requisição ao dashboard cria um http.Client com um novo Transport — descartando o pool de conexões. Sob carga, isso multiplica handshakes TCP e TLS desnecessários. Solução: cliente como variável de pacote ou campo de struct, criado uma vez. O segundo: as três chamadas externas são feitas em série (soma dos timeouts). Paralelizá-las com golang.org/x/sync/errgroup reduz a latência total para o máximo das três, não a soma. A opção D seria uma melhora parcial (resolve o pool), mas http.DefaultClient não tem timeout — perigoso em produção.
Exercício 2 — Decisão de design Aplicação prática

Você está construindo uma API REST em Go. Precisa que todas as rotas sob /api/ exijam autenticação, mas a rota /healthz deve ser pública. Qual é a abordagem idiomática em Go com ServeMux?

✓ Correto! Usar sub-mux separados é o padrão idiomático em Go porque mantém cada grupo de rotas com seu próprio conjunto de middlewares — sem lógica condicional dentro do middleware. A abordagem com whitelist (opção C) é frágil: qualquer nova rota pública exige editar o middleware, e a lógica de exceção cresce indefinidamente. Com sub-mux: mux.Handle("/api/", comAutenticacao(apiMux)) e mux.HandleFunc("/healthz", handleHealth) — cada rota tem exatamente os middlewares que precisa, sem acoplamento.
