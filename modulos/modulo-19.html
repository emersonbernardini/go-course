Criando pacotes

Em Go, um pacote é simplesmente um diretório com arquivos .go que compartilham a mesma declaração package. Não existe sintaxe especial de criação — você cria uma pasta, cria arquivos .go dentro dela, e declara o nome do pacote na primeira linha de cada arquivo.

bash estrutura de diretórios 
meuprojeto/
├── go.mod
├── main.go
└── math/
    ├── soma.go
    └── media.go
go math/soma.go 
package math  // nome do pacote — deve ser igual em todos os arquivos da pasta

func Somar(a, b int) int {
    return a + b
}
go math/media.go 
package math  // mesmo nome — faz parte do mesmo pacote

func Media(nums []float64) float64 {
    if len(nums) == 0 {
        return 0
    }
    var total float64
    for _, n := range nums {
        total += n
    }
    return total / float64(len(nums))
}

Os dois arquivos pertencem ao mesmo pacote math. Eles enxergam as funções, variáveis e tipos uns dos outros diretamente — sem importação — como se fossem um arquivo só. Para usar o pacote de outro lugar, você o importa pelo caminho do módulo:

go main.go 
package main

import (
    "fmt"
    "meuprojeto/math"  // caminho do módulo + subpasta
)

func main() {
    fmt.Println(math.Somar(3, 4))    // 7
    fmt.Println(math.Media([]float64{1, 2, 3}))  // 2
}

Nome do pacote vs caminho de importação

O caminho de importação é o caminho do diretório relativo ao módulo (meuprojeto/math). O nome do pacote é o identificador que você usa no código (math.Somar). Por convenção, os dois coincidem — mas não são obrigados:

go 
// Diretório: meuprojeto/httputil/
// Declaração no arquivo: package httputil
// Importado como: "meuprojeto/httputil"
// Usado como: httputil.AlgumaFunc()

// Caso real da stdlib: o diretório é encoding/json
// mas o pacote se chama json — import "encoding/json", uso: json.Marshal()
Todos os arquivos da pasta devem ter o mesmo package
Se dois arquivos no mesmo diretório declaram nomes de pacote diferentes, o compilador rejeita. A única exceção é package nome_test — o sufixo _test é permitido para testes externos ao pacote no mesmo diretório.

Exportação por maiúscula

Go não tem palavras-chave public ou private. A visibilidade é determinada pela primeira letra do identificador: maiúscula é exportado (visível fora do pacote), minúscula é não-exportado (visível apenas dentro do pacote). Essa regra se aplica a funções, tipos, variáveis, constantes, campos de struct e métodos.

go pacote/usuario.go 
package usuario

// Usuario — exportado: acessível por quem importar o pacote
type Usuario struct {
    Nome  string  // exportado
    Email string  // exportado
    senha string  // não-exportado: só acessível dentro de pacote/
}

// Novo — exportado: construtor público
func Novo(nome, email, senha string) *Usuario {
    return &Usuario{
        Nome:  nome,
        Email: email,
        senha: hashSenha(senha),  // usa função não-exportada
    }
}

// ValidarSenha — exportado: API pública
func (u *Usuario) ValidarSenha(tentativa string) bool {
    return hashSenha(tentativa) == u.senha
}

// hashSenha — não-exportada: detalhe de implementação
func hashSenha(s string) string {
    // ... lógica interna
    return s
}

Quem importar o pacote usuario pode acessar usuario.Novo, u.Nome, u.ValidarSenha — mas u.senha e hashSenha são invisíveis. O compilador rejeita qualquer acesso a identificadores não-exportados de fora do pacote.

Exportação se aplica a campos de struct individualmente

go 
// Struct exportada com campos mistos
type Config struct {
    Host    string // exportado — quem usa o pacote pode ler/escrever
    Porta   int    // exportado
    timeout int    // não-exportado — controlado internamente
    retries int    // não-exportado
}

// Do ponto de vista de quem importa:
cfg := config.Config{Host: "localhost", Porta: 8080}
// cfg.timeout = 30  // ERRO de compilação: campo não-exportado

Convenções de nomenclatura

Identificador Convenção Exemplo
Tipo exportado PascalCase HttpClient, UserRepo
Função/método exportado PascalCase Marshal, ParseURL
Variável/constante não-exportada camelCase maxRetries, defaultTimeout
Erro sentinela exportado Err + PascalCase ErrNotFound, ErrTimeout
Go não usa underscores em nomes — exceto em testes
Ao contrário de Python ou C, Go usa camelCase para identificadores não-exportados e PascalCase para exportados. Underscores aparecem apenas em nomes de arquivo de teste (_test.go), em imports em branco (_) e em constantes geradas (como iota patterns). Nunca em funções ou variáveis normais.

Pacotes internos (internal)

Exportação por maiúscula tem uma limitação: qualquer módulo externo pode importar um pacote exportado da sua biblioteca. Às vezes você quer compartilhar código entre subpacotes do seu próprio módulo sem expô-lo ao mundo. Para isso existe o diretório especial internal/.

Uma regra do toolchain Go: apenas o código dentro da árvore pai do diretório internal pode importá-lo. Qualquer módulo externo que tente importar um pacote internal/ recebe um erro de compilação.

bash estrutura com internal 
github.com/empresa/api/
├── go.mod
├── main.go
├── handler/
│   └── usuario.go      // pode importar internal/
├── service/
│   └── usuario.go      // pode importar internal/
└── internal/
    ├── db/
    │   └── conn.go     // só acessível dentro de github.com/empresa/api/
    └── validator/
        └── cpf.go      // idem
go handler/usuario.go 
package handler

import (
    "github.com/empresa/api/internal/db"        // ✓ permitido — mesmo módulo
    "github.com/empresa/api/internal/validator"  // ✓ permitido
)

func CriarUsuario(w http.ResponseWriter, r *http.Request) {
    if !validator.CPF(r.FormValue("cpf")) {
        http.Error(w, "CPF inválido", 400)
        return
    }
    conn := db.Get()
    // ...
}
go outro-modulo/main.go 
package main

import "github.com/empresa/api/internal/db"
// ERRO de compilação:
// use of internal package github.com/empresa/api/internal/db
// not allowed

internal aninhado — escopo mais restrito

Você pode aninhar internal dentro de subpacotes para restringir ainda mais o acesso:

bash 
github.com/empresa/api/
└── service/
    ├── usuario.go
    └── internal/
        └── cache.go  // só service/ pode importar — nem handler/ consegue
internal é a ferramenta certa para API privada de biblioteca
Se você publica uma biblioteca Go no GitHub, tudo fora de internal/ com letra maiúscula vira API pública de fato — qualquer usuário pode depender disso. Use internal/ para código de suporte que você não quer comprometer a manter compatível entre versões.

Organização de código

Go não impõe uma estrutura de projeto — mas a comunidade convergiu em padrões práticos baseados em como o toolchain e os pacotes interagem. Entender esses padrões evita reorganizações dolorosas conforme o projeto cresce.

Flat first — comece simples

Para projetos pequenos, um único pacote main com múltiplos arquivos .go na raiz é suficiente e preferível. Não crie subpacotes antes de precisar — Go não recompensa estrutura prematura:

bash projeto pequeno — flat 
minha-cli/
├── go.mod
├── main.go
├── config.go    // package main — mesmo pacote, arquivo separado por clareza
├── handler.go   // package main
└── storage.go   // package main

Quando extrair um pacote

Extraia para um subpacote quando o código tem uma responsabilidade coesa o suficiente para ter sua própria API, ou quando precisa ser reutilizado por mais de um ponto do projeto:

bash projeto médio — com subpacotes 
minha-api/
├── go.mod
├── main.go              // package main — ponto de entrada
├── handler/
│   ├── usuario.go       // package handler
│   └── produto.go
├── service/
│   ├── usuario.go       // package service
│   └── produto.go
├── repository/
│   └── usuario.go       // package repository
└── internal/
    └── validator/
        └── validator.go // package validator

cmd/ para múltiplos binários

Se o projeto produz mais de um executável, cada um fica em seu próprio subdiretório de cmd/. Cada diretório é um package main independente:

bash múltiplos binários 
meu-sistema/
├── go.mod
├── cmd/
│   ├── api/
│   │   └── main.go    // go build ./cmd/api → binário do servidor HTTP
│   └── worker/
│       └── main.go    // go build ./cmd/worker → binário do processador
├── internal/
│   └── db/
└── pkg/
    └── models/        // pacotes reutilizáveis e importáveis externamente

// Para compilar um binário específico:
// go build ./cmd/api
// go build ./cmd/worker
// Para compilar todos:
// go build ./...

Imports em grupos e ordem canônica

O goimports (e o gofmt) organiza os imports em três grupos separados por linha em branco — essa é a convenção oficial:

go ordem de imports 
import (
    // 1. Stdlib
    "fmt"
    "net/http"
    "os"

    // 2. Dependências externas
    "github.com/go-chi/chi/v5"
    "go.uber.org/zap"

    // 3. Pacotes do próprio módulo
    "github.com/empresa/api/internal/db"
    "github.com/empresa/api/service"
)
Imports circulares são proibidos — e por isso o design importa
Go não permite que o pacote A importe B e B importe A — nem indiretamente. O compilador rejeita com erro. Isso força uma hierarquia clara de dependências. Se você se encontra tentando criar um import circular, é sinal de que dois pacotes estão muito acoplados e deveriam ser reorganizados — ou que a lógica compartilhada pertence a um terceiro pacote que ambos importam.
Quiz · Questão 1 de 3 Verificação de entendimento

Qual é o output do código abaixo? O pacote config declara a struct à esquerda; o pacote main executa o código à direita.

go 
// pacote config
type Opcoes struct {
    Host    string
    Porta   int
    timeout int
}

// pacote main
cfg := config.Opcoes{Host: "localhost", Porta: 8080, timeout: 30}
fmt.Println(cfg.Host)
✓ Correto! Campos não-exportados não podem ser referenciados por código fora do pacote — nem para leitura, nem para escrita, nem em struct literals. O compilador rejeita config.Opcoes{..., timeout: 30} com "cannot refer to unexported field 'timeout'". A struct deve ser inicializada sem o campo, ou via uma função construtora exportada pelo próprio pacote config.
Quiz · Questão 2 de 3 Verificação de entendimento

Dado o layout abaixo, qual pacote não consegue importar service/internal/cache?

bash 
github.com/empresa/app/
├── main.go
├── handler/
│   └── usuario.go
└── service/
    ├── usuario.go
    └── internal/
        └── cache/
            └── cache.go
✓ Correto! O pai de service/internal/ é o diretório service/. Somente código dentro de service/ (e seus subdiretórios) pode importar service/internal/cache. O handler/ está fora dessa árvore — assim como o main.go na raiz. O main não tem nenhum privilégio especial de importação.
Quiz · Questão 3 de 3 Verificação de entendimento

Dois arquivos no mesmo diretório util/ têm as seguintes declarações. O que acontece ao compilar?

go 
// util/strings.go
package util

// util/numbers.go
package utilities
✓ Correto! O compilador Go exige que todos os arquivos .go no mesmo diretório declarem o mesmo nome de pacote. Ter package util em um arquivo e package utilities em outro resulta em: "found packages util (strings.go) and utilities (numbers.go)". A única exceção permitida é o sufixo _test para arquivos de teste de caixa-preta no mesmo diretório.
Exercício 1 — Decisão de exportação Aplicação prática

Você está escrevendo um pacote pagamento que: (a) expõe uma função Processar para quem usar o pacote; (b) usa internamente uma função de cálculo de taxa; (c) tem uma struct Transacao com campos de valor, moeda e um campo idInterno gerado pela infraestrutura. Qual conjunto de declarações está correto?

✓ Correto! Cada identificador tem visibilidade própria e independente. Processar é a API pública — exportada. calcularTaxa é detalhe de implementação — não-exportada, e quem usa o pacote não precisa saber que existe. Transacao precisa ser exportada para que quem chama Processar possa receber e usar o retorno — mas idInterno é gerado internamente e não deve ser acessível ou modificável de fora. Tags de struct controlam serialização (JSON, SQL), não visibilidade de acesso.
Exercício 2 — Import circular Aplicação prática

O pacote service importa repository para buscar dados, e o pacote repository quer importar service para reutilizar uma função de validação. O compilador rejeita: import circular. Qual é a solução idiomática em Go?

✓ Correto! A solução canônica para imports circulares em Go é identificar a dependência comum e extraí-la para um pacote independente que nenhum dos dois precisa importar. Isso força uma hierarquia de dependências limpa: service e repository ambos dependem de validator, mas não um do outro. Colocar em internal/validator ainda restringe o uso ao próprio módulo. Duplicar lógica e fundir tudo em main são antipadrões que escalam mal.
