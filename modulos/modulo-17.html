O que é uma interface

Uma interface em Go é um conjunto de assinaturas de métodos. Qualquer tipo que implemente todos esses métodos satisfaz a interface — automaticamente, sem declarar isso explicitamente. Não existe a palavra-chave implements.

go definição básica 
// Uma interface define o que um tipo consegue fazer — não o que ele é
type Stringer interface {
    String() string
}

// Qualquer tipo com o método String() string satisfaz Stringer
type Produto struct {
    Nome  string
    Preco float64
}

func (p Produto) String() string {
    return fmt.Sprintf("%s — R$ %.2f", p.Nome, p.Preco)
}

// Produto satisfaz Stringer sem declarar isso em nenhum lugar
var s Stringer = Produto{Nome: "Teclado", Preco: 299.90}
fmt.Println(s.String())  // Teclado — R$ 299.90

Interfaces separam o que algo faz de como faz. Uma função que recebe uma interface não precisa saber qual tipo concreto está por trás — só precisa saber que o tipo tem os métodos exigidos. Isso é o que permite substituir implementações sem alterar o código que as usa.

go separação de responsabilidades 
type Notificador interface {
    Notificar(destinatario, mensagem string) error
}

// A função não sabe se está enviando e-mail, SMS ou push notification
func enviarAlerta(n Notificador, usuario, msg string) error {
    return n.Notificar(usuario, msg)
}

// Qualquer tipo com Notificar(...) funciona aqui
enviarAlerta(emailService, "ana@exemplo.com", "Sua senha foi alterada")
enviarAlerta(smsService,   "11999998888",    "Sua senha foi alterada")
Interface vs herança
Go não tem herança. Interfaces são o mecanismo de polimorfismo da linguagem. Em vez de perguntar "de que tipo esse objeto herda?", Go pergunta "quais métodos esse tipo tem?". Isso resulta em acoplamento menor e composição mais flexível.

Implementação implícita

Em Go, um tipo satisfaz uma interface quando possui todos os métodos que ela exige. Não há declaração de intenção — nenhum implements, nenhum extends. O compilador verifica isso em tempo de compilação.

go implementação sem declaração explícita 
type Animal interface {
    Som() string
    Nome() string
}

type Cachorro struct{ nome string }

func (c Cachorro) Som() string  { return "Au" }
func (c Cachorro) Nome() string { return c.nome }

type Gato struct{ nome string }

func (g Gato) Som() string  { return "Miau" }
func (g Gato) Nome() string { return g.nome }

// Cachorro e Gato satisfazem Animal sem nunca mencionar Animal
func apresentar(a Animal) {
    fmt.Printf("%s faz: %s\n", a.Nome(), a.Som())
}

apresentar(Cachorro{nome: "Rex"})   // Rex faz: Au
apresentar(Gato{nome: "Whiskers"})  // Whiskers faz: Miau

Satisfação parcial não é satisfação

Um tipo precisa implementar todos os métodos da interface. Implementar apenas parte deles causa erro de compilação ao tentar usar o tipo como a interface:

go 
type Peixe struct{}

func (p Peixe) Som() string { return "..." }
// Peixe não tem o método Nome() string

var a Animal = Peixe{}
// ERRO: cannot use Peixe as type Animal in assignment:
//       Peixe does not implement Animal (missing Nome method)

Verificação de implementação em tempo de compilação

Uma convenção idiomática em Go é declarar explicitamente que um tipo satisfaz uma interface — não para o runtime, mas para o compilador verificar e emitir um erro descritivo se a implementação estiver incompleta:

go compile-time check 
// Garante em tempo de compilação que *EmailService implementa Notificador
// Se um método estiver faltando, o erro aparece aqui — não no ponto de uso
var _ Notificador = (*EmailService)(nil)

// O padrão: atribuir nil convertido para o tipo concreto à variável em branco (_)
// Zero custo em runtime — o compilador descarta a atribuição
Por que implementação implícita?
Permite que um tipo satisfaça interfaces definidas depois que ele foi escrito — inclusive interfaces de pacotes que nem existiam quando o tipo foi criado. É por isso que fmt.Println chama automaticamente o método String() de qualquer tipo que o implemente: fmt.Stringer foi definida no pacote fmt, mas qualquer tipo do seu código pode satisfazê-la.

Interface vazia (any / interface{})

Uma interface sem métodos é satisfeita por qualquer tipo — afinal, todo tipo implementa zero métodos. Em Go 1.18+, any é o alias oficial para interface{}. Os dois são idênticos.

go any aceita qualquer valor 
var v any

v = 42
v = "olá"
v = true
v = []int{1, 2, 3}
v = struct{ X int }{X: 99}

// Todos os assignments acima são válidos
// any é o tipo "qualquer coisa" de Go

Onde any aparece na prática

go 
// fmt.Println aceita qualquer coisa porque usa ...any
func Println(a ...any) (n int, err error)

// map com valores de tipos mistos
config := map[string]any{
    "porta":   8080,
    "debug":   true,
    "nome":    "gomonitor",
    "timeout": 30.0,
}

// JSON desserializado sem struct conhecido
var dados map[string]any
json.Unmarshal(jsonBytes, &dados)
any remove a proteção do compilador
Ao usar any, você abre mão da verificação de tipos em tempo de compilação. O erro se move para runtime. Use any quando o tipo é genuinamente desconhecido em tempo de compilação (JSON arbitrário, dados de reflexão). Para casos onde os tipos são conhecidos mas variados, prefira generics (módulo 31) ou interfaces com métodos.

Type assertion

Uma interface armazena dois campos internos: o tipo concreto e o valor. Type assertion extrai o valor concreto de dentro da interface — afirmando ao compilador "eu sei que o valor por trás dessa interface é deste tipo".

go sintaxe básica 
var v any = "olá, Go"

// Forma sem verificação — panic se o tipo estiver errado
s := v.(string)
fmt.Println(s)       // olá, Go
fmt.Println(len(s))  // 8

// Tentativa errada — causa panic em runtime
n := v.(int)  // panic: interface conversion: interface {} is string, not int

Forma segura: comma ok

Para evitar panic, use a forma de dois valores. Se a asserção falhar, ok é false e v recebe o zero value do tipo — sem panic:

go 
var i any = "texto"

// Forma segura — nunca causa panic
s, ok := i.(string)
if ok {
    fmt.Println("é string:", s)  // é string: texto
}

n, ok := i.(int)
if !ok {
    fmt.Println("não é int")     // não é int
    fmt.Println(n)               // 0 — zero value de int
}

// Padrão idiomático: verificar e usar no mesmo bloco
if s, ok := i.(string); ok {
    fmt.Println(strings.ToUpper(s))
}

Type assertion em interface para interface

Type assertion também funciona entre interfaces — para verificar se o tipo concreto por trás de uma interface satisfaz outra interface:

go 
type Leitor interface {
    Ler() string
}

type LeitorEscritor interface {
    Leitor
    Escrever(s string)
}

var l Leitor = obterLeitor()

// Verificar se o tipo concreto também implementa LeitorEscritor
if le, ok := l.(LeitorEscritor); ok {
    le.Escrever("dados")
}

Type switch

Quando você precisa verificar vários tipos possíveis, encadear type assertions com if/else fica verboso. O type switch resolve isso de forma idiomática:

go type switch 
func descrever(v any) string {
    switch t := v.(type) {  // t recebe o valor já convertido para o tipo correto
    case string:
        return fmt.Sprintf("string com %d caracteres", len(t))
    case int:
        return fmt.Sprintf("inteiro: %d", t)
    case bool:
        if t {
            return "booleano verdadeiro"
        }
        return "booleano falso"
    case []int:
        return fmt.Sprintf("slice de int com %d elementos", len(t))
    case nil:
        return "nil"
    default:
        return fmt.Sprintf("tipo desconhecido: %T", v)
    }
}

fmt.Println(descrever("Go"))        // string com 2 caracteres
fmt.Println(descrever(42))          // inteiro: 42
fmt.Println(descrever([]int{1,2}))  // slice de int com 2 elementos
fmt.Println(descrever(nil))         // nil

Múltiplos tipos no mesmo case

go 
func eNumero(v any) bool {
    switch v.(type) {
    case int, int8, int16, int32, int64,
         uint, uint8, uint16, uint32, uint64,
         float32, float64:
        return true
    default:
        return false
    }
}

// Nota: quando há múltiplos tipos no mesmo case,
// a variável t não pode ser usada — o tipo seria ambíguo
%T no fmt
O verbo %T do pacote fmt imprime o tipo de qualquer valor em tempo de execução — útil para debugging. fmt.Sprintf("%T", v) retorna uma string como "main.Produto" ou "[]int".

Interfaces pequenas (filosofia Go)

A maior parte das interfaces da stdlib de Go tem um ou dois métodos. Essa não é coincidência — é filosofia. Rob Pike resumiu: "The bigger the interface, the weaker the abstraction." Interfaces grandes exigem mais do implementador e acoplam mais. Interfaces de um método são quase universalmente satisfazíveis.

go interfaces de um método da stdlib 
// io.Reader — lê bytes
type Reader interface {
    Read(p []byte) (n int, err error)
}

// io.Writer — escreve bytes
type Writer interface {
    Write(p []byte) (n int, err error)
}

// io.Closer — libera recurso
type Closer interface {
    Close() error
}

// fmt.Stringer — representa como string
type Stringer interface {
    String() string
}

// error — a interface mais usada de Go
type error interface {
    Error() string
}

Composição de interfaces

Interfaces maiores são construídas pela composição de interfaces menores — não redefinindo tudo do zero:

go 
// io.ReadWriter = Reader + Writer
type ReadWriter interface {
    Reader
    Writer
}

// io.ReadWriteCloser = Reader + Writer + Closer
type ReadWriteCloser interface {
    Reader
    Writer
    Closer
}

// O mesmo padrão para interfaces do seu código:
type Storage interface {
    Salvar(r Resultado)
    Buscar(id string) (Resultado, bool)
}

// Interfaces separadas com responsabilidades únicas:
type Salvador interface {
    Salvar(r Resultado)
}

type Buscador interface {
    Buscar(id string) (Resultado, bool)
}

// Funções que só precisam salvar recebem Salvador — não Storage inteiro
// Isso facilita testes: o mock só precisa implementar Salvar
Defina interfaces onde são usadas, não onde são implementadas
Em Go, a convenção é declarar a interface no pacote que a consome — não no pacote que a implementa. O pacote checker define a interface Checker que ele mesmo usa. Quem quiser fornecer uma implementação apenas implementa os métodos. Isso inverte a dependência: o consumidor define o contrato, o fornecedor o respeita.

Erros comuns com interfaces

Interfaces em Go têm dois comportamentos que surpreendem quem vem de outras linguagens. Entendê-los evita bugs difíceis de diagnosticar.

1 — Interface nil vs nil concreto

Uma variável de interface tem dois campos internos: tipo e valor. Uma interface é nil apenas quando ambos são nil. Se o campo tipo for preenchido, a interface não é nil — mesmo que o valor seja nil:

go armadilha clássica 
type MeuErro struct{ msg string }

func (e *MeuErro) Error() string { return e.msg }

func podeFalhar(falhar bool) error {
    var err *MeuErro  // nil do tipo *MeuErro

    if falhar {
        err = &MeuErro{msg: "algo falhou"}
    }

    return err  // ⚠️ retorna interface com tipo=*MeuErro, valor=nil
}

err := podeFalhar(false)
if err != nil {
    fmt.Println("erro:", err)  // ← esta linha executa! err não é nil
}
// Por quê? A interface retornada tem tipo=*MeuErro, valor=nil
// Tipo preenchido = interface não nil
go correção 
// Correto: retornar nil da interface, não nil do tipo concreto
func podeFalhar(falhar bool) error {
    if falhar {
        return &MeuErro{msg: "algo falhou"}
    }
    return nil  // nil de interface — ambos os campos nil
}

2 — Receiver por valor não satisfaz interface com receiver por ponteiro

go 
type Incrementador interface {
    Incrementar()
}

type Contador struct{ n int }

// Receiver por PONTEIRO — modifica o estado
func (c *Contador) Incrementar() { c.n++ }

var i Incrementador

i = &Contador{}  // ✓ ponteiro satisfaz a interface
i = Contador{}   // ✗ ERRO: Contador does not implement Incrementador
                 //   (Incrementar method has pointer receiver)

// Por quê? Go pode pegar o endereço de *Contador para chamar o método,
// mas não pode garantir endereçabilidade de um valor em todos os contextos
Receiver definido em Valor satisfaz interface? Ponteiro satisfaz interface?
func (c Contador) ✓ Sim ✓ Sim
func (c *Contador) ✗ Não ✓ Sim
Não crie interfaces antecipadamente
Um erro comum vindo de outras linguagens é definir interfaces antes de ter duas implementações concretas. Em Go, o padrão é o oposto: escreva o tipo concreto primeiro. Quando uma segunda implementação for necessária — ou quando um teste exigir um mock — extraia a interface nesse momento. Interfaces prematuras criam acoplamento desnecessário e abstrações que nunca se justificam.
Quiz · Questão 1 de 3 Verificação de entendimento

O código abaixo compila?

go 
type Voador interface {
    Voar() string
}

type Aviao struct{}
func (a Aviao) Voar() string { return "vroom" }

type Passaro struct{}
func (p Passaro) Voar() string  { return "flap" }
func (p Passaro) Cantar() string { return "piu" }

func decolar(v Voador) {
    fmt.Println(v.Voar())
}

func main() {
    decolar(Aviao{})
    decolar(Passaro{})
}
✓ Correto! Em Go, um tipo satisfaz uma interface quando tem ao menos os métodos que ela exige. Ter métodos adicionais é permitido — e comum. Passaro tem Voar() e Cantar(); como Voador só exige Voar(), Passaro a satisfaz sem problemas.
Quiz · Questão 2 de 3 Verificação de entendimento

Qual é o output do código abaixo?

go 
type Falha struct{}
func (f *Falha) Error() string { return "falha" }

func gerarErro(retornar bool) error {
    var f *Falha
    if retornar {
        f = &Falha{}
    }
    return f
}

func main() {
    err := gerarErro(false)
    if err != nil {
        fmt.Println("tem erro")
    } else {
        fmt.Println("sem erro")
    }
}
✓ Correto! Esta é a armadilha mais clássica de interfaces em Go. A função retorna f (um *Falha nil) convertido para error. A interface resultante tem tipo=*Falha e valor=nil. Como o campo tipo não é nil, a interface inteira não é nil — e o if err != nil é verdadeiro. A correção é retornar nil diretamente, não uma variável tipada nil.
Quiz · Questão 3 de 3 Verificação de entendimento

O que acontece ao executar o código abaixo?

go 
var v any = 42

s, ok := v.(string)
fmt.Println(s, ok)
✓ Correto! A forma com dois valores (s, ok := v.(string)) nunca causa panic. Quando o tipo não corresponde, ok é false e s recebe o zero value de string — que é a string vazia "". O output é uma linha em branco seguida de false. Use sempre esta forma quando não tiver certeza do tipo concreto.
Exercício 1 — Identificar satisfação de interface Aplicação prática

Dado o código abaixo, quais tipos satisfazem a interface Formatador?

go 
type Formatador interface {
    Formatar() string
}

type A struct{}
func (a A) Formatar() string { return "A" }

type B struct{}
func (b *B) Formatar() string { return "B" }

type C struct{}
func (c C) Formatar() string   { return "C" }
func (c C) Validar() bool      { return true }

type D struct{}
func (d D) formatar() string { return "D" }  // minúsculo
✓ Correto! A tem receiver por valor — satisfeito por valor e ponteiro. *B tem receiver por ponteiro — satisfeito apenas por ponteiro (B{} não satisfaz, mas &B{} satisfaz). C tem receiver por valor e métodos extras — eles não impedem a satisfação. D tem formatar com letra minúscula — é um método não-exportado, invisível fora do pacote, e não conta como implementação de Formatar (F maiúsculo).
Exercício 2 — Type switch Aplicação prática

Uma função recebe any e deve retornar o dobro do valor para tipos numéricos, o texto em maiúsculas para strings, e "tipo não suportado" para qualquer outro tipo. Qual implementação está correta?

✓ Correto! A forma switch t := v.(type) é a idiomática: a variável t já carrega o valor convertido para o tipo do case atual — sem precisar fazer type assertion manual dentro do case. A opção de agrupar int e float64 no mesmo case não funciona para operações aritméticas porque t ficaria com tipo ambíguo e não poderia ser multiplicado. Cada tipo numérico precisa do seu próprio case.
