sync.Mutex

Goroutines compartilham memória — e isso cria um problema: quando duas goroutines leem e escrevem a mesma variável ao mesmo tempo, o resultado é uma race condition. O valor final depende de qual goroutine executou por último, e isso muda a cada run. O programa parece funcionar em testes e quebra em produção.

O sync.Mutex (mutual exclusion lock) garante que apenas uma goroutine execute uma seção de código por vez. Quem tenta entrar enquanto o mutex está bloqueado fica suspenso — não ocupa CPU, apenas aguarda.

go contador seguro para concorrência 
import "sync"

type Contador struct {
    mu    sync.Mutex
    valor int
}

func (c *Contador) Incrementar() {
    c.mu.Lock()
    defer c.mu.Unlock()  // garante unlock mesmo se houver panic
    c.valor++
}

func (c *Contador) Valor() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.valor
}

// Uso correto: 1000 goroutines incrementando o mesmo contador
func main() {
    var wg sync.WaitGroup
    c := &Contador{}

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            c.Incrementar()
        }()
    }

    wg.Wait()
    fmt.Println(c.Valor())  // sempre 1000 — nunca 997 ou 1001
}

Regras do Mutex

go erros comuns 
var mu sync.Mutex

// ✗ DEADLOCK: a mesma goroutine tenta Lock duas vezes
// sync.Mutex não é reentrante — bloqueia para sempre
mu.Lock()
mu.Lock()  // trava aqui eternamente

// ✗ Unlock sem Lock anterior: panic em runtime
mu.Unlock()

// ✗ Copiar um Mutex após primeiro uso invalida o estado
// Mutex deve ser passado por ponteiro, nunca por valor
type Cache struct{ mu sync.Mutex }
c1 := Cache{}
c2 := c1  // ✗ copia o mutex — c2.mu está em estado indefinido
_ = c2

// ✓ Sempre: Lock → seção crítica → Unlock (via defer)
mu.Lock()
defer mu.Unlock()
// ... operações seguras aqui
Não copie tipos do pacote sync
sync.Mutex, sync.WaitGroup, sync.Once e outros tipos do pacote sync não devem ser copiados após o primeiro uso. O go vet detecta isso e emite um aviso. Sempre embuta-os em structs e passe a struct por ponteiro.

sync.RWMutex

Um sync.Mutex trata leitura e escrita da mesma forma: bloqueia tudo para todos. Mas leituras concorrentes são seguras — o problema é leitura simultânea a uma escrita. Quando o padrão de acesso é muitas leituras, poucas escritas, bloquear leitores desnecessariamente desperdiça performance.

O sync.RWMutex resolve isso com dois tipos de lock: múltiplos leitores podem segurar RLock() ao mesmo tempo, mas uma escrita com Lock() exclui todos — leitores e escritores.

go cache com leitura concorrente 
type Cache struct {
    mu    sync.RWMutex
    dados map[string]string
}

// Leitura: múltiplas goroutines podem chamar ao mesmo tempo
func (c *Cache) Get(chave string) (string, bool) {
    c.mu.RLock()
    defer c.mu.RUnlock()
    v, ok := c.dados[chave]
    return v, ok
}

// Escrita: exclusiva — bloqueia todos os outros acessos
func (c *Cache) Set(chave, valor string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    if c.dados == nil {
        c.dados = make(map[string]string)
    }
    c.dados[chave] = valor
}

Quando RWMutex é a escolha certa

Situação Escolha
Leitura e escrita em proporção similar sync.Mutex
Muitas leituras, escritas raras (cache, config, lookup) sync.RWMutex
Contagem, flag, ponteiro simples sob concorrência intensa sync/atomic
Writer starvation: escritores podem ficar bloqueados indefinidamente
Se leitores chegam continuamente, um escritor aguardando Lock() pode esperar muito tempo — os leitores já ativos terminam, mas novos são admitidos antes do escritor ter chance. Na implementação do Go, quando um escritor está aguardando, novos RLock() ficam bloqueados — mas isso é um detalhe de implementação, não uma garantia de spec. Em cargas extremas, meça antes de assumir que RWMutex é mais rápido.

sync.Once

Algumas inicializações devem acontecer exatamente uma vez — não importa quantas goroutines chamem o código ao mesmo tempo. O padrão naive com um bool e um mutex funciona, mas é verboso e fácil de errar. sync.Once encapsula esse padrão de forma idiomática e com garantias formais.

go singleton de conexão de banco 
type DB struct {
    pool *sql.DB
    once sync.Once
    err  error
}

func (db *DB) Conectar(dsn string) (*sql.DB, error) {
    db.once.Do(func() {
        db.pool, db.err = sql.Open("postgres", dsn)
        if db.err == nil {
            db.err = db.pool.Ping()
        }
    })
    return db.pool, db.err
}

// Mesmo que 100 goroutines chamem Conectar simultaneamente,
// sql.Open é chamado uma única vez. As outras 99 aguardam o
// Do terminar e recebem o pool já inicializado.

Comportamento com erro

sync.Once tem uma propriedade importante e às vezes surpreendente: se a função passada ao Do falhar, ela não é chamada novamente. Uma vez executada, o Once está "queimado" para sempre.

go armadilha do Once com erro 
var once sync.Once
var config *Config

func CarregarConfig(caminho string) (*Config, error) {
    var err error
    once.Do(func() {
        config, err = lerArquivo(caminho)
    })
    // ✗ Problema: se lerArquivo falhou, once.Do não vai rodar de novo.
    // Chamadas subsequentes retornam config=nil, err=nil — silenciosamente errado.
    return config, err
}

// ✓ Solução: armazenar o erro no estado compartilhado
type Loader struct {
    once   sync.Once
    config *Config
    err    error
}

func (l *Loader) Carregar(caminho string) (*Config, error) {
    l.once.Do(func() {
        l.config, l.err = lerArquivo(caminho)
    })
    return l.config, l.err  // err preservado entre chamadas
}
sync.OnceValue e sync.OnceFunc (Go 1.21+)
Go 1.21 adicionou sync.OnceValue[T] e sync.OnceFunc — wrappers genéricos que tornam o padrão de inicialização única ainda mais ergonômico: getConfig := sync.OnceValue(func() *Config { return lerConfig() }). Cada chamada a getConfig() retorna o mesmo valor, calculado apenas uma vez.

sync.Map

Maps em Go não são thread-safe. Leituras concorrentes são permitidas, mas qualquer escrita simultânea — mesmo que em chaves diferentes — causa um panic de runtime com a mensagem concurrent map writes. O módulo 11 cobriu isso.

A solução direta é proteger o map com um mutex. Mas o pacote sync oferece sync.Map: um map otimizado para dois casos de uso específicos onde ele supera map + RWMutex.

go API do sync.Map 
var m sync.Map

// Store: armazenar
m.Store("sessão-abc", &Sessao{UserID: 42})

// Load: ler — retorna (value any, ok bool)
if v, ok := m.Load("sessão-abc"); ok {
    sessao := v.(*Sessao)  // type assertion necessária — sync.Map usa any
    fmt.Println(sessao.UserID)
}

// LoadOrStore: atomic — carrega se existe, armazena se não existe
// Retorna o valor atual e se já existia
valor, carregado := m.LoadOrStore("chave", "valor-padrão")

// Delete
m.Delete("sessão-abc")

// Range: itera — não garante ordem, snapshot pode ser inconsistente
m.Range(func(k, v any) bool {
    fmt.Printf("%v: %v\n", k, v)
    return true  // retornar false interrompe a iteração
})

Quando usar sync.Map vs map+mutex

Use sync.Map quando Use map+RWMutex quando
Chaves são escritas uma vez e lidas muitas vezes (cache de rotas, resultados de lookup) Leituras e escritas são frequentes e nas mesmas chaves
Muitas goroutines lendo/escrevendo chaves disjuntas (sharding por chave) Você precisa de type safety (sync.Map usa any)
sync.Map não é o map padrão com lock por cima
sync.Map tem uma estrutura interna de dois estágios (read map e dirty map) que o torna mais rápido que map+Mutex nos dois cenários acima, mas mais lento no caso geral. A documentação oficial diz explicitamente: "O tipo Map deve ser usado apenas em casos de uso específicos". Na dúvida, use map+RWMutex — é mais simples, type-safe e mais fácil de raciocinar.

atomic

Mutex suspende goroutines — há custo de context switch. Para operações simples em valores escalares (contadores, flags, ponteiros), o pacote sync/atomic oferece operações que o hardware executa atomicamente: sem locks, sem suspensão, sem context switch. São as operações mais baratas disponíveis para sincronização.

go operações atômicas básicas 
import "sync/atomic"

var (
    contadorReqs atomic.Int64   // Go 1.19+ — tipo genérico, zero value seguro
    servidorVivo atomic.Bool
    config       atomic.Pointer[Config]
)

// Incremento atômico — sem mutex, sem race condition
contadorReqs.Add(1)
total := contadorReqs.Load()

// Flag de shutdown
servidorVivo.Store(true)
// ... em outra goroutine:
if !servidorVivo.Load() {
    return  // servidor sendo desligado
}

// Troca atômica de ponteiro — config hot-reload sem downtime
novaConfig := &Config{Timeout: 30 * time.Second}
config.Store(novaConfig)
// Leitores obtêm sempre um ponteiro consistente:
cfg := config.Load()  // nunca um ponteiro parcialmente escrito

CompareAndSwap — operação fundamental de lock-free

CompareAndSwap (CAS) é a operação atômica mais poderosa: troca o valor somente se ele ainda é o valor esperado. É a base de estruturas lock-free e de padrões como o spin-lock.

go CAS: compare and swap 
var estado atomic.Int32
const (
    Parado  int32 = 0
    Rodando int32 = 1
)

// Tenta transitar de Parado para Rodando atomicamente
// Retorna true apenas se conseguiu — evita que duas goroutines
// "iniciem o servidor" ao mesmo tempo
func iniciar() bool {
    return estado.CompareAndSwap(Parado, Rodando)
}

// Em produção: implementação de rate limiter lock-free
type RateLimiter struct {
    reqs atomic.Int64
}

func (r *RateLimiter) Allow(limite int64) bool {
    atual := r.reqs.Add(1)
    return atual <= limite
}
Go 1.19: atomic.Int64, atomic.Bool, atomic.Pointer
Antes de Go 1.19, o pacote sync/atomic exportava apenas funções como atomic.AddInt64(&n, 1) — exigindo que você gerenciasse o alinhamento de memória manualmente em structs. Go 1.19 adicionou os tipos atomic.Int32, atomic.Int64, atomic.Bool, atomic.Pointer[T] e atomic.Uint64 — mais seguros, mais ergonômicos, e com zero value funcional. Prefira-os às funções legadas em código novo.
Atomic não compõe — mutex sim
Operações atômicas garantem atomicidade individualmente. Se você precisar de uma operação que lê e escreve dois campos atomicamente (ex: incrementar um contador e atualizar um timestamp juntos), atomic não resolve — você precisa de um mutex em torno das duas operações. Atomic é para escalares simples; mutex é para invariantes compostos.

O que acontece quando a função abaixo é chamada?

go 
var mu sync.Mutex

func operacao() int {
    mu.Lock()
    defer mu.Unlock()
    return calcular()
}

func calcular() int {
    mu.Lock()
    defer mu.Unlock()
    return 42
}
✓ Correto! sync.Mutex não é reentrante — ao contrário de locks em Java ou Python, a mesma goroutine bloqueará tentando adquirir um lock que ela mesma segura. O programa trava para sempre (deadlock detectado pelo runtime somente se todas as goroutines estiverem bloqueadas). A solução é refatorar para não chamar funções que fazem Lock a partir de dentro de uma seção crítica, ou expor uma versão interna sem lock.
Quiz · Questão 2 de 3 Verificação de entendimento

O código abaixo parece correto. Qual é o bug?

go 
var (
    once sync.Once
    db   *sql.DB
)

func GetDB() (*sql.DB, error) {
    var err error
    once.Do(func() {
        db, err = sql.Open("postgres", os.Getenv("DSN"))
    })
    return db, err
}
✓ Correto! err é uma variável local de GetDB(). Na primeira chamada, a closure captura e escreve nela — mas essa variável desaparece após o retorno. Na segunda chamada, once.Do não roda mais; err é uma nova variável local inicializada com nil. O chamador recebe nil, nil e não sabe que a inicialização falhou. A correção é declarar err como parte do estado global junto com db.
Quiz · Questão 3 de 3 Verificação de entendimento

Qual afirmação sobre o código abaixo é verdadeira?

go 
type Estatisticas struct {
    reqs     atomic.Int64
    bytes    atomic.Int64
}

func (e *Estatisticas) Registrar(tamanho int64) {
    e.reqs.Add(1)
    e.bytes.Add(tamanho)
}

func (e *Estatisticas) Snapshot() (reqs, bytes int64) {
    return e.reqs.Load(), e.bytes.Load()
}
✓ Correto! Cada Add e Load individual é atômico — sem race condition em nenhum campo isolado. Mas Snapshot lê dois campos em dois instantes diferentes: entre o Load de reqs e o de bytes, outra goroutine pode ter chamado Registrar e incrementado bytes. O snapshot retorna reqs=5, bytes=1020 quando o estado real coerente seria reqs=4, bytes=820 ou reqs=5, bytes=1220. Para snapshots consistentes entre campos, use mutex.

✓ Correto! atomic.Pointer[Config] é a solução idiomática para hot-reload de configuração. Handlers chamam cfg := configPtr.Load() e obtêm um ponteiro imutável para a config atual — sem bloquear, sem esperar. Exercício 2 — Bug de sincronização Aplicação prática

O código abaixo usa sync.RWMutex mas tem um bug sutil que pode causar deadlock. Qual é o problema?

go 
type Repositorio struct {
    mu   sync.RWMutex
    dados map[string]int
}

func (r *Repositorio) IncrementarOuCriar(chave string) {
    r.mu.RLock()
    v, ok := r.dados[chave]
    r.mu.RUnlock()

    if !ok {
        v = 0
    }
    r.mu.Lock()
    r.dados[chave] = v + 1
    r.mu.Unlock()
}
✓ Correto! O intervalo entre RUnlock e Lock é uma janela de race condition: duas goroutines podem ler v=5, ambas desbloqueiam o RLock, ambas adquirem o Lock separadamente e escrevem 6 — quando o resultado correto seria 7. Isso é um problema clássico de check-then-act não atômico. A correção é usar mu.Lock() desde o início da operação, que abrange tanto a leitura quanto a escrita. O RWMutex aqui não traz benefício — o padrão correto é Mutex simples.
