O que é um channel

Um channel é um cano tipado por onde goroutines enviam e recebem valores. É o mecanismo central de comunicação da concorrência em Go — a linguagem preferiu channels a memória compartilhada, seguindo o princípio criado por Tony Hoare nos anos 1970 e adotado como lema do Go:

O princípio central do Go
"Do not communicate by sharing memory; instead, share memory by communicating."

Em vez de duas goroutines competirem por acesso a uma variável com locks, elas passam o dado por um channel. Quem tem o dado é quem está segurando o valor recebido — sem disputa de acesso, sem corrida.

Criando e usando um channel

Channels são criados com make, pois são referências a estruturas internas do runtime — não podem ser declarados com var sem make (resultariam em nil):

go channel básico 
// make(chan T) cria um channel unbuffered do tipo T
ch := make(chan int)

// Enviar e receber em goroutines separadas
go func() {
    ch <- 42  // envia o valor 42 para o channel
}()

v := <-ch      // recebe o valor do channel
fmt.Println(v) // 42

O operador <- serve para ambas as direções. Quando à esquerda de um channel (ch <- v), envia. Quando à esquerda de uma variável (v := <-ch), recebe. A sintaxe foi escolhida para lembrar visualmente o fluxo de dados.

Sincronização implícita

Um channel unbuffered garante sincronia: o envio só completa quando alguém está pronto para receber, e vice-versa. Isso cria um ponto de encontro (rendezvous) entre goroutines — e é ao mesmo tempo mecanismo de comunicação e de sincronização:

go channel como sincronizador 
func main() {
    done := make(chan struct{})  // canal de sinalização — não carrega dados

    go func() {
        fmt.Println("trabalhando...")
        time.Sleep(500 * time.Millisecond)
        fmt.Println("concluído!")
        done <- struct{}{}  // sinaliza que terminou
    }()

    <-done  // main bloqueia aqui até receber o sinal
    fmt.Println("goroutine concluída, encerrando")
}
// Sem o <-done, main poderia encerrar antes da goroutine imprimir qualquer coisa
var ch chan int cria um channel nil
Declarar var ch chan int sem make resulta em ch == nil. Enviar ou receber de um channel nil bloqueia para sempre — causando deadlock. Sempre use make(chan T) ou make(chan T, n) para criar um channel utilizável.

Buffered vs Unbuffered

A diferença entre os dois tipos de channel é a presença (ou não) de uma fila interna de capacidade fixa. Essa distinção muda completamente o comportamento de bloqueio — e portanto o design dos programas concorrentes.

Unbuffered — sincronização estrita

Criado com make(chan T) (sem capacidade). Envio e recebimento bloqueiam até que o outro lado esteja pronto. É como uma passagem de mão em mão — os dois precisam estar presentes:

go unbuffered — bloqueio mútuo 
ch := make(chan string)

go func() {
    fmt.Println("produtor: pronto para enviar")
    ch <- "mensagem"  // BLOQUEIA até alguém receber
    fmt.Println("produtor: enviou")
}()

time.Sleep(100 * time.Millisecond)  // atraso artificial
fmt.Println("consumidor: pronto para receber")
msg := <-ch  // só aqui o produtor desbloqueia
fmt.Println("consumidor recebeu:", msg)

// Saída garantida:
// produtor: pronto para enviar
// consumidor: pronto para receber
// produtor: enviou        ← só depois que o consumidor recebeu
// consumidor recebeu: mensagem

Buffered — fila assíncrona com limite

Criado com make(chan T, n) onde n é a capacidade. O envio só bloqueia quando o buffer está cheio; o recebimento só bloqueia quando está vazio. Permite que produtor e consumidor trabalhem sem esperar um pelo outro — até o limite da capacidade:

go buffered — fila com capacidade 3 
ch := make(chan int, 3)  // buffer para 3 valores

// Estes três envios NÃO bloqueiam — o buffer absorve
ch <- 1
ch <- 2
ch <- 3

// O quarto BLOQUEARIA — buffer cheio (não faça isso na goroutine principal sem receptor)
// ch <- 4  // deadlock!

fmt.Println(len(ch), cap(ch))  // 3 3 — len=itens atuais, cap=capacidade total

fmt.Println(<-ch)  // 1  — FIFO: primeiro que entrou, primeiro que sai
fmt.Println(<-ch)  // 2
fmt.Println(<-ch)  // 3

Quando usar cada um

Tipo Bloqueia no envio Use quando
make(chan T) Sempre, até ter receptor Sincronização precisa; sinalização; handshake entre goroutines
make(chan T, n) Somente quando buffer está cheio Produtor/consumidor com ritmos diferentes; limitar concorrência; evitar goroutine ociosa
Buffer não elimina sincronização — só a adia
Um erro comum é usar buffer para "resolver" um deadlock sem entender a causa. Se o buffer for 3 e houver 4 envios sem receptor, ainda há deadlock. Buffer ajuda quando há diferença de ritmo legítima e temporária entre produtor e consumidor — não é um atalho para código mal estruturado.

Direção de channels

Por padrão, um channel criado com make é bidirecional — aceita envio e recebimento. Mas ao passar um channel como parâmetro de função, você pode restringir a direção no tipo. Isso transforma a intenção em contrato verificado em tempo de compilação.

go sintaxe de direção 
// Bidirecional — pode enviar e receber
var ch chan int = make(chan int)

// Somente envio — a seta aponta para o channel
var envio chan<- int = ch

// Somente recebimento — a seta aponta para fora
var recv <-chan int = ch

// Atribuições acima são válidas: bidirecional é atribuível a qualquer direção
// O inverso NÃO funciona: chan<- não é atribuível a chan

Direção em parâmetros de função

O uso mais importante de direção é em assinaturas de funções. Comunicar intenção e proteger contra uso incorreto:

go produtor e consumidor com direção 
// produtor: só envia — chan<- int
// Se tentar receber dentro desta função, erro de compilação
func gerarNumeros(out chan<- int, n int) {
    for i := 0; i < n; i++ {
        out <- i
    }
    close(out)  // close é permitido em chan<- (quem envia fecha)
}

// consumidor: só recebe — <-chan int
// Se tentar enviar dentro desta função, erro de compilação
func somarNumeros(in <-chan int) int {
    total := 0
    for v := range in {
        total += v
    }
    return total
}

func main() {
    ch := make(chan int, 5)  // bidirecional — criado aqui

    go gerarNumeros(ch, 5)   // conversão implícita: chan int → chan<- int
    total := somarNumeros(ch)  // conversão implícita: chan int → <-chan int

    fmt.Println(total)  // 0+1+2+3+4 = 10
}

Funções que retornam channels direcionados

Um padrão idiomático em Go é criar o channel dentro da função e retornar apenas a direção de leitura. O chamador não pode enviar nem fechar — o canal pertence à função:

go factory de channel direcionado 
// Retorna <-chan int — chamador só pode ler
func contador(ate int) <-chan int {
    ch := make(chan int)  // bidirecional internamente

    go func() {
        for i := 0; i <= ate; i++ {
            ch <- i
        }
        close(ch)  // responsabilidade de quem criou
    }()

    return ch  // conversão implícita para <-chan int
}

// Chamador só consegue receber — tentar enviar é erro de compilação
for v := range contador(5) {
    fmt.Println(v)  // 0 1 2 3 4 5
}
Direção é documentação executável
Um parâmetro chan<- int documenta ao leitor — sem precisar ler a implementação — que esta função produz dados. Um <-chan int documenta que ela consome. O compilador garante que o código honra essa promessa. É o princípio do menor privilégio aplicado a channels.

range em channels

Assim como em slices e maps, range funciona em channels. A diferença crucial: ao iterar um channel com range, o loop continua recebendo valores até que o channel seja fechado. Se o channel nunca for fechado, o loop bloqueia para sempre.

go range sobre channel 
func gerarTarefas() <-chan string {
    ch := make(chan string)
    go func() {
        tarefas := []string{"indexar", "processar", "notificar", "arquivar"}
        for _, t := range tarefas {
            ch <- t
        }
        close(ch)  // OBRIGATÓRIO para que o range do consumidor termine
    }()
    return ch
}

// range recebe cada valor e para quando o channel é fechado
for tarefa := range gerarTarefas() {
    fmt.Printf("executando: %s\n", tarefa)
}
fmt.Println("todas as tarefas concluídas")

A forma longa — receive com ok

O range é equivalente a uma forma explícita com a variável ok. Entender essa forma ajuda a compreender o que range faz internamente:

go receive com ok — equivalente ao range 
ch := make(chan int, 3)
ch <- 10
ch <- 20
ch <- 30
close(ch)

// Forma longa — ok é false quando o channel está fechado E vazio
for {
    v, ok := <-ch
    if !ok {
        break  // channel fechado e sem mais valores
    }
    fmt.Println(v)
}

// Equivalente com range — mais conciso, mais idiomático
for v := range ch {
    fmt.Println(v)
}
Receber de channel fechado não bloqueia — retorna zero value
Após close(ch), receber do channel não bloqueia: retorna imediatamente o zero value do tipo (0 para int, "" para string, nil para ponteiros) com ok == false. Isso pode causar bugs silenciosos se você ignorar o ok e continuar processando zero values como se fossem dados reais.

Pipeline com range

range em channels é o bloco de construção de pipelines — cada estágio lê do anterior com range e escreve no próximo:

go mini-pipeline com range 
func quadrados(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        for v := range in {  // lê até in ser fechado
            out <- v * v
        }
        close(out)  // fecha o próximo estágio quando este terminar
    }()
    return out
}

nums := make(chan int, 5)
for i := 1; i <= 5; i++ { nums <- i }
close(nums)

for q := range quadrados(nums) {
    fmt.Println(q)  // 1 4 9 16 25
}

close

close(ch) sinaliza que nenhum valor adicional será enviado pelo channel. Não é sobre liberar memória — é uma sinalização semântica: o produtor avisa o consumidor que terminou.

Regras de close

go comportamentos de close 
ch := make(chan int, 2)
ch <- 1
ch <- 2
close(ch)

// ✓ Receber valores pendentes do buffer — funciona normalmente
fmt.Println(<-ch)  // 1
fmt.Println(<-ch)  // 2

// ✓ Receber após esvaziar retorna zero value + ok=false
v, ok := <-ch
fmt.Println(v, ok)  // 0 false

// ✗ Enviar para channel fechado → panic em runtime
// ch <- 3  // panic: send on closed channel

// ✗ Fechar canal já fechado → panic em runtime
// close(ch)  // panic: close of closed channel

// ✗ Fechar canal nil → panic em runtime
// var nilCh chan int
// close(nilCh)  // panic: close of nil channel

A regra fundamental: quem envia fecha

Fechar um channel é responsabilidade do produtor — nunca do consumidor. Se múltiplos produtores enviam para o mesmo channel, nenhum deles pode fechar com segurança (outro pode ainda querer enviar). A solução idiomática é usar um sync.WaitGroup e uma goroutine coordenadora:

go múltiplos produtores — fechar com segurança 
func fanIn(produtores int, trabalho func(int, chan<- string)) <-chan string {
    ch := make(chan string)
    var wg sync.WaitGroup

    for i := 0; i < produtores; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            trabalho(id, ch)  // cada produtor envia ao channel
        }(i)
    }

    // Goroutine coordenadora: espera todos terminarem, então fecha
    go func() {
        wg.Wait()
        close(ch)  // seguro — nenhum produtor mais ativo
    }()

    return ch
}

Fechar como broadcast

Uma propriedade poderosa: fechar um channel desbloqueia todos os receptores simultaneamente. É o único mecanismo nativo de Go para enviar um sinal de "pare" para N goroutines ao mesmo tempo sem loops:

go close como broadcast 
func main() {
    stop := make(chan struct{})

    // Inicia 5 workers — todos aguardam o mesmo sinal
    for i := 0; i < 5; i++ {
        go func(id int) {
            <-stop  // bloqueia até o channel ser fechado
            fmt.Printf("worker %d encerrando\n", id)
        }(i)
    }

    time.Sleep(200 * time.Millisecond)
    close(stop)  // desbloqueia TODOS os workers simultaneamente
    time.Sleep(50 * time.Millisecond)
}
// Todos os 5 workers imprimem quase ao mesmo tempo após close(stop)
context.Context na prática
O padrão done channel mostrado acima é a base do context.Context da stdlib. Quando você usa ctx.Done(), recebe exatamente um <-chan struct{} que é fechado quando o contexto é cancelado ou expira. Entender close como broadcast é pré-requisito para entender context.

Deadlocks

Um deadlock em Go ocorre quando todas as goroutines estão bloqueadas sem nenhuma chance de progredir. O runtime detecta isso e encerra o programa imediatamente com a mensagem fatal error: all goroutines are asleep - deadlock! — diferente de um deadlock silencioso que trava o processo indefinidamente.

Deadlock 1 — envio sem receptor

go envio na goroutine principal sem receptor 
// ✗ DEADLOCK — envia na goroutine principal, ninguém recebe
func main() {
    ch := make(chan int)
    ch <- 1  // bloqueia para sempre — nenhuma goroutine vai receber
    fmt.Println(<-ch)
}
// fatal error: all goroutines are asleep - deadlock!

// ✓ Correção: receptor em goroutine separada
func main() {
    ch := make(chan int)
    go func() { fmt.Println(<-ch) }()
    ch <- 1  // agora há um receptor
}

Deadlock 2 — range sem close

go range em channel nunca fechado 
// ✗ DEADLOCK — range aguarda mais valores que nunca chegam
func main() {
    ch := make(chan int, 3)
    ch <- 1
    ch <- 2
    ch <- 3
    // Esqueceu close(ch) !

    for v := range ch {  // consome 1, 2, 3 e então bloqueia esperando mais
        fmt.Println(v)
    }
}
// fatal error: all goroutines are asleep - deadlock!

// ✓ Correção: fechar o channel após enviar todos os valores
close(ch)
for v := range ch { fmt.Println(v) }

Deadlock 3 — dependência circular

go goroutines esperando uma pela outra 
// ✗ DEADLOCK — cada goroutine espera a outra enviar primeiro
func main() {
    a := make(chan int)
    b := make(chan int)

    go func() {
        v := <-a  // espera goroutine 2 enviar em 'a'
        b <- v
    }()

    go func() {
        v := <-b  // espera goroutine 1 enviar em 'b'
        a <- v
    }()

    time.Sleep(time.Second)
    // Nenhuma goroutine progride — ambas bloqueadas esperando receber
}

// ✓ Correção: uma das goroutines precisa ENVIAR primeiro, não receber
go func() {
    a <- 42  // inicia o fluxo
}()

Deadlock 4 — goroutine vazada (leak)

Goroutines bloqueadas em channels sem receptor não causam o erro de deadlock do runtime se a goroutine principal ainda está rodando. São goroutines vazadas — consomem memória e goroutine stack para sempre:

go goroutine leak — sem erro, mas problemático 
func buscarComTimeout(url string) (string, error) {
    ch := make(chan string)  // unbuffered!

    go func() {
        resp := fazerRequisicao(url)  // pode demorar muito
        ch <- resp  // se o chamador já saiu (timeout), ninguém vai receber
        // → esta goroutine fica bloqueada para sempre: LEAK
    }()

    select {
    case result := <-ch:
        return result, nil
    case <-time.After(2 * time.Second):
        return "", errors.New("timeout")
        // goroutine ainda está rodando tentando enviar para ch...
    }
}

// ✓ Correção: usar channel buffered — goroutine pode enviar e encerrar
ch := make(chan string, 1)  // buffer de 1 — envio não bloqueia
Como o runtime detecta deadlocks
O runtime do Go mantém uma contagem de goroutines rodando. Quando todas as goroutines estão em estado de espera (blocked), o runtime conclui que nenhuma pode progredir e dispara o panic de deadlock. Isso cobre apenas deadlocks totais — goroutines individuais vazadas (onde a goroutine principal ainda roda) não são detectadas automaticamente. Para isso, use ferramentas como runtime.NumGoroutine() em testes ou o pacote goleak.
Quiz · Questão 1 de 3 Verificação de entendimento

O que acontece ao executar o código abaixo?

go 
func main() {
    ch := make(chan int, 2)
    ch <- 10
    ch <- 20
    ch <- 30
    fmt.Println(<-ch)
}
✓ Correto! O channel tem capacidade 2. Os primeiros dois envios (10 e 20) são absorvidos pelo buffer sem bloquear. O terceiro envio (ch <- 30) bloqueia porque o buffer está cheio e a goroutine principal é a única em execução — nenhuma outra goroutine pode receber. Resultado: deadlock. A correção seria usar make(chan int, 3) ou iniciar uma goroutine receptora antes dos envios.
Quiz · Questão 2 de 3 Verificação de entendimento

O que são impressos por v1, ok1, v2 e ok2?

go 
ch := make(chan string, 1)
ch <- "olá"
close(ch)

v1, ok1 := <-ch
v2, ok2 := <-ch

fmt.Println(v1, ok1)
fmt.Println(v2, ok2)
✓ Correto! close não descarta o buffer — apenas sinaliza que nada mais será enviado. O primeiro receive retira "olá" do buffer com ok=true. O segundo receive, com o buffer vazio e o channel fechado, retorna imediatamente com o zero value ("" para string) e ok=false. Ignorar o ok neste segundo receive processaria a string vazia como dado real — um bug silencioso.
Quiz · Questão 3 de 3 Verificação de entendimento

Qual das afirmações sobre o código abaixo é correta?

go 
func pipeline(in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        for v := range in {
            out <- v * 2
        }
        close(out)
    }()
    return out
}
✓ Correto! Este é o padrão de pipeline idiomático em Go. range in itera até in ser fechado. Quando o loop termina, close(out) é chamado — fechando o channel de saída e sinalizando ao próximo consumidor que não há mais dados. A cadeia de fechamentos se propaga estágio por estágio. O range funciona perfeitamente em <-chan int — direção somente-leitura ainda permite receber, o que é exatamente o que range faz.
Exercício 1 — Goroutine leak silenciosa Aplicação prática

O código abaixo implementa uma busca com timeout. Ele funciona corretamente no caminho feliz, mas tem um problema grave no caminho de timeout. Qual é o problema e qual a correção mínima?

go 
func buscarComTimeout(id int) (string, error) {
    ch := make(chan string)  // unbuffered

    go func() {
        resultado := buscarNoBanco(id)  // operação lenta
        ch <- resultado                 // pode bloquear para sempre
    }()

    select {
    case r := <-ch:
        return r, nil
    case <-time.After(1 * time.Second):
        return "", errors.New("timeout")
    }
}
✓ Correto! O problema é goroutine leak. Quando há timeout, a função retorna — mas a goroutine ainda está rodando buscarNoBanco. Quando a busca termina, ela tenta ch <- resultado em um channel unbuffered sem receptor (a função já saiu). A goroutine bloqueia para sempre, vazando. Com make(chan string, 1), a goroutine pode depositar o resultado no buffer e encerrar normalmente, mesmo que ninguém vá lê-lo. O valor no buffer é descartado pelo garbage collector quando o channel perde todas as referências.
Exercício 2 — Fechar channel com múltiplos produtores Aplicação prática

O código inicia 3 goroutines produtoras que enviam para o mesmo channel e cada uma tenta fechá-lo ao terminar. O que acontece em runtime e qual a forma correta de estruturar isso?

go 
func main() {
    ch := make(chan int)

    for i := 0; i < 3; i++ {
        go func(id int) {
            ch <- id * 10
            close(ch)  // cada produtor tenta fechar
        }(i)
    }

    for v := range ch {
        fmt.Println(v)
    }
}
✓ Correto! O código atual causa panic: close of closed channel. A primeira goroutine a terminar fecha o channel; as outras duas tentam fechar novamente — panic. Channels fechados não viram nil e não há isClosed() em Go (seria race condition). A solução idiomática: remover close dos produtores e usar um sync.WaitGroup. Uma goroutine separada faz wg.Wait(); close(ch) — ela espera todos os produtores terminarem e fecha o channel exatamente uma vez. Isso é o padrão fan-in que veremos no Módulo 23.
