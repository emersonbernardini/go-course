Declaração e inicialização

Um map é uma estrutura de dados que associa chaves a valores. Internamente é uma hash table — acesso, inserção e deleção têm complexidade média O(1). O tipo é declarado como map[TipoChave]TipoValor.

go declaração e map literal 
// Map literal — forma mais comum quando os valores iniciais são conhecidos
capitais := map[string]string{
    "Brasil":   "Brasília",
    "França":   "Paris",
    "Japão":    "Tóquio",
}

// Map com tipo numérico como valor
frequencia := map[string]int{
    "go":   150,
    "rust": 80,
    "c":    200,
}

// Acessando valores
fmt.Println(capitais["Brasil"])  // Brasília
fmt.Println(frequencia["go"])    // 150

Tipos válidos como chave

A chave de um map deve ser um tipo comparável — que suporte o operador ==. Tipos válidos: todos os tipos básicos (int, string, bool, etc.), ponteiros, arrays (não slices), e structs cujos campos sejam todos comparáveis. Slices, maps e funções não podem ser chaves.

go 
// ✓ Tipos válidos como chave
var m1 map[string]int
var m2 map[int]string
var m3 map[[2]int]string    // array é comparável
var m4 map[bool]string

// ✗ Tipos inválidos como chave — erro de compilação
var m5 map[[]int]string     // slice não é comparável
var m6 map[map[string]int]string  // map não é comparável
Map nil vs map vazio
var m map[string]int é nil. Ler de um map nil retorna o zero value sem panic. Escrever em um map nil causa panic. Sempre inicialize maps antes de escrever — use literal ou make.

make — criando maps dinamicamente

Quando os valores iniciais não são conhecidos em tempo de compilação, use make para criar um map vazio pronto para uso. A segunda forma de make aceita uma dica de capacidade inicial — não é um limite, apenas uma otimização de alocação:

go 
// make sem dica de capacidade
m := make(map[string]int)

// make com dica de capacidade — evita rehashing para N entradas iniciais
m2 := make(map[string]int, 100)

// Ambos estão prontos para leitura e escrita imediatamente
m["go"] = 1
m2["go"] = 1

// Diferença de make vs literal
// Use make quando: construindo o map incrementalmente (loop, inputs dinâmicos)
// Use literal quando: os pares chave-valor são conhecidos no momento da criação

Leitura, escrita e deleção

As três operações básicas de um map em Go:

go 
m := map[string]int{"a": 1, "b": 2}

// Escrita — insere ou sobrescreve
m["c"] = 3
m["a"] = 99  // sobrescreve

// Leitura
fmt.Println(m["a"])  // 99
fmt.Println(m["z"])  // 0 — chave inexistente retorna zero value, sem panic

// Deleção
delete(m, "b")       // remove a chave "b"
delete(m, "z")       // deletar chave inexistente é uma no-op — sem panic

fmt.Println(len(m))  // len retorna o número de pares chave-valor

Leitura retorna zero value para chaves inexistentes

Este comportamento é importante e tem uma consequência prática: você não consegue distinguir "a chave existe com valor zero" de "a chave não existe" usando apenas a leitura simples. Para isso existe o padrão comma ok — próximo tópico.

go 
contagem := map[string]int{
    "erros": 0,  // valor zero intencional
}

// Impossível distinguir sem comma ok:
fmt.Println(contagem["erros"])   // 0 — chave existe com valor 0
fmt.Println(contagem["avisos"])  // 0 — chave não existe

Comma ok — verificando existência de chave

O idioma comma ok é a forma correta de verificar se uma chave existe em um map. A leitura retorna dois valores: o valor associado e um booleano que indica se a chave estava presente:

go comma ok 
m := map[string]int{
    "go":   1,
    "rust": 2,
}

// Forma simples — não distingue zero value de ausência
v := m["python"]  // 0 — mas não sabemos se a chave existe

// Comma ok — forma correta
valor, ok := m["go"]
if ok {
    fmt.Println("encontrado:", valor)  // encontrado: 1
}

valor2, ok2 := m["python"]
if !ok2 {
    fmt.Println("python não existe")  // python não existe
    _ = valor2  // 0 — zero value de int
}

Padrão idiomático com if de inicialização

Combinado com o if de inicialização que estudamos no Módulo 07, o comma ok fica ainda mais conciso:

go 
config := map[string]string{
    "host": "localhost",
    "port": "8080",
}

if porta, ok := config["port"]; ok {
    fmt.Println("porta configurada:", porta)
} else {
    fmt.Println("porta não definida, usando padrão")
}
// porta e ok só existem dentro do if

Iteração e ordem não garantida

Iterar sobre um map com for range retorna pares chave-valor. A ordem de iteração é intencionalmente não determinística — muda entre execuções, e até entre iterações da mesma execução. Go aleatoriza a ordem deliberadamente para evitar que código dependa de um comportamento que não é garantido pela especificação.

go 
m := map[string]int{"c": 3, "a": 1, "b": 2}

// Iteração — ordem não garantida
for k, v := range m {
    fmt.Printf("%s: %d\n", k, v)
}
// Pode imprimir em qualquer ordem: a, b, c ou c, a, b, etc.

// Apenas chaves
for k := range m {
    fmt.Println(k)
}

// Apenas valores (raro — normalmente a chave é necessária)
for _, v := range m {
    fmt.Println(v)
}

Iteração em ordem determinística

Quando a ordem importa, extraia as chaves para um slice, ordene-o, e então acesse o map via o slice ordenado:

go 
import "sort"

m := map[string]int{"banana": 3, "abacate": 1, "cereja": 2}

// Extrai chaves
chaves := make([]string, 0, len(m))
for k := range m {
    chaves = append(chaves, k)
}

// Ordena
sort.Strings(chaves)

// Itera em ordem alfabética
for _, k := range chaves {
    fmt.Printf("%s: %d\n", k, m[k])
}
// abacate: 1
// banana: 3
// cereja: 2

Maps não são thread-safe

Acessar um map concorrentemente — mesmo apenas para leitura simultânea com uma escrita — causa uma race condition que resulta em panic com fatal error em Go. O runtime do Go detecta escritas concorrentes em maps e encerra o programa imediatamente:

go race condition — fatal error 
m := make(map[string]int)

// PERIGO: goroutines acessando o mesmo map sem sincronização
go func() { m["a"] = 1 }()
go func() { m["b"] = 2 }()

// fatal error: concurrent map writes

Solução 1: sync.RWMutex

Para casos gerais — múltiplos leitores, múltiplos escritores:

go 
import "sync"

type MapSeguro struct {
    mu sync.RWMutex
    m  map[string]int
}

func (ms *MapSeguro) Get(k string) (int, bool) {
    ms.mu.RLock()         // múltiplos leitores simultâneos
    defer ms.mu.RUnlock()
    v, ok := ms.m[k]
    return v, ok
}

func (ms *MapSeguro) Set(k string, v int) {
    ms.mu.Lock()          // exclusão mútua para escrita
    defer ms.mu.Unlock()
    ms.m[k] = v
}

Solução 2: sync.Map

Para casos de alta concorrência com padrão de acesso específico (chaves estáveis, muitas leituras, poucas escritas):

go 
import "sync"

var m sync.Map

// Escrita
m.Store("chave", 42)

// Leitura com comma ok
if v, ok := m.Load("chave"); ok {
    fmt.Println(v.(int))  // type assertion necessária — sync.Map usa interface{}
}

// Deleção
m.Delete("chave")

// Iteração
m.Range(func(k, v interface{}) bool {
    fmt.Println(k, v)
    return true  // false encerra a iteração
})
sync.Map vs mutex: quando usar cada um
Use sync.RWMutex com map regular para a maioria dos casos — é mais simples e tipado. Use sync.Map apenas quando benchmarks mostram vantagem: chaves escritas uma vez e lidas muitas vezes por goroutines diferentes, ou quando cada goroutine lê/escreve um conjunto disjunto de chaves. Estudaremos sync em detalhes no Módulo 24.

Gotchas

Os erros mais frequentes ao trabalhar com maps em Go:

Gotcha 1: escrever em map nil

go 
var m map[string]int  // nil

// Leitura de nil map — OK, retorna zero value
fmt.Println(m["x"])   // 0

// Escrita em nil map — PANIC
m["x"] = 1  // panic: assignment to entry in nil map

// Correção
m = make(map[string]int)
m["x"] = 1  // OK

Gotcha 2: modificar struct armazenada em map

Valores em maps não são endereçáveis — você não pode modificar um campo de uma struct armazenada diretamente:

go 
type Ponto struct{ X, Y int }

m := map[string]Ponto{
    "origem": {0, 0},
}

// ✗ ERRO de compilação — valor de map não é endereçável
m["origem"].X = 10

// ✓ Solução 1: copiar, modificar, reatribuir
p := m["origem"]
p.X = 10
m["origem"] = p

// ✓ Solução 2: usar ponteiro como valor
mp := map[string]*Ponto{
    "origem": {0, 0},
}
mp["origem"].X = 10  // OK — modifica via ponteiro

Gotcha 3: maps são referências — comportam como slices

Assim como slices, maps são tipos de referência. Atribuir um map a outra variável não copia os dados — ambas apontam para a mesma hash table:

go 
a := map[string]int{"x": 1}
b := a  // b é uma referência ao mesmo map

b["x"] = 99
fmt.Println(a["x"])  // 99 — a foi afetado!

// Para clonar um map, copie manualmente
clone := make(map[string]int, len(a))
for k, v := range a {
    clone[k] = v
}
clone["x"] = 0
fmt.Println(a["x"])  // 99 — a não foi afetado

Gotcha 4: incrementar contador inexistente funciona

Esse é um comportamento intencional e útil, mas pode surpreender: como leitura de chave ausente retorna zero value, incrementar um contador inexistente funciona corretamente:

go 
frequencia := make(map[string]int)
palavras := []string{"go", "é", "rápido", "go", "é", "go"}

for _, p := range palavras {
    frequencia[p]++  // se p não existe, começa do zero value (0) e incrementa
}

fmt.Println(frequencia)
// map[é:2 go:3 rápido:1]

Quiz · Questão 3 de 3 Verificação de entendimento

Por que Go aleatoriza a ordem de iteração de maps deliberadamente?

✓ Correto! A aleatorização é uma decisão deliberada da equipe Go para evitar que programadores escrevam código que dependa implicitamente de uma ordem. Nas versões antigas do Go, a ordem era consistente entre execuções — e código incorreto funcionava por acidente. A aleatorização força o programador a ser explícito quando ordem importa.
Exercício 1 — Gotcha de struct em map Aplicação prática

Por que o código abaixo não compila e qual é a correção correta?

go 
type Usuario struct{ Nome string; Ativo bool }

usuarios := map[int]Usuario{
    1: {"Alice", true},
}

usuarios[1].Ativo = false  // linha problemática
✓ Correto! usuarios[1].Ativo = false falha porque usuarios[1] retorna uma cópia não endereçável — você não pode tomar o endereço de um valor de map para modificá-lo. Solução 1: u := usuarios[1]; u.Ativo = false; usuarios[1] = u. Solução 2: map[int]*Usuario — aí usuarios[1].Ativo = false funciona via ponteiro.
Exercício 2 — Contagem de frequência Aplicação prática

Qual é a forma mais idiomática em Go de contar a frequência de cada palavra em um slice de strings?

✓ Correto! freq[p]++ é idiomático e correto porque ler uma chave ausente retorna 0 (zero value de int), então o incremento começa de 0 automaticamente. A alternativa com comma ok funciona, mas é redundante e mais verbosa — não é necessária aqui. Dois slices paralelos seriam O(n) por busca, ineficiente e propenso a bugs de sincronização entre os dois slices.
