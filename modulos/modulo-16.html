Receivers por valor vs por ponteiro

Um método é uma função com um parâmetro especial chamado receiver, declarado entre func e o nome do método. O receiver define em qual tipo o método é chamado:

go sintaxe 
func (receiver Tipo) NomeDoMetodo(params) retorno {
    // corpo
}

O receiver pode ser por valor ou por ponteiro — a diferença é análoga à passagem de argumentos por valor vs ponteiro:

go valor vs ponteiro 
type Contador struct {
    n int
}

// Receiver por valor — opera em cópia, não modifica o original
func (c Contador) Valor() int {
    return c.n
}

// Receiver por ponteiro — opera no original, pode modificar
func (c *Contador) Incrementar() {
    c.n++
}

func (c *Contador) Reset() {
    c.n = 0
}

ct := Contador{}
ct.Incrementar()  // Go passa &ct automaticamente
ct.Incrementar()
fmt.Println(ct.Valor())  // 2
ct.Reset()
fmt.Println(ct.Valor())  // 0

Chamada automática: Go converte entre valor e ponteiro

Go converte automaticamente entre valor e ponteiro ao chamar métodos, desde que a variável seja endereçável. Ou seja, você não precisa escrever (&ct).Incrementar() — Go faz isso por você:

go 
ct := Contador{}

// Ambas as formas são equivalentes — Go converte automaticamente
ct.Incrementar()       // Go trata como (&ct).Incrementar()
(&ct).Incrementar()    // explícito, mas desnecessário

// Exceção: valores não endereçáveis não podem ser convertidos
// Contador{}.Incrementar()  // ERRO — literal não é endereçável

Receiver por valor não modifica o original

go 
type Ponto struct{ X, Y float64 }

// Receiver por valor — retorna novo Ponto, não modifica o original
func (p Ponto) Escalar(f float64) Ponto {
    return Ponto{p.X * f, p.Y * f}
}

// Receiver por ponteiro — modifica in-place
func (p *Ponto) EscalarInPlace(f float64) {
    p.X *= f
    p.Y *= f
}

p := Ponto{3, 4}
p2 := p.Escalar(2)   // p inalterado, p2 = {6, 8}
p.EscalarInPlace(2)  // p modificado para {6, 8}

Quando usar cada receiver

A escolha entre receiver por valor e por ponteiro tem três critérios principais — e uma regra de consistência que os une:

Use receiver por ponteiro quando:

  • O método precisa modificar o receptor — a razão mais óbvia e mais comum
  • A struct é grande — evita cópia cara a cada chamada de método
  • Consistência — se qualquer método do tipo usa ponteiro, todos devem usar

Use receiver por valor quando:

  • O método não precisa modificar o receptor e a struct é pequena
  • O tipo é um tipo básico ou pequeno — time.Time usa receivers por valor por exemplo
  • Semântica de valor é intencional — como tipos imutáveis
Regra de consistência — a mais importante
Se um tipo tem qualquer método com receiver por ponteiro, todos os seus métodos devem usar receiver por ponteiro — mesmo os que não modificam o receptor. Misturar os dois cria confusão sobre o comportamento de atribuição e cópia, e causa problemas com interfaces (o método set com ponteiro não satisfaz interfaces quando o tipo é passado por valor).
go consistência na prática 
type Pilha struct {
    items []int
}

// ✓ Consistente — todos usam ponteiro porque Push precisa modificar
func (p *Pilha) Push(v int)  { p.items = append(p.items, v) }
func (p *Pilha) Pop() int    { n := len(p.items)-1; v := p.items[n]; p.items = p.items[:n]; return v }
func (p *Pilha) Tamanho() int { return len(p.items) }
func (p *Pilha) Vazia() bool  { return len(p.items) == 0 }

// ✗ Inconsistente — Tamanho e Vazia por valor, Push por ponteiro
// Evite: gera confusão e quebra satisfação de interface

Impacto na satisfação de interfaces

Este é o ponto mais sutil. Um método com receiver por ponteiro só está no method set de *T, não de T. Isso afeta diretamente quais interfaces um tipo satisfaz:

go 
type Stringer interface {
    String() string
}

type Pessoa struct{ Nome string }

// Receiver por ponteiro
func (p *Pessoa) String() string { return p.Nome }

var s Stringer

s = &Pessoa{"Alice"}  // ✓ *Pessoa satisfaz Stringer
// s = Pessoa{"Alice"}  // ✗ Pessoa (valor) não satisfaz Stringer
                        //   — String() está no method set de *Pessoa, não de Pessoa

// Com receiver por valor:
// func (p Pessoa) String() string { return p.Nome }
// s = Pessoa{"Alice"}   ✓ Pessoa satisfaz Stringer
// s = &Pessoa{"Alice"}  ✓ *Pessoa também satisfaz (Go promove automaticamente)

Métodos em tipos não-struct

Em Go, qualquer tipo nomeado definido no mesmo pacote pode ter métodos — não apenas structs. Isso permite adicionar comportamento a tipos baseados em tipos básicos, slices, maps e funções.

Métodos em tipos baseados em primitivos

go 
// Tipo nomeado baseado em int
type DiaSemana int

const (
    Domingo DiaSemana = iota
    Segunda
    Terca
    Quarta
    Quinta
    Sexta
    Sabado
)

func (d DiaSemana) String() string {
    nomes := []string{"Domingo", "Segunda", "Terça", "Quarta", "Quinta", "Sexta", "Sábado"}
    if d < Domingo || d > Sabado {
        return "Desconhecido"
    }
    return nomes[d]
}

func (d DiaSemana) EhFimDeSemana() bool {
    return d == Domingo || d == Sabado
}

dia := Sexta
fmt.Println(dia)                 // Sexta — usa String() automaticamente no fmt
fmt.Println(dia.EhFimDeSemana()) // false

Métodos em tipos baseados em slice

go 
type Inteiros []int

func (s Inteiros) Soma() int {
    total := 0
    for _, v := range s {
        total += v
    }
    return total
}

func (s Inteiros) Filtrar(f func(int) bool) Inteiros {
    var resultado Inteiros
    for _, v := range s {
        if f(v) {
            resultado = append(resultado, v)
        }
    }
    return resultado
}

nums := Inteiros{1, 2, 3, 4, 5, 6}
pares := nums.Filtrar(func(n int) bool { return n%2 == 0 })
fmt.Println(pares.Soma())  // 12 (2+4+6)

Métodos em tipos função — padrão http.HandlerFunc

O padrão mais famoso da stdlib: http.HandlerFunc é um tipo baseado em função que implementa a interface http.Handler. Isso permite usar funções comuns diretamente como handlers:

go 
// Como a stdlib implementa http.HandlerFunc
type HandlerFunc func(ResponseWriter, *Request)

// Método ServeHTTP — faz HandlerFunc satisfazer a interface http.Handler
func (f HandlerFunc) ServeHTTP(w ResponseWriter, r *Request) {
    f(w, r)  // chama a própria função como implementação
}

// Na prática: sua função vira um http.Handler sem criar struct
func meuHandler(w http.ResponseWriter, r *http.Request) {
    fmt.Fprintln(w, "olá")
}

// http.HandlerFunc(meuHandler) adapta a função para a interface
http.Handle("/", http.HandlerFunc(meuHandler))
Restrição: apenas tipos do mesmo pacote
Você só pode declarar métodos em tipos definidos no mesmo pacote. Não é possível adicionar métodos a tipos de outros pacotes — incluindo tipos da stdlib como int ou string diretamente. A solução é criar um tipo nomeado local baseado no tipo externo, como nos exemplos acima.
Quiz · Questão 1 de 3 Verificação de entendimento

O tipo Animal abaixo satisfaz a interface Descritivel quando passado por valor?

go 
type Descritivel interface {
    Descrever() string
}

type Animal struct{ Nome string }

func (a *Animal) Descrever() string {
    return "Animal: " + a.Nome
}
✓ Correto! Método com receiver *Animal está no method set de *Animal, não de Animal. var d Descritivel = Animal{"Rex"} é erro de compilação. var d Descritivel = &Animal{"Rex"} funciona. O inverso não é verdade: receiver por valor está no method set de ambos — valor e ponteiro.
Quiz · Questão 2 de 3 Verificação de entendimento

O que é impresso?

go 
type Caixa struct{ valor int }

func (c Caixa) Dobrar() {
    c.valor *= 2
}

cx := Caixa{valor: 5}
cx.Dobrar()
fmt.Println(cx.valor)
✓ Correto! Receiver por valor copia a struct inteira para o parâmetro c. c.valor *= 2 modifica apenas a cópia local. cx.valor permanece 5. Para modificar o original, o receiver deveria ser func (c *Caixa) Dobrar().
Quiz · Questão 3 de 3 Verificação de entendimento

Por que o código abaixo não compila?

go 
package main

func (n int) Dobro() int {
    return n * 2
}
✓ Correto! Go proíbe declarar métodos em tipos de outros pacotes. int pertence ao pacote builtin. A solução é criar um tipo nomeado local: type MeuInt int e então declarar func (n MeuInt) Dobro() MeuInt.
Exercício 1 — Consistência de receiver Aplicação prática

O tipo abaixo mistura receivers por valor e por ponteiro. Qual é o problema e qual a solução correta?

go 
type Fila struct{ items []string }

func (f *Fila) Enqueue(s string) { f.items = append(f.items, s) }
func (f Fila) Tamanho() int      { return len(f.items) }
func (f Fila) Vazia() bool       { return len(f.items) == 0 }
✓ Correto! Como Enqueue usa *Fila, o method set completo está em *Fila. Uma interface que inclua todos os três métodos só seria satisfeita por *Fila — o que é esperado. Mas misturar os dois cria surpresas: Fila (valor) satisfaz uma interface com apenas Tamanho/Vazia, enquanto *Fila satisfaz qualquer interface. Uniformidade com *Fila em todos elimina essa assimetria.
Exercício 2 — Tipo não-struct com método Aplicação prática

Qual é a forma correta de adicionar um método Celsius() ao tipo float64 que converta Fahrenheit para Celsius?

✓ Correto! Crie um tipo nomeado local (type Fahrenheit float64) e declare o método nesse tipo. Isso resolve a restrição de pacote: Fahrenheit é definido no seu pacote, então você pode adicionar métodos a ele. O cast float64(...) no retorno é necessário pois a expressão tem tipo Fahrenheit, não float64.
