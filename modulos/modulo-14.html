Declaração de structs

Uma struct é um tipo composto que agrupa campos nomeados de tipos possivelmente diferentes. É o mecanismo principal de Go para modelar dados — não há classes, herança ou construtores.

go declaração 
type Pessoa struct {
    Nome  string
    Idade int
    Ativo bool
}

// Campos do mesmo tipo podem ser agrupados
type Retangulo struct {
    Largura, Altura float64
}

// Struct com tipos variados
type Servidor struct {
    Host    string
    Porta   int
    TLS     bool
    Tags    []string
    Config  map[string]string
}

Structs são tipos de valor

Assim como arrays, structs são tipos de valor. Atribuir uma struct a outra variável copia todos os campos. Passá-la para uma função copia todos os campos. Para evitar a cópia, use ponteiro — estudaremos isso no Módulo 15.

go 
p1 := Pessoa{Nome: "Alice", Idade: 30}
p2 := p1       // cópia completa de todos os campos

p2.Nome = "Bob"
fmt.Println(p1.Nome)  // Alice — p1 não foi afetada
fmt.Println(p2.Nome)  // Bob

Visibilidade dos campos

A mesma regra de capitalização se aplica aos campos: campo com letra maiúscula é exportado (visível fora do pacote); minúscula é privado ao pacote.

go 
type Conta struct {
    Titular string  // exportado
    Saldo   float64 // exportado
    senha   string  // privado — só acessível dentro do pacote
}

Campos e acesso

Campos são acessados com o operador ponto (.). Campos não inicializados recebem o zero value do seu tipo.

go 
var p Pessoa  // todos os campos com zero value
fmt.Println(p.Nome)   // ""
fmt.Println(p.Idade)  // 0
fmt.Println(p.Ativo)  // false

// Atribuição de campos
p.Nome = "Carlos"
p.Idade = 25
p.Ativo = true

Acesso via ponteiro

Ao acessar campos via ponteiro, Go derreferencia automaticamente. Não é necessário escrever (*p).Nome — p.Nome funciona diretamente:

go 
p := &Pessoa{Nome: "Diana", Idade: 28}

// Ambas as formas são equivalentes — Go prefere a segunda
fmt.Println((*p).Nome)  // Diana
fmt.Println(p.Nome)     // Diana (sintaxe sugar — Go derreferencia automaticamente)

p.Idade = 29  // modifica o campo original via ponteiro

Structs são comparáveis

Se todos os campos de uma struct forem comparáveis, a struct inteira é comparável com == — comparação campo a campo:

go 
type Ponto struct{ X, Y int }

p1 := Ponto{1, 2}
p2 := Ponto{1, 2}
p3 := Ponto{3, 4}

fmt.Println(p1 == p2)  // true
fmt.Println(p1 == p3)  // false

// Structs comparáveis podem ser chaves de map
cache := map[Ponto]string{}
cache[Ponto{0, 0}] = "origem"

// Structs com campos não-comparáveis (slice, map) não são comparáveis
type Ruim struct { Dados []int }
// var r1, r2 Ruim
// r1 == r2  // ERRO de compilação

Struct literal

Structs são inicializadas com literais. Há duas formas: por posição e por nome de campo. A forma por nome é fortemente preferida.

go formas de inicialização 
type Pessoa struct {
    Nome  string
    Idade int
    Ativo bool
}

// Por posição — frágil, não recomendado
p1 := Pessoa{"Alice", 30, true}

// Por nome — idiomático, robusto a refatorações
p2 := Pessoa{
    Nome:  "Alice",
    Idade: 30,
    Ativo: true,
}

// Inicialização parcial — campos omitidos recebem zero value
p3 := Pessoa{Nome: "Bob"}  // Idade=0, Ativo=false

// Ponteiro para struct literal
p4 := &Pessoa{Nome: "Carol", Idade: 25}
Não use inicialização por posição em tipos exportados
Se o tipo for exportado (usado por outros pacotes), a inicialização por posição é um contrato frágil — qualquer adição ou reordenação de campos quebra o código do chamador. Inicialização por nome de campo compila corretamente mesmo após mudanças na struct (novos campos ficam com zero value).

Funções construtoras

Go não tem construtores, mas o padrão idiomático é uma função New* que valida e retorna uma struct inicializada:

go 
type Servidor struct {
    host string
    porta int
}

func NovoServidor(host string, porta int) (*Servidor, error) {
    if host == "" {
        return nil, fmt.Errorf("host não pode ser vazio")
    }
    if porta < 1 || porta > 65535 {
        return nil, fmt.Errorf("porta inválida: %d", porta)
    }
    return &Servidor{host: host, porta: porta}, nil
}

Structs anônimas

Uma struct anônima é definida e usada inline, sem type. É útil para dados temporários, payloads de teste e configurações locais que não precisam de um nome reutilizável.

go struct anônima 
// Variável de struct anônima
config := struct {
    Host  string
    Porta int
}{
    Host:  "localhost",
    Porta: 8080,
}
fmt.Println(config.Host)  // localhost

Casos de uso reais

go 
// 1. Table-driven tests — padrão muito comum em Go
testes := []struct {
    entrada  string
    esperado int
    erro     bool
}{
    {"42", 42, false},
    {"abc", 0, true},
    {"-1", -1, false},
}

for _, tc := range testes {
    resultado, err := strconv.Atoi(tc.entrada)
    if (err != nil) != tc.erro {
        t.Errorf("entrada %q: erro inesperado", tc.entrada)
    }
    if resultado != tc.esperado {
        t.Errorf("entrada %q: esperado %d, obtido %d", tc.entrada, tc.esperado, resultado)
    }
}

// 2. Resposta JSON inline — sem criar tipo nomeado
w.Header().Set("Content-Type", "application/json")
json.NewEncoder(w).Encode(struct {
    Status  string `json:"status"`
    Versao  string `json:"version"`
}{
    Status: "ok",
    Versao: "1.0",
})

Embedding — composição de structs

Go não tem herança. O mecanismo de reutilização de código é composição via embedding: ao embutir um tipo em uma struct sem dar nome ao campo, seus campos e métodos são promovidos à struct externa — acessíveis diretamente.

go embedding básico 
type Animal struct {
    Nome string
}

func (a Animal) Descrever() string {
    return "Animal: " + a.Nome
}

type Cachorro struct {
    Animal       // embedding — sem nome de campo
    Raca  string
}

c := Cachorro{
    Animal: Animal{Nome: "Rex"},
    Raca:   "Labrador",
}

// Campos e métodos de Animal são promovidos
fmt.Println(c.Nome)        // Rex — acesso direto ao campo de Animal
fmt.Println(c.Descrever()) // Animal: Rex — método promovido
fmt.Println(c.Animal.Nome) // Rex — acesso explícito também funciona

Embedding não é herança

A diferença crucial: embedding promove campos e métodos, mas não estabelece um relacionamento "é um". Um Cachorro não é um Animal para o sistema de tipos — não pode ser passado onde um Animal é esperado. A relação "é um" em Go é estabelecida por interfaces (Módulo 17).

go 
func processarAnimal(a Animal) {}

c := Cachorro{Animal: Animal{Nome: "Rex"}}

// processarAnimal(c)       // ERRO — Cachorro não é Animal
processarAnimal(c.Animal)   // OK — passa o Animal embutido explicitamente

Múltiplos embeddings e sobreposição

go 
type Logger struct{}
func (l Logger) Log(msg string) { fmt.Println("[LOG]", msg) }

type DB struct{}
func (d DB) Query(sql string) {}

type App struct {
    Logger  // promove Log()
    DB      // promove Query()
    Nome string
}

app := App{Nome: "MeuApp"}
app.Log("iniciando")   // método de Logger promovido
app.Query("SELECT 1")  // método de DB promovido

// Conflito: se Logger e DB tivessem um método com o mesmo nome,
// seria necessário acesso explícito: app.Logger.MetodoConflitante()
Composição sobre herança
Embedding encoraja o padrão "composição sobre herança" — um princípio amplamente reconhecido como superior à herança para código flexível e testável. Em Go, essa é a única opção, o que elimina hierarquias de herança profundas e frágeis.

Tags de struct

Tags são metadados associados a campos de struct. São strings literais (raw strings com backtick) que ficam após o tipo do campo. Em tempo de execução, podem ser lidas via reflection. Sua principal aplicação é controlar serialização JSON/XML e validação de formulários.

go tags de struct 
type Usuario struct {
    ID    int    `json:"id"`
    Nome  string `json:"nome"`
    Email string `json:"email,omitempty"`  // omite se vazio
    Senha string `json:"-"`                // nunca serializa
    Ativo bool   `json:"ativo"`
}

Comportamento das opções JSON

go 
u := Usuario{
    ID:   1,
    Nome: "Alice",
    // Email vazio, Senha preenchida, Ativo false
    Senha: "secreto",
    Ativo: false,
}

dados, _ := json.Marshal(u)
fmt.Println(string(dados))
// {"id":1,"nome":"Alice","ativo":false}
// Email omitido (omitempty + valor zero)
// Senha omitida (tag "-")

Múltiplas tags por campo

Um campo pode ter tags para múltiplos sistemas — cada tag identificada por sua chave, separadas por espaço:

go 
type Formulario struct {
    Nome  string `json:"nome"  xml:"nome"  validate:"required,min=2"`
    Email string `json:"email" xml:"email" validate:"required,email"`
    Idade int    `json:"idade" xml:"idade" validate:"min=0,max=150"`
}
Tags são convenção, não sintaxe especial
O compilador não interpreta tags — são apenas strings. Quem as lê são bibliotecas via reflect.StructTag. O formato chave:"valor" é uma convenção da comunidade, não uma exigência da linguagem. Qualquer biblioteca pode definir suas próprias chaves de tag.

O que embedding de structs não faz em Go?

✓ Correto! Embedding não é herança. Cachorro com Animal embutido não pode ser passado onde um Animal é esperado — o sistema de tipos não reconhece esse relacionamento. Apenas interfaces criam polimorfismo em Go. O embedding apenas promove campos e métodos para conveniência.

Dado o tipo abaixo, qual JSON é produzido ao serializar Produto{ID: 1, Nome: "Teclado", Preco: 0.0}?

go 
type Produto struct {
    ID    int     `json:"id"`
    Nome  string  `json:"nome"`
    Preco float64 `json:"preco,omitempty"`
    Custo float64 `json:"-"`
}
✓ Correto! omitempty omite o campo se for o zero value do tipo (0.0 para float64). A tag "-" omite o campo sempre, independente do valor. Os campos restantes usam os nomes definidos nas tags.

O que é impresso pelo código abaixo?

go 
type Config struct {
    Debug bool
    Tags  []string
}

a := Config{Debug: true, Tags: []string{"prod"}}
b := a

b.Debug = false
b.Tags[0] = "dev"

fmt.Println(a.Debug, a.Tags[0])
✓ Correto! Ao copiar a struct, campos de tipo valor (bool) são copiados independentemente. Campos de tipo referência ([]string) têm o header copiado, mas o backing array é compartilhado. Modificar b.Tags[0] afeta a.Tags[0]; modificar b.Debug não afeta a.Debug.
Exercício 1 — Table-driven test Aplicação prática

Por que structs anônimas são o padrão para table-driven tests em Go, em vez de criar um tipo nomeado para cada conjunto de casos?

✓ Correto! Structs anônimas para table-driven tests mantêm a definição do schema de teste co-localizada com os casos de teste. O leitor vê imediatamente quais campos cada caso usa, sem precisar procurar uma declaração de tipo em outro lugar. Tipos nomeados para dados usados em um único lugar são desnecessários e poluem o pacote.
Exercício 2 — Comparabilidade Aplicação prática

Quais dos tipos abaixo podem ser usados como chave de map?

go 
type A struct { X, Y int }
type B struct { Nome string; Tags []string }
type C struct { ID int; Config map[string]int }
type D struct { Lat, Lng float64 }
✓ Correto! Uma struct é comparável somente se todos os seus campos forem comparáveis. A (int, int) e D (float64, float64) são comparáveis — podem ser chaves de map. B tem []string (slice não-comparável) e C tem map[string]int (map não-comparável) — ambos tornam a struct não comparável.
