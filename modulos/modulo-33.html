O que são build tags

Build tags (também chamadas de build constraints) são instruções que dizem ao compilador Go se um arquivo deve ou não ser incluído numa compilação. Em vez de usar diretivas de pré-processador como #ifdef do C, Go aplica a seleção no nível de arquivo inteiro: um arquivo ou é compilado, ou é ignorado completamente.

Isso resolve problemas reais em projetos que precisam de comportamento diferente por plataforma, ambiente ou configuração — como código específico para Linux versus Windows, implementações de desenvolvimento versus produção, ou funcionalidades opcionais que só devem existir em certas builds.

go sintaxe moderna — Go 1.17+ 
//go:build linux

package main

// Este arquivo inteiro só é compilado quando GOOS=linux
// Pode conter qualquer código Go válido

A diretiva //go:build deve ser a primeira linha não-vazia do arquivo, antes até da declaração package. Uma linha em branco deve separar a diretiva do restante do arquivo — isso diferencia a constraint de um comentário de documentação comum.

A sintaxe legada — antes do Go 1.17

Antes do Go 1.17 a sintaxe era um comentário especial com // +build. Ela ainda é reconhecida pelo toolchain, mas foi depreciada em favor de //go:build:

go sintaxe legada (depreciada) 
// +build linux

package main

// Problemas da sintaxe antiga:
// 1. Silenciosamente ignorada se não houver linha em branco após ela
// 2. Operadores booleanos com sintaxe confusa (vírgula = OR, espaço = AND)
// 3. Difícil de distinguir de comentários normais
// 4. Fácil de esquecer a linha em branco obrigatória
gofmt sincroniza as duas sintaxes automaticamente
Em arquivos que contêm apenas //go:build, o gofmt (Go 1.17+) adiciona automaticamente o equivalente em // +build para compatibilidade retroativa com toolchains antigos. Em arquivos com apenas a sintaxe legada, o gofmt adiciona a nova. Em projetos novos, escreva apenas //go:build e deixe o gofmt cuidar da compatibilidade.

Constraints de SO e arquitetura

As constraints mais comuns são as de sistema operacional (GOOS) e arquitetura de CPU (GOARCH). O compilador Go define automaticamente essas tags com base no ambiente de compilação — ou nos valores explicitamente passados via variáveis de ambiente para cross-compilation.

Valores de GOOS reconhecidos

bash 
# Listar todos os GOOS e GOARCH suportados
go tool dist list

# Valores mais comuns de GOOS:
# linux, windows, darwin (macOS), freebsd, openbsd, netbsd
# android, ios, js (WebAssembly), wasip1 (WASI)

# Valores mais comuns de GOARCH:
# amd64 (x86-64), arm64 (Apple Silicon / ARM 64-bit)
# 386 (x86-32), arm (ARM 32-bit), mips, mips64, riscv64, wasm

Expressões booleanas nas constraints

A sintaxe //go:build usa expressões booleanas completas com operadores familiares — muito mais legível que a sintaxe legada:

go operadores booleanos 
//go:build linux
// Compila apenas em Linux

//go:build linux || darwin
// Compila em Linux OU macOS (qualquer Unix-like)

//go:build linux && amd64
// Compila apenas em Linux com CPU x86-64

//go:build !windows
// Compila em qualquer SO exceto Windows

//go:build (linux || darwin) && amd64
// Compila em Linux ou macOS, mas apenas com x86-64

//go:build linux && (amd64 || arm64)
// Linux com x86-64 ou ARM64 (ex: Raspberry Pi 64-bit)
Sintaxe nova (//go:build) Sintaxe legada (// +build) Significado
A && B // +build A B AND — ambos obrigatórios
A || B // +build A,B OR — qualquer um
!A // +build !A NOT — exceto este
A lógica invertida da sintaxe legada era fonte de bugs
Na sintaxe legada, espaço significa AND e vírgula significa OR — o oposto do que a maioria das linguagens usa. Era trivial escrever // +build linux windows pensando em "Linux ou Windows" quando na verdade significa "Linux E Windows" (impossível simultaneamente, arquivo nunca compilado). A nova sintaxe //go:build linux || windows é inequívoca.

Tags customizadas

Além das tags predefinidas de SO e arquitetura, você pode definir suas próprias tags e ativá-las com a flag -tags do compilador. Tags customizadas permitem controlar quais partes do código são incluídas com base em critérios de negócio, ambiente ou produto — sem alterar o código-fonte.

go arquivo com tag customizada 
//go:build premium

package pagamento

// Este arquivo só é compilado quando -tags premium for passado
// Sem a flag, este arquivo inteiro é ignorado

func processarPagamentoAvancado(valor float64) error {
    // Lógica exclusiva do plano premium
    return integrarGatewayExterno(valor)
}
bash ativando tags na compilação 
# Compilar sem nenhuma tag customizada
go build ./...

# Compilar com uma tag
go build -tags premium ./...

# Múltiplas tags separadas por vírgula
go build -tags "premium debug" ./...
# ou equivalente (Go 1.17+)
go build -tags premium,debug ./...

# Rodar testes com tag
go test -tags integration ./...

# Verificar quais arquivos seriam compilados com determinadas tags
go list -f '{{.GoFiles}}' -tags premium ./pacote/

Tags predefinidas pela stdlib e toolchain

O toolchain define algumas tags automaticamente que você pode usar em constraints sem precisar passá-las manualmente:

go tags automáticas 
//go:build go1.21
// Compila apenas se a versão do compilador for Go 1.21 ou superior
// Útil para usar APIs introduzidas em versões específicas

//go:build go1.18
// Habilitar código que usa generics (introduzidos no Go 1.18)

//go:build cgo
// Compila apenas quando CGO está habilitado (linkagem com C)
// Automaticamente false quando GONOSUMCHECK ou CGO_ENABLED=0

//go:build !cgo
// Alternativa pura Go quando CGO não está disponível
Convenção de nomes para tags customizadas
Tags customizadas devem usar apenas letras, dígitos, underscores e hífens — e por convenção são escritas em minúsculas. Evite nomes que colidam com tags do sistema: não use nomes de SO (linux, windows), arquiteturas (amd64) ou versões (go1.21). Use nomes descritivos de domínio: integration, e2e, production, premium.

Seleção por nome de arquivo

Além das diretivas //go:build, o compilador Go reconhece automaticamente sufixos nos nomes dos arquivos para aplicar constraints de SO e arquitetura — sem nenhum comentário no código. Essa convenção é usada extensivamente na própria stdlib do Go e é a forma preferida quando o arquivo inteiro é específico de plataforma.

Padrões de nomes reconhecidos

bash sufixos automáticos 
# Padrão: *_GOOS.go
signal_linux.go      # compilado apenas em Linux
signal_windows.go    # compilado apenas em Windows
signal_darwin.go     # compilado apenas em macOS

# Padrão: *_GOARCH.go
asm_amd64.go         # compilado apenas em x86-64
asm_arm64.go         # compilado apenas em ARM64

# Padrão: *_GOOS_GOARCH.go — ambos precisam corresponder
syscall_linux_amd64.go   # Linux + x86-64
syscall_darwin_arm64.go  # macOS + Apple Silicon

# Arquivos de teste com sufixo também funcionam
cache_linux_test.go  # teste específico de Linux

Exemplo prático — implementação por plataforma

bash estrutura de pacote cross-platform 
internal/processo/
├── processo.go          # interface pública — compilado em todas as plataformas
├── processo_linux.go    # implementação Linux (usa /proc)
├── processo_darwin.go   # implementação macOS (usa sysctl)
└── processo_windows.go  # implementação Windows (usa WinAPI)
go processo.go — interface comum 
// processo.go — compilado em todas as plataformas
package processo

// ListarPIDs é declarada em cada arquivo de plataforma
// Esta função existe em processo_linux.go, processo_darwin.go, processo_windows.go
// Cada plataforma fornece sua própria implementação
func ListarTodos() ([]Info, error) {
    return listarPIDs()  // chamada à função definida no arquivo de plataforma
}
go processo_linux.go 
// Sem //go:build — o nome do arquivo já aplica a constraint
package processo

import (
    "os"
    "strconv"
    "strings"
)

func listarPIDs() ([]Info, error) {
    // Implementação Linux: lê /proc para listar processos
    entradas, err := os.ReadDir("/proc")
    if err != nil {
        return nil, err
    }
    var lista []Info
    for _, e := range entradas {
        if _, err := strconv.Atoi(e.Name()); err == nil {
            lista = append(lista, Info{PID: e.Name()})
        }
    }
    return lista, nil
}
Sufixo de nome e //go:build podem coexistir — mas não conflitar
Um arquivo chamado foo_linux.go com //go:build linux && amd64 será compilado apenas em Linux e amd64 — a constraint mais restritiva vence (interseção). Isso é útil para restringir ainda mais um arquivo já limitado pelo nome. Mas cuidado: um arquivo foo_linux.go com //go:build windows nunca será compilado — as constraints são aplicadas com AND.

Integração com go build e go test

Build tags integram com todas as ferramentas do toolchain Go. Entender como inspecionar, depurar e usar tags corretamente nos comandos do dia a dia é essencial para evitar surpresas onde código é silenciosamente excluído da build.

Inspecionando o que será compilado

bash 
# Listar arquivos Go que seriam incluídos na build atual
go list -f '{{.GoFiles}}' ./pacote/

# Com tags customizadas
go list -f '{{.GoFiles}}' -tags integration ./...

# Listar arquivos ignorados (excluídos pelas constraints)
go list -f '{{.IgnoredGoFiles}}' ./pacote/

# Ver todas as informações de build de um pacote
go list -json ./pacote/

# Verificar quais tags estão ativas no ambiente atual
go env GOARCH GOOS CGO_ENABLED GOVERSION

# Cross-compilation: compilar para Linux a partir de macOS
GOOS=linux GOARCH=amd64 go build -o app-linux ./cmd/app/

# Verificar que a build funciona sem executar (apenas compilar)
GOOS=windows go build ./...

Testes com build tags

Um padrão muito comum é separar testes de integração (que precisam de banco de dados, rede ou serviços externos) dos testes unitários rápidos usando uma tag:

go db_integration_test.go 
//go:build integration

package repositorio_test

import (
    "testing"
    "os"
)

// Este teste só roda quando: go test -tags integration ./...
// go test ./...  → ignora este arquivo completamente

func TestBuscarUsuarioNoPostgres(t *testing.T) {
    dsn := os.Getenv("DATABASE_URL")
    if dsn == "" {
        t.Skip("DATABASE_URL não definida — pulando teste de integração")
    }

    db, err := conectar(dsn)
    if err != nil {
        t.Fatalf("falha ao conectar: %v", err)
    }
    defer db.Close()

    usuario, err := BuscarPorID(db, "user-123")
    if err != nil {
        t.Fatalf("erro inesperado: %v", err)
    }
    if usuario.Email != "test@exemplo.com" {
        t.Errorf("email incorreto: got %q, want %q", usuario.Email, "test@exemplo.com")
    }
}
bash comandos no CI/CD 
# Pipeline rápido — apenas testes unitários (sem -tags)
go test ./...

# Pipeline completo — inclui testes de integração
go test -tags integration -timeout 120s ./...

# Rodar apenas testes E2E em ambiente específico
go test -tags "integration e2e" -run TestFluxoCompleto ./...

# Verificar se o código compila para múltiplas plataformas (sem executar)
GOOS=linux   go build ./...
GOOS=darwin  go build ./...
GOOS=windows go build ./...
go vet também respeita build tags
go vet, staticcheck e ferramentas de análise estática também respeitam build tags. Se você rodar go vet ./... sem -tags integration, arquivos marcados com essa tag não serão analisados. Inclua as tags relevantes no pipeline de lint para garantir que todo o código é verificado: go vet -tags integration ./....

Casos de uso reais

Build tags não são um recurso de nicho — aparecem em quase todo projeto Go de médio porte. Conhecer os padrões consolidados evita reinventar soluções para problemas comuns.

Caso 1 — Stub para desenvolvimento local

Quando integrar com um serviço externo (pagamento, e-mail, SMS) é inviável em desenvolvimento, uma implementação stub pode substituir a real com base em tag:

go email_real.go 
//go:build !dev

package notificacao

import "github.com/empresa/sendgrid"

func Enviar(para, assunto, corpo string) error {
    return sendgrid.Send(para, assunto, corpo)
}
go email_dev.go 
//go:build dev

package notificacao

import "log/slog"

// Em desenvolvimento: apenas loga, não envia e-mail real
func Enviar(para, assunto, corpo string) error {
    slog.Info("e-mail simulado", "para", para, "assunto", assunto)
    return nil
}
bash 
# Desenvolvimento: usa o stub (sem chamadas reais ao Sendgrid)
go run -tags dev ./cmd/server/

# Produção: compila com a implementação real
go build -o servidor ./cmd/server/

Caso 2 — Embeder banco de dados de fusos com timetzdata

go tzdata.go 
//go:build timetzdata

package main

// Importar time/tzdata embute o banco de fusos no binário (~450KB)
// Necessário em containers sem tzdata instalado (alpine, scratch)
// Ativado com: go build -tags timetzdata ./...
import _ "time/tzdata"

Caso 3 — Excluir arquivo da build permanentemente

Um padrão especial: //go:build ignore exclui o arquivo de qualquer build, inclusive das ferramentas de análise. É usado para scripts auxiliares, geradores de código e exemplos que ficam no repositório mas não devem ser compilados como parte do pacote:

go gerar_mocks.go 
//go:build ignore

// Este arquivo é um script gerador — nunca compilado como parte do pacote
// Executado manualmente: go run gerar_mocks.go
//
// Ou via go:generate:
//go:generate go run gerar_mocks.go

package main

import (
    "os"
    "text/template"
)

func main() {
    // Gera mocks para testes a partir de interfaces
    tmpl := template.Must(template.ParseFiles("mock.tmpl"))
    f, _ := os.Create("mocks_generated.go")
    defer f.Close()
    tmpl.Execute(f, carregarInterfaces())
}

Caso 4 — Feature flags em tempo de compilação

go metrics_prometheus.go 
//go:build prometheus

package metrics

import "github.com/prometheus/client_golang/prometheus"

var requestsTotal = prometheus.NewCounterVec(
    prometheus.CounterOpts{Name: "http_requests_total"},
    []string{"method", "path", "status"},
)

func init() {
    prometheus.MustRegister(requestsTotal)
}

func RecordRequest(method, path string, status int) {
    requestsTotal.WithLabelValues(method, path, fmt.Sprint(status)).Inc()
}
go metrics_noop.go 
//go:build !prometheus

package metrics

// Implementação vazia quando Prometheus não está habilitado
// O compilador elimina estas chamadas (dead code elimination)
func RecordRequest(method, path string, status int) {}
Compilação condicional vs configuração em runtime
Build tags são decisões em tempo de compilação — o código excluído não existe no binário. Isso é diferente de flags de configuração em runtime (os.Getenv, flags de linha de comando), onde o código existe mas pode ser desativado. Use build tags quando quiser garantia de que o código (e suas dependências) não existam no binário de produção — eliminando surface area de segurança, tamanho do binário e dependências transitivas desnecessárias.
Quiz · Questão 1 de 3 Verificação de entendimento

Em quais plataformas o arquivo abaixo será compilado?

go 
//go:build (linux || darwin) && !arm64

package main
✓ Correto! A expressão (linux || darwin) && !arm64 é avaliada da esquerda para a direita com a precedência normal: primeiro o grupo entre parênteses (linux OU darwin), depois AND com NOT arm64. O resultado: qualquer Linux ou macOS, desde que a arquitetura não seja ARM64. Isso exclui Macs com Apple Silicon (darwin/arm64) e Raspberry Pi 64-bit (linux/arm64), mas inclui Linux amd64, Linux 386, macOS amd64 (Intel), etc.
Quiz · Questão 2 de 3 Verificação de entendimento

O arquivo servidor_linux.go contém a diretiva //go:build linux || windows. Em quais plataformas ele será compilado?

✓ Correto! O sufixo _linux no nome do arquivo e a diretiva //go:build são aplicados simultaneamente com AND — a interseção vence. O sufixo impõe: somente Linux. A diretiva impõe: Linux ou Windows. A interseção de {linux} ∩ {linux, windows} = {linux}. O arquivo é compilado apenas em Linux. Windows é coberto pela diretiva mas excluído pelo sufixo. Esse tipo de combinação costuma ser um bug — a diretiva //go:build linux || windows em um arquivo _linux.go é redundante na parte Linux e ineficaz na parte Windows.
Quiz · Questão 3 de 3 Verificação de entendimento

Por que um arquivo com //go:build ignore e package main pode coexistir em um diretório que já tem outro package main sem causar erro de compilação?

✓ Correto! //go:build ignore usa a tag especial ignore — que nunca é definida pelo toolchain nem pode ser passada via -tags. A constraint nunca é satisfeita, portanto o arquivo é completamente excluído da compilação. O compilador não o processa, não verifica conflitos de pacote, não analisa imports. É exatamente por isso que scripts geradores, exemplos standalone e arquivos //go:generate podem viver no mesmo diretório de um pacote sem conflitar — para o compilador, eles simplesmente não existem.
Exercício 1 — Diagnóstico de arquivo nunca compilado Aplicação prática

Um colega adicionou suporte a Windows no arquivo abaixo, mas em nenhuma plataforma o código é incluído na build. O CI em Linux não compila o arquivo, e em Windows também não. Qual é o problema?

go clipboard_windows.go 
// +build linux windows

//go:build linux

package clipboard
✓ Correto! Há dois problemas sobrepostos. Primeiro: as duas diretivas (// +build linux windows e //go:build linux) são aplicadas com AND — a interseção é apenas Linux, excluindo Windows. Segundo: o sufixo _windows no nome do arquivo exige que a plataforma seja Windows — mas a diretiva restringe a Linux. A interseção de {windows} ∩ {linux} é vazia: o arquivo nunca compila em nenhuma plataforma. A correção é remover ambas as diretivas de comentário e confiar apenas no sufixo _windows.go para a constraint de plataforma.
Exercício 2 — Separar testes de integração Aplicação prática

Você quer que go test ./... rode apenas testes unitários rápidos (sem dependências externas), e que testes que precisam de banco de dados real só sejam executados em CI com o comando go test -tags integration ./.... Qual é a abordagem correta para o arquivo de testes de integração?

✓ Correto! //go:build integration no arquivo de testes é a abordagem canônica em projetos Go. O arquivo inteiro é excluído da compilação sem a tag — os testes não aparecem em go test ./... nem geram overhead de compilação. As alternativas têm desvantagens: subdiretório funciona mas separa os testes da lógica que testam; t.Skip() ainda compila e registra os testes (overhead de build + necessidade de importar dependências pesadas como drivers de banco); e !short é uma convenção diferente — a flag -short é passada para o código do teste via testing.Short(), não exclui arquivos com build tags.
